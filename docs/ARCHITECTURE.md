# Architecture de référence — GoldenBrain

> Référence par domaine, à jour du code. Les invariants `INV-*` sont le contrat : tout identifiant cité par le code doit figurer ici (contrôle de `scripts/check.py`). Les raisons des choix et leur chronologie sont dans `docs/DECISIONS.md` ; la carte fichier → rôle → tests dans `docs/CODE_MAP.md`.

## Raison d'être

Poste de pilotage de tâches confiées à des agents IA, adossé à un vault Markdown. **GoldenBrain pilote ; il n'exécute rien.** Chaque tâche est une conversation d'un harnais natif (Claude Code, Codex, OpenCode, Antigravity, Copilot), reprise telle quelle. Le vault est la seule base de données ; l'état propre au poste (tours actifs, propositions, revues, mandats, sessions, jardinage) vit sous `<donnees>/etat/`, les journaux sous `<donnees>/journal/`.

Nom affiché : GoldenBrain (icône de cerveau doré). Le paquet Python et le dépôt gardent le nom `orchestrateur`.

## Invariants

### Vault
- **INV-VAULT-1** — Une réécriture de tâche ne modifie que les clés gérées (`statut`, `updated`, `harnais`, `session`, `parent`, `projet`, `casquette`, `tags`, `alimente`, `prerequis`, `voir_aussi`, `modele`, `echeance`, `priorite`, `echec_tour`, `ou`, `controle`, `validation`, `validation_accord`, `executant`) et le bloc entre `<!-- orchestrateur:debut -->` et `<!-- orchestrateur:fin -->`. Tout le reste est restitué octet pour octet (ordre des clés, commentaires, clés inconnues, fins de ligne, octets hors UTF-8). Jamais de `yaml.dump` du frontmatter : édition ligne à ligne. Le bloc géré est le dernier `debut` seul sur sa ligne suivi de son `fin` ; un marqueur cité dans la prose n'est jamais une borne. Seule exception : le geste `liberer` retire les clés `paperclip` et `execution`, par la même édition ligne à ligne.
- **INV-VAULT-2** — Écriture atomique (fichier temporaire dans le même dossier puis `os.replace`). Un déplacement ne détruit jamais : refus si la destination existe. Un retrait (persona) déplace, jamais ne supprime.
- **INV-VAULT-3** — Tout chemin écrit est sous `vault.racine` et provient de l'index (tâche ou conteneur connu). Aucun chemin fourni par un client n'est utilisé tel quel.
- **INV-VAULT-4** — Quand `[vault] verrou_paperclip` est vrai, une tâche qui porte la clé `paperclip:` appartient à Paperclip pour son statut : GoldenBrain n'y écrit jamais `statut` ni `tags` (409 sur un geste humain, silence pour le moteur). Le geste humain `liberer` lève le verrou de la tâche. Réglage livré : `false` (Paperclip en sommeil).

### Dossier de travail
- **INV-DEPOT-1** — Tout tour d'une tâche s'exécute dans le dépôt déclaré par son projet ou l'un de ses ancêtres (`depot:` de `contexte.md`, le plus proche l'emporte ; à défaut la table `_meta/projets-externes.md`, dépôt → projet), pour tous les harnais (`depot.conf_harnais` surcharge `dossier` sans muter la config). Un dépôt absent du disque est ignoré : repli sur `[harnais.<nom>] dossier`, puis le dossier personnel. Visible dans la fiche (`dossier_travail`, « Dossier de travail »).

### Exécution
- **INV-EXEC-1** — Jamais de relance automatique d'un tour, hors trois exceptions voulues : la reprise d'office après redémarrage (ci-dessous), le réveil sur quota (INV-EXEC-10) et la bascule unique sur quota épuisé (INV-QUOTA-1) ; jamais les deux pour un même tour. Un tour interrompu est marqué `interrompu`. Les tours actifs sont persistés dans `<donnees>/etat/tours.json` (une entrée par tâche : `tache`, `texte`, `sauts`, `de`, `source`, `mandat`, `role`, `reprise` ; l'ancien format, liste d'identifiants, est lu) ; l'arrêt du serveur tue leurs processus. Au démarrage (`reprise.reprendre_au_demarrage`, lifespan), chaque tour coupé par l'arrêt ou le plantage du serveur est **repris d'office** (INV-REPRISE-1, au plus trois fois par tour) : dans la même session du harnais par un message signé GoldenBrain (`[GoldenBrain — reprise après interruption] …`), ou, sans session ou pour un tour de rôle éphémère, par son message d'origine ; le tour ainsi repris porte `reprise: true` et son compte `reprises` (persisté) ; au plafond de trois il n'est plus repris d'office : incident et retour à l'humain ; un tour gelé par le réseau (INV-RESEAU-1) est persisté sans la marque ; une tâche fermée n'est pas reprise. Un tour arrêté à la main n'est jamais repris d'office. Tout tour `interrompu` se relance par le geste humain « Relancer » (`POST /taches/{id}/relancer`, 409 s'il n'y a rien d'interrompu).
- **INV-EXEC-2** — Un seul tour à la fois par tâche ; les messages suivants attendent en file, dans l'ordre.
- **INV-EXEC-3** — L'identifiant de session est écrit dans la fiche dès qu'il est connu (premier événement `session`), pas en fin de tour.
- **INV-SESSION-1** — Un identifiant de session sans transcript ne fait jamais échouer un tour (`session_perdue.py`) : si la reprise est refusée pour session inconnue (« No conversation found with session ID… » de Claude Code, équivalents des autres harnais) avant toute sortie utile, le moteur journalise un événement `session_perdue`, retire `session` de la fiche et relance UNE fois en conversation neuve ; cette erreur ne compte pas dans l'escalade de modèle (INV-ECO-1). L'interface native refermée avant le premier message (transcript absent) retire elle aussi l'identifiant qu'elle avait posé.
- **INV-EXEC-4** — Chaque tour a son journal brut : `journal/<AAAA-MM-JJ>/<id-tâche>-<HHMMSS>.jsonl` (persona : `<id-tâche>@<persona>-HHMMSS.jsonl` ; conseil : `conseil-<action>-HHMMSS.jsonl`).
- **INV-EXEC-5** — L'agent d'une tâche ne change jamais la structure seul : `orch proposer` crée une proposition ; seul un geste humain (`/accepter`) l'exécute, hors gestes de routine appliqués d'office et annulables (INV-PROP-1). Créer une tâche neuve (`orch creer`, `POST /taches`) n'est pas un changement de structure : aucune tâche existante n'est déplacée ni transformée (c'est l'outil de l'agent de tri Telegram). Il n'écrit jamais `cloture` ni `abandonne` ; `fait` est écrit par le moteur sur sa déclaration `terminee`. `cloture` n'est écrit que par un geste humain, par le verdict du persona validateur ou par la validation automatique d'un périmètre (INV-VALID-2).
- **INV-EXEC-6** — Aucune mort silencieuse : toute exception dans la boucle d'une tâche (attente d'un créneau, tour, conclusion) est journalisée (`log.exception`) et publiée en `tour_fin` avec `erreur` ; la file continue. Un mandat (INV-TRANSFO-1) dont aucun tour n'a reçu le message est signalé : événement `mandat_sans_tour` et `mandats_sans_tour` dans `GET /etat` (clé `tour` du mandat, posée au début du tour qui le reçoit).
- **INV-ECO-1** — Moteur du travail principal d'une tâche (`economie.py`, `[economie]`). Un `modele:` posé à la main l'emporte toujours ; tout choix fait à la main dans le sélecteur (harnais ou modèle) pose `moteur_impose: oui` et le harnais n'est plus jamais changé d'office (« défaut » lève l'imposition). Sinon le modèle vient d'une famille (rapide, sonnet, opus) : profil par règles déterministes (tri → rapide ; conception, refonte, débogage → opus ; dépôt → sonnet ; à défaut `famille_defaut`, `sonnet` par défaut ; corps long → un cran au-dessus ; contrôle requis comme oracle → opus descend à sonnet), un cran au-dessus après deux échecs consécutifs (tour en échec ou « terminée » refusée par le contrôle ; un succès remet à zéro, `<donnees>/etat/economie.json`), décalé par la position du curseur (tâche `economie:`, puis contexte le plus proche, puis `[economie] position`) ; le modèle est celui de `[harnais.<nom>.familles]`, jamais le défaut implicite du harnais quand la table existe. Avant toute conversation, dans les positions économie max, économie et intelligent, la tâche part sur le fournisseur de l'ordre des crédits le moins tendu si son rythme est inférieur de plus de `ecart_bascule` à celui du prévu. Une conversation commencée (ou dérivée) garde son harnais : la bascule est seulement proposée (`GET /taches/{id}/economie` → `bascule`) et s'accepte par `POST /taches/{id}/moteur`. Le motif est porté sur la tâche (`moteur_motif`) quand il change. La règle vaut pour toute conversation neuve : tâche enfant, dérivation sans fil, conversation de pilotage d'un conteneur (toutes passent par le tour de tâche) et rôle éphémère réglé par famille (`[moteurs_par_role]` : famille décalée par la position générale, fournisseur nettement moins tendu en tête de l'ordre des crédits) ; un harnais fixé (persona, réglage explicite) et une conversation déjà ouverte gardent le leur, ainsi qu'une dérivation avec fil — sauf quota épuisé d'un moteur non imposé (INV-QUOTA-1). Un compte épuisé (`<donnees>/etat/quotas.json`) est exclu de l'équilibrage jusqu'à sa reprise ; `GET /economie` → `epuises`. Un agent délègue par `orch deleguer "<titre>" "<brief>"` (tâche enfant qui alimente l'appelante, lancée avec un brief explicite ; son résultat revient par la propagation, INV-LIEN-1, plafonnée par INV-MSG-1) plutôt que par les sous-agents natifs de son harnais, invisibles de GoldenBrain (consigne commune).
- **INV-ECO-2** — Mesure (`conso.py`). Jetons et coût par tour lus de l'événement de fin du harnais quand son format est vérifié (Claude Code `result`, Codex `turn.completed`) ; Antigravity et OpenCode ne sont pas mesurés. Fenêtres de quota par registre de sources (`codex` : `rate_limits` des journaux de session ; `fichier` : JSON de la ligne d'état de Claude Code). Rythme P = part consommée / part du temps écoulé, absent pour une fenêtre illisible, renouvelée ou écoulée à moins de 5 % : sans rythme, aucune décision (mode intelligent neutre, pas d'équilibrage). Mode intelligent avec hystérésis : P > `seuil_haut` → un cran vers l'économie, maintenu tant que P > `seuil_haut − hysteresis` ; près du renouvellement de la plus longue fenêtre (moins de `proche_renouvellement` à courir, moins de 80 % consommés) et P < `seuil_bas` → un cran vers la performance, maintenu tant que P < `seuil_bas + hysteresis`.
- **INV-SIMULT-1** — Agents simultanés (`simultanes.py`, `[simultanes]`). Le sémaphore du moteur est un `Creneaux` à trois modes exclusifs : `fixe` (au plus `moteur.simultanes_max` tours), `optimiser` (un tour de plus tant que la RAM libre dépasse `marge_pct` % du total et le processeur `cpu_max_pct` %), `plafond` (tant que la RAM occupée reste sous `plafond`, en `pct` du total ou en `go`) ; ces deux derniers sont bornés par `garde_max` et ne démarrent qu'un tour par mesure. Une veille mesure le poste toutes les `intervalle_s` secondes (modes régulés seulement) ; au-dessus du seuil elle met en pause un tour par mesure, du moins prioritaire au plus prioritaire selon le classement d'INV-ORDO-2 (à rang égal, du plus récent au plus ancien) : suspension de tout l'arbre de processus (`NtSuspendProcess`) puis vidage de sa mémoire de travail, sans rien tuer ni perdre. Sous le seuil, elle reprend les pauses en ordre inverse, une par mesure, si la mémoire de travail d'avant la pause tient encore sous le seuil. Tant qu'une pause dure ou que le seuil est dépassé, aucun tour en file ne démarre. Suspension impossible : le tour est arrêté (`arrete`, INV-EXEC-1) puis remis en tête de sa file par la reprise (même session, message de reprise, non compté comme reprise automatique) ; un tour de persona n'est jamais remis en file : il est laissé courir. « Reprendre maintenant » (`POST /taches/{id}/reprendre-ram`) lève la pause et exempte le tour de toute nouvelle pause jusqu'à sa fin. Mesure indisponible (système sans `GlobalMemoryStatusEx` ni `/proc/meminfo`) : les modes régulés se comportent comme `fixe`. Un tour en pause continue de compter dans `duree_max_s`. Une reprise refusée par le système garde la pause (nouvel essai à la mesure suivante) ; une pause dont le tour a fini ou a été arrêté est oubliée dès que son créneau est rendu ; un processus sorti entre l'instantané et la suspension est ignoré, pas compté comme un échec. Régulation sans oscillation (audit L1) : le plafond effectif ne dépasse jamais 85 % du total (earlyoom tue à 10 % libres) ; un démarrage exige de la marge pour un tour (`COUT_TOUR`, 600 Mo) ; après un repli, la file attend que la RAM soit redescendue de 5 % du total sous le seuil (hystérésis) ; le repli remet le tour en file par `reprise_auto` (cause `ram`, au plus trois reprises d'office, INV-REPRISE-1 ; ensuite « Relancer » à la main) ; le titulaire de la réservation du poste (INV-POSTE-1) n'est jamais mis en pause ni replié. Limites connues : un arrêt brutal du serveur pendant une pause laisse l'arbre suspendu (un arrêt normal le tue) ; l'ordre d'attente des créneaux suit INV-ORDO-2.
- **INV-REPRISE-1** — Reprise automatique (`reprise_auto.py`). Un tour arrêté par la régulation mémoire (cause `ram`), par un redémarrage du serveur (`serveur`) ou par une erreur d'API passagère (`echecs.est_passagere` : « No response from API », 5xx, surcharge ; jamais un quota) repart seul dans sa conversation, par la consigne « reprends où tu en étais », sans changer le statut de la tâche ni écrire dans Décisions. Erreur d'API : reprise différée (30 s, 2 min, 5 min), persistée. Au plus `MAX_REPRISES` (3) reprises d'office par tour (compte `reprises`, persisté dans `tours.json` et `file.json`) ; au plafond : un incident, la tâche passe au statut de retour à l'humain (`vault.retour`), l'état reste `interrompu` et « Relancer » reste le geste humain. Un arrêt demandé par l'humain (`Moteur.arreter`, cause `humain`) ne reprend jamais seul et annule toute reprise différée. L'ordre de reprise est l'ordre d'arrêt ; l'hystérésis d'INV-SIMULT-1 interdit la boucle de relance. L'écran dit « interrompu (reprise automatique dans la file) » (`reprise_auto` dans l'arbre et le détail). Corrige aussi la remise en file d'une sous-tâche regroupée (INV-REGROUPE-2) : le message reprend directement (`soumettre(direct=True)`), sans être redirigé vers la mère.
- **INV-MAIN-1** — Quatre états lisibles, une seule pastille (`etat_main.py`, champ `main` des nœuds, du détail et d'Aujourd'hui) : « L'IA travaille », « En file » (motif dit : mémoire, agents simultanés, poste réservé, quota ou assistant indisponible, routine, dépendance nommée, pause ; reprise dite), « Action humaine nécessaire » (une phrase et le geste sur place : confier, renvoyer, répondre, valider, lever), « Terminé ». Calculé par-dessus les statuts du vault, sans migration ni écriture ; pilotage et permanente n'ont pas de pastille. Une livraison qui attend sa fusion se lit « intégration en cours », jamais une attente humaine.
- **INV-MAIN-2** — Une fin de tour réussi sans conclusion est renvoyée à l'IA (`attente_muette.py`, message « [GoldenBrain — conclus] … »), au plus `MAX_RENVOIS` (2) fois par tâche, compteur persisté dans `<donnees>/etat/attente.json`. Conclusion valable : terminé, demande humaine précise dans `prochain_pas`, ou attente nommée (file, sous-tâche, réveil, routine, report). Jamais pour un tour arrêté, en échec, sans fiche (INV-EXEC-12), de pilotage, permanent ou récurrent, ni pour une tâche tenue par l'humain.
- **INV-MAIN-3** — Renvois épuisés = demande humaine nommée : la tâche passe au statut de retour et se lit « Action humaine nécessaire : l'agent n'a pas conclu » ; jamais « en-cours » sans agent, file ni demande.
- **INV-MAIN-4** — « À moi » (compteur de la barre haute, trois pastilles) = les tâches en « Action humaine nécessaire » hors catégorie `confier` (`etat_main.humain_par_id`, `compteurs`) : `moi_valider` (à valider), `moi_questions` (à répondre ou à lever), `moi_faire` (à faire par vous). Les « jamais lancées » de l'IA (`confier`) ne comptent pas ; décisions reportées exclues. Détail par catégorie : `GET /api/main/a-moi` (triée par ancienneté).
- **INV-MAIN-6** — Une tâche permanente (nature permanente/recurrente/routine, ou cible d'un lien `alimente`) ou un groupe (tâche libre ayant des enfants) sans travail propre se lit « terminé pour l'instant » (motifs `veille` et `groupe`, clé `termine`), sans alerte et hors « À moi » ; un groupe dit la synthèse de ses enfants (« n à vous, n à l'IA »).
- **INV-MAIN-7** — Une tâche dont l'exécutant est l'utilisateur (`executant: humain`, ou démarche dans le titre : avocat, banque, appel, signature…) se lit « à faire par vous » ; « Confier à l'IA » reste disponible sur la fiche mais n'est jamais suggéré en liste (`suggere: false`).
- **INV-MAIN-5** — Gestes humains seuls : `POST /api/taches/{id}/ia` et `POST /api/lots/ia` (aperçu puis envoi, consigne facultative) envoient la tâche en file et remettent le compteur de renvois à zéro ; refusés (403) à un agent (en-tête `x-orch-tache`), comme `/confier`. Seules les tâches en action humaine ou en file, sans agent actif, sont envoyées.
- **INV-REPRISE-2** — Enregistrement d'étape (`etape.py`). La consigne de tout tour de développement (tâche d'un projet à dépôt) impose un commit d'étape sur la branche de travail à chaque palier et avant toute vérification longue. À l'arrêt d'un tour, GoldenBrain retrouve (git en lecture seule) l'arbre de travail et la branche actifs, les note dans la « Situation » de la fiche (préfixe `[étape]`, remplacée à chaque arrêt) et les rappelle dans le message de reprise.
- **INV-FROID-1** — Premier affichage à froid : `prechauffage.chauffer_tout` s'exécute dans le cycle de démarrage, avant que le serveur accepte une requête : index du vault, arbre, état global, PUIS les premières lectures lentes des routes du premier chargement (catalogue des moteurs : découverte des modèles ; contrôle de mise à jour : `git fetch` ; arbre tel que servi), en parallèle, chacune bornée à 8 s. Mesure du 26/11 sur le vrai vault : le préchauffage de l'index seul laissait ~3,9 s (moteurs 2,1 s, mise à jour 0,9 s, arbre 0,55 s) ; chaud : 0,58 s. Lecture seule, une erreur ou un délai est journalisé et n'empêche jamais le démarrage. Budget : premier chargement complet après démarrage, sur un vault de 260 tâches et 150 décisions et une découverte de modèles lente, ≤ 1,5 s (`tests/ui/scenario_reactivite.py`).
- **INV-VIGIE-1** — Signe de vie des tours (`vigie.py`, `diagnostic.py`, routes `api_vigie.py`, `[vigie]`). La vigie écoute les événements publiés par le moteur, comme un abonné SSE, sans rien changer au moteur. Par tour en cours elle tient : la phrase d'activité (première phrase du dernier message texte de l'agent, 160 caractères ; à défaut, l'outil traduit : « écrit build.py », « cherche dans Gmail »), l'heure du dernier événement et le nombre de lectures consécutives (`Read`, `Grep`, `Glob`, `LS`, lectures web ; une écriture ou un message remet à zéro, une commande est neutre). Un tour sans événement depuis `silence_s` secondes (défaut 300 ; décompté depuis le début du tour) est « silencieux », sauf s'il est en pause RAM (INV-SIMULT-1) ; une veille (`intervalle_s`, défaut 15) le diagnostique hors de la boucle asyncio : processeur de son arbre de processus sur 2 s (`poste_ram.temps_cpu`) et descendants lus par CIM `Win32_Process` (commande, date) ; la phrase nomme un hook (commande sous un dossier `hooks`), sinon la plus ancienne commande née plus de 20 s après l'agent (plus tôt : plomberie de session, serveurs MCP), sinon « l'agent calcule » (processeur ≥ 5 %) ou « en attente de la réponse du modèle ». Linux : même diagnostic par `/proc` (`stat`, `cmdline`, temps processeur `utime + stime`). Ailleurs : diagnostic neutre. Le diagnostic porte aussi `vivant` (processus du tour présent), `trace` (dernière ligne du journal du harnais lue pendant le tour, `derniere_trace()`) et `quota` (cette trace signale un quota). `lectures_max` (défaut 30) lectures d'affilée signalent une exploration prolongée. **Détection seule** : rien n'est arrêté sans geste humain. Gestes : « Arrêter <processus> » (`POST /taches/{id}/vigie/arreter-enfant {pid}`) n'atteint qu'un descendant de l'arbre du tour en cours — jamais sa racine (c'est « Arrêter le tour »), jamais un processus étranger (400) — et ses propres descendants ; « Attendre » tait l'alerte pour un nouveau délai de silence ; « Arrêter le tour » est l'arrêt ordinaire (INV-EXEC-1). SSE `vigie {tache}` à chaque entrée ou sortie de silence ou d'exploration et à chaque diagnostic ; `GET /etat` porte `tours[].signe` et `alertes_vigie` (bandeau) ; `GET /taches/{id}` porte `signe` (null hors tour).
- **INV-VIGIE-2** — Raison d'attente d'un tour en file (`vigie.raison_attente`), dans `raison_attente` de `GET /taches/{id}` et `file[].raison` de `GET /etat` : prérequis attendus (INV-ORDO-1), sinon poste réservé (INV-POSTE-1), sinon la conjonction de : rang (« en file derrière N tours »), limite des créneaux (« déplacement de dossiers en cours », « un agent est en pause faute de mémoire », « limité par la mémoire : X Go libres, plafond atteint », « processeur saturé », « agents simultanés au maximum (n/n) ») et quota épuisé au dernier tour (`echec_tour`, heure de reprise quand le harnais l'a donnée) ; « démarrage imminent » à défaut ; null hors file.
- **INV-TRAVAUX-1** — Écran « En cours » (`harnais/suivi.py`, `vigie.py`, `api_travaux.py`, `web/travaux.js`). Les sous-agents et l'avancement sont lus dans le flux que l'adaptateur lit déjà, jamais sondés : Claude Code (`tool_use` `Task`/`Agent` → début ; son `tool_result` → fin, `is_error` → échec ; `TodoWrite` hors `parent_tool_use_id` → avancement), OpenCode (outil `task` → début, `state.status` `completed|error` → fin ; `todowrite` → avancement), Codex (item `todo_list` → avancement). L'adaptateur rend un `Evenement("suivi")`, le moteur publie le SSE `suivi {tache, sous_agent|avancement}`, la vigie le tient dans le signe du tour (`sous_agents` bornés à 20, le plus ancien fini part d'abord ; `avancement {fait, total}` ; `fichiers` : nombre de chemins distincts écrits). Un `suivi` compte comme signe de vie. `GET /api/travaux` rend `{tours[] (tache, titre, projet, harnais, modele, depuis, signe), file[] (raison, INV-VIGIE-2), routines[] actives à venir (10), incidents[] ouverts (20)}`. L'écran ne se relit que sur événement serveur et seulement s'il est affiché : aucun minuteur.
- **INV-TRAVAUX-2** — Pause à la main (`simultanes.pauser_main|reprendre_main`, `POST /api/taches/{id}/suspendre|continuer`). Elle fige tout l'arbre de processus du tour (`poste_ram.figer` : `NtSuspendProcess` sous Windows, `SIGSTOP` au groupe de processus ailleurs, jamais le groupe du serveur) et se tient à part des pauses RAM : la veille ne la reprend ni ne la compte, ne la met pas en pause une seconde fois, et elle ne retient pas la file. Seul « Reprendre » la lève (`degeler`). Refus (409) : aucun tour, déjà en pause, processus introuvable, suspension impossible. Un tour arrêté ou fini pendant la pause l'oublie ; « Arrêter » fonctionne sur un tour figé. Le signe porte `pause_manuelle`.
- **INV-QUOTA-1** — Bascule unique sur quota épuisé (`quota.py`, `[economie] quota_bascule`, `quota_attente` ; demande du 18/11). Un tour de tâche (rôle `tache`/vide, non interrompu) en échec pour quota (`echecs.est_quota`) note le compte épuisé jusqu'à l'heure de reprise annoncée (sinon 30 min, `<donnees>/etat/quotas.json`) puis, si le moteur n'est pas imposé (ni `moteur_impose`, ni `modele:` posé, ni serveur en arrêt), relance **une fois** le même message sur le meilleur autre compte : ordre des crédits de la famille, puis harnais configurés, comptes épuisés, déjà essayés depuis le dernier succès ou indisponibles exclus, le moins tendu en tête. Conversation commencée : nouvelle conversation dans l'autre harnais avec le préambule de reprise (`sessions.changement`) ; `moteur_impose` reste levé, `moteur_motif` dit la bascule. Journal (INV-EXEC-8) et incident disent « GoldenBrain a relancé une fois sur X ». Jamais de boucle : un compte déjà essayé pour la tâche n'est plus proposé tant qu'un tour n'a pas abouti ; sans secours, ou moteur imposé, l'attente de la reprise prend le relais (INV-EXEC-10), sauf `quota_attente = false` (tâche bloquée, rien relancé). Tours de rôle (revue, persona, conseil, mandat) : quand le dernier candidat de la chaîne est en quota, un seul secours est ajouté (`roles.lancer`), jamais pour un moteur fixé (persona qui nomme son harnais, rôle réglé `repli = false` — INV-MOTEUR-1). Une seule reconnaissance du quota (`echecs.QUOTA`, « usage limit » compris). **Harnais non installé** (`echecs.INTROUVABLE` : « exécutable introuvable », `FileNotFoundError`) : même bascule unique, sans noter de quota ; un `modele:` posé à la création (assistant Telegram) ne retient pas, seul `moteur_impose` le fait ; la famille se lit alors du modèle posé dans `[harnais.X.familles]`, et le modèle de secours de cette famille est écrit. L'équilibrage n'inscrit jamais un harnais absent du poste : `roles.installe` filtre la chaîne d'une famille (`roles.choisir`) et les candidats de l'équilibrage (`economie._candidats`, hors moteur prévu).
- **INV-QUOTA-2** — Quota lu dans le journal du harnais (`harnais/opencode.py`, incident du 18/11 : `opencode run` reste vivant après « Free usage limit reached »). Pendant un tour, un guet lit toutes les `GUET_S` s les octets nouveaux du journal le plus récent (`[harnais.opencode] journal`, défaut `~/.local/share/opencode/log`) ; une ligne `level=ERROR` de la session du tour dont `error.error` est un quota arrête le processus et termine le tour en erreur avec ce motif. La dernière ligne lue alimente le diagnostic de la vigie (INV-VIGIE-1).
- **INV-INCIDENT-1** — Tout échec ou arrêt d'un tour laisse un incident lisible (`incidents.py`, `<donnees>/etat/incidents.json`, 200 derniers) : date, tâche, moteur (compte), rôle, cause classée (quota avec reprise annoncée, harnais non installé — geste « Installer X (Réglages → Installation) ou retirer X de [credits] », testée avant le réseau car « FileNotFoundError » contient « ENOTFOUND » —, réseau, harnais introuvable, non connecté, durée maximale, arrêt demandé, redémarrage du serveur, autre), motif brut, action de GoldenBrain (bascule, attente et heure de relance, gel réseau, abandon, rien) et geste proposé. Écrit par la fin de tour (`reveil`), la bascule (`quota`), le gel réseau (`reseau`) et les revues ; SSE `incident {tache}`. Un tour abouti clôt les incidents ouverts de la tâche (`clos`). Exposition : `GET /api/incidents` (liste, comptes épuisés) — panneau « Incidents » du bandeau avec jauge par compte (épuisé et reprise, sinon fenêtre la plus entamée) — et `GET /taches/{id}` / `…/vigie` → `incident` (dernier ouvert), bandeau de la conversation hors tour.
- **INV-RESEAU-1** — Coupures réseau (`reseau.py`, `[reseau]`). Une erreur de tour qui porte un motif de connexion (`echecs.RESEAU` : ENOTFOUND, ECONNREFUSED, « can't reach the API server », DNS…) et n'est pas un quota déclenche une sonde (DNS + connexion TCP vers les `hotes` du harnais, rien n'est envoyé ; sans erreur réseau préalable, jamais de sonde). Sonde qui dément la coupure : échec ordinaire (INV-EXEC-8). Sonde qui la confirme : le tour passe à l'état `attente_reseau` (message gardé dans `tours.json`, statut vault inchangé, message du système au journal), aucun nouveau tour ne démarre vers un fournisseur injoignable (`attendre_depart`, sans créneau), un tour encore vivant n'est jamais tué. Bandeau « Réseau perdu depuis HH:MM — N agents en attente » (`etat.reseau`, événement `reseau`). Arrêt humain d'une tâche gelée : plus de reprise. Limite : le fournisseur d'un départ retenu se lit sur l'envoi, la fiche ou le défaut (pas sur le choix automatique d'INV-ECO-1).
- **INV-RESEAU-2** — Reprise spontanée. Une veille sonde toutes les `intervalle_court_s` (2 min) pendant `duree_courte_s` (10 min) depuis le gel, puis toutes les `intervalle_long_s` (5 min) ; un réveil de veille de la machine la fait sonder aussitôt (`time.monotonic` ne compte pas la veille sous Linux : un guet par pas de 5 s compare horloge murale et monotone, écart > 30 s = veille) ; elle s'éteint quand tout répond. Au retour d'un fournisseur, chaque tour gelé de ce fournisseur est resoumis une seule fois (`reprise._resoumettre`, message signé GoldenBrain « coupure du réseau », même session, remis en tête de sa file), dans l'ordre du classement INV-ORDO-2 ; un nouvel échec réseau confirmé par la sonde regèle, sans boucle tant que la sonde répond. Gel persisté comme un tour actif : un redémarrage le reprend (INV-EXEC-1).
- **INV-RESEAU-3** — Trois pannes distinctes. Quota épuisé : jamais classé réseau (`est_reseau` l'exclut), jamais sondé. Réseau perdu : aucun fournisseur sondé ne répond (`perdu_depuis`). Panne d'un seul fournisseur : seul celui-là est dans `hors` ; ses tâches attendent, celles des autres fournisseurs continuent ; le bandeau dit « Fournisseur injoignable : … ».
- **INV-RESEAU-4** — Trace d'une coupure (`reseau.py`). Chaque sonde de chaque hôte laisse une ligne de journal (hôte, répond/muet, durée) ; la boucle de veille journalise son arrêt (raison, durée, tours encore gelés) ; la durée du gel est consignée à la levée dans `mesures.jsonl` (ligne `gel`, INV-COMPACT-1). Aucun changement de comportement.
- **INV-COMPACT-1** — Compactage automatique (`compactage.py`, routes `api_compactage.py`, `[compactage]`). Le seuil d'une tâche est le **premier atteint** de `pct` % de la fenêtre de son modèle (défaut **45 %**) et du `plafond` absolu en jetons (facultatif, 0 = désactivé) ; il s'hérite champ par champ **tâche → `contexte.md` du projet → réglage général** (clés `compactage_pct`, `compactage_plafond` du frontmatter, posées à la main ; valeur illisible ignorée). La fenêtre vient d'une table par motif de nom de modèle (défauts documentés dans le module, à vérifier ; `[compactage.fenetres]` prime ; `[1m]` = un million ; inconnu = 200 000). **Un seul chemin de traduction** : à chaque tour le moteur pose `harnais.compactage = (pct effectif, jetons)` sur l'adaptateur, qui l'applique à son mécanisme natif quand il existe — Claude Code : variable `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` ; Codex : `-c model_auto_compact_token_limit=<jetons>` — et l'ignore sinon (OpenCode, Antigravity : pas de seuil dans leur ligne de commande). **Repli commun** : pour un harnais sans mécanisme natif (`compactage_natif` faux) et muni d'un `ordre_compactage` (défaut ou `[compactage.ordres]`), si le contexte du dernier tour réussi a atteint le seuil, le moteur joue, avant le message suivant, un tour dont le texte est l'ordre (rôle `compactage` : ni statut ni fiche touchés, son échec se journalise et la file continue), puis préfixe le message d'un rappel de la fiche et du contexte du projet ; le contexte connu est alors oublié (jamais d'ordre en boucle) ; un arrêt humain pendant l'ordre abandonne le message. **Mesure** : chaque tour (réussi, en échec, interrompu, ordre de compactage compris) ajoute une ligne à `<donnees>/etat/mesures.jsonl` (hors vault) : `date, tache, harnais, modele, contexte` (jetons du dernier appel quand le harnais le dit, sinon null), `fenetre, seuil, cout, duree_s, signaux` (`tour_en_echec`, `relance`, `porte_rouge` et `terminee_refusee` quand le contrôle requis d'INV-CONTROLE-1 échoue, `interrompu`), `compactage` (le tour est un ordre), `apres_compactage` (ordre envoyé juste avant, ou contexte tombé sous 70 % du précédent : compactage natif présumé) ; la vue des Réglages groupe par harnais et tranche de contexte (tours, durée moyenne, taux d'échec = tours portant `tour_en_echec`, `relance`, `porte_rouge` ou `terminee_refusee` ; la ligne est écrite à la fin de la conclusion du tour, après le contrôle). **Instrumentation** (`instrumentation.py`) : le `contexte` d'une ligne est écarté (`null`) s'il dépasse la fenêtre (cumul des appels d'un tour chez certains harnais : valeur fausse, qui ne déclenche aucun compactage) ; la ligne de tour porte `rss_ko` et `petits_fils` (mémoire résidente du fils du harnais et nombre de ses descendants au-delà des enfants directs, lus dans `/proc` à l'événement `fin`, Linux seulement, absents ailleurs et pour un exécuteur distant) ; deux lignes à clé `type`, ignorées de la synthèse : `attente` (au lancement du tour : `file_s` depuis la mise en file du message, `prerequis_s`, `poste_s`, `reseau_s`, `creneau_s`, `role`) et `gel` (`portee` « reseau » à la levée d'une coupure, ou « tache » à la reprise d'un tour gelé : `gel_s`). Le journal de mesure ne porte aucun contenu de conversation.
- **INV-INTEG-1** — Pastille « intégration en retard » (`integration.py`, routes `api_integration.py`, `[integration]`). Une tâche `fait`/`cloture` dont les champs « fait » ou « résultat » de la fiche citent une branche `gb/*` (hors la branche d'intégration elle-même) porte `integration_retard: {branche, heures}` dans `/api/arbre` quand la pointe de cette branche n'est contenue dans aucune copie (distante ou locale) de la branche d'intégration (`branche`, défaut `gb/integration`) et que sa dernière validation date de plus de `retard_h` heures (défaut 2, réglable dans Réglages, relu à chaud). Lecture git **seule** (`rev-parse`, `log -1`, `merge-base --is-ancestor`, sans shell) dans le dépôt de GoldenBrain (ou `[integration] depot`) ; résultat **mis en cache** `cache_s` secondes (défaut 60), calculé par un fil d'arrière-plan : l'arbre ne lit que le cache et n'attend au plus que 0,5 s la toute première lecture. Branche, dépôt ou intégration introuvable = aucune pastille. L'interface recharge l'arbre toutes les 60 s : la pastille apparaît et disparaît (après fusion) sans geste.
- **INV-PROP-1** — Les propositions se règlent par famille de geste (`[interface] office`, Réglages → Propositions ; défaut `config.GESTES_OFFICE` : lier, rattacher, déplacer, renommer, échéance, ticket). Un geste de cette famille est appliqué d'office par `propositions.proposer` (même chemin que `/accepter`), marqué `auto`, son état antérieur gardé dans `avant`, consigné dans « Traces » de la tâche, listé sept jours sous « Appliqué d'office » de la page Décisions et annulable (`POST /propositions/{n}/annuler`, `annulation.py` : état `annulee` ; un ticket né est abandonné, jamais supprimé). Un échec d'application (conflit, invalide, introuvable) laisse la proposition en attente avec `echec`. Les autres gestes (fermer, projet, opération, périmètre, tâche hors de celle de l'agent) suivent la politique `propositions` (INV-INTERFACE-3). Les propositions du jardinier (INV-JARD-2) et du scan (INV-SCAN-1) restent toujours à trancher. Sur la page Décisions, les propositions en attente se regroupent par tâche émettrice en une entrée repliée (« Tout accepter » / « Tout refuser »), une ligne chacune, motif au survol ou au dépli.
- **INV-PROP-2** — Les propositions en attente s'affichent groupées par tâche émettrice (`web/propositions.js`, `groupePropositions`), dans le panneau déroulant « Propositions » (INV-DEROULANT-1 ; l'accueil n'a plus de zone permanente) et la page Décisions : un groupe replié tient en une ligne (« Propositions de <tâche> », nombre, « Tout accepter », « Tout refuser ») ; déplié, une ligne par proposition (verbe et objet tronqués, deux icônes accepter et refuser) ; motif et détail long au dépli ou au survol ; aucune carte multi-lignes (`tests/ui/scenario_propositions_compactes.py` : six propositions repliées ≤ 2 × 32 px, lignes ≤ 32 px).
- **INV-LIEN-2** — Un lien `alimente` proposé vers une tâche de nature `permanente` (l'intégration) est un geste de routine : `propositions.proposer` l'accepte d'office, quelle que soit la politique des propositions et le plafond du jardinier, le marque `auto` et le consigne dans « Traces » de la tâche (mention discrète, rien à trancher). Les autres liens suivent la politique.
- **INV-INTEG-2** — Lien d'office vers la tâche d'intégration (`depot.integration`, `liens.relier_integration`, appelé par `api_rapprochement.creer`). Un projet déclare sa tâche permanente d'intégration par la clé `integration: <identifiant>` de son `contexte.md` (le conteneur le plus proche l'emporte, comme `depot:`). Toute tâche créée par `POST /api/taches` (interface, `orch creer`, `orch deleguer`) dans ce projet reçoit aussitôt `alimente: [<intégration>]` : sa fin de tour prévient l'intégration (INV-LIEN-1), qui fusionne les branches citées. Exceptions : l'intégration elle-même, et l'enfant de l'intégration ou d'une tâche qui l'alimente déjà (la parente porte le lien). Un lien impossible (cible absente, cycle, déjà présent) est ignoré : la création n'échoue jamais pour lui. Les créations internes (routines, Telegram, jardinier) ne sont pas reliées.
- **INV-ORDO-1** — Prérequis (`ordonnancement.py`, `liens.py`). `B: prerequis: [A]` : aucun tour de B ne démarre tant que A a un statut ouvert (`vault.statuts_ouverts` ; `fait`, même à valider, compte comme terminée). Le tour retenu ne prend ni créneau ni poste ; la tâche reste `en_file` et affiche « En attente de : <titres> » (`attente_prerequis` de la tâche, `attend` dans `GET /etat` → `file`). Le moteur relit l'état des prérequis toutes les `INTERVALLE_PREREQUIS_S` secondes (une fiche fermée à la main compte aussi) : le tour part de lui-même dès que le dernier prérequis est terminé, sans message ni tour gaspillé. La règle vaut pour tout message, y compris d'un humain : pour lever l'attente, retirer le lien. Un lien `prerequis` qui fermerait un cycle (direct ou transitif) est refusé (409, motif lisible). `alimente` ne bloque jamais rien.
- **INV-ORDO-2** — Classement unique (`ordonnancement.classer`) des tours éligibles, déterministe : (a) message d'un humain (ni `de`, ni propagation, ni mandat, ni reprise) ; (b) `priorite` haute, moyenne, basse, puis sans priorité ; (c) chemin critique : nombre de tâches ouvertes qui attendent celle-ci, transitivement, par `prerequis` ; (d) échéance la plus proche ; (e) ordre d'arrivée. Un créneau libre (`Creneaux.acquire`) va au premier du classement ; chaque tâche en attente de créneau expose son rang et son motif (premier critère qui la distingue : « message d'un humain », « priorité haute », « débloque N tâches », « échéance AAAA-MM-JJ », « priorité moyenne|basse », « ordre d'arrivée ») dans `rang_file` de la tâche et `file` de `GET /etat`. Le même classement, lu à l'envers, désigne l'agent mis en pause quand la RAM manque (INV-SIMULT-1). Classement impossible (vault illisible) : ordre d'arrivée, journalisé.
- **INV-EXEC-8** — Un tour en échec (erreur du harnais, durée maximale, tour sans résultat ; pas un tour interrompu) est visible : le moteur écrit au journal une ligne `{"type": "orch_echec", "texte", "motif", "date"}`, que la conversation montre comme message de rôle `systeme` (signé GoldenBrain, distinct de l'agent) ; la fiche porte `echec_tour` (le message) et l'arbre `echec` jusqu'à la fin du prochain tour réussi, qui le retire. Quota épuisé (`echecs.QUOTA`) : le message dit « Quota épuisé » et l'heure de reprise quand le harnais la donne. Aucune relance automatique (INV-EXEC-1). Sans session (premier tour en échec), `/conversation` se relit dans les journaux.
- **INV-EXEC-9** — La file des messages survit à un redémarrage. `<donnees>/etat/file.json` garde, dans l'ordre de départ par tâche, chaque message pas encore démarré — y compris celui déjà sorti de la file mais retenu (verrou, prérequis INV-ORDO-1, poste, réseau) avant son tour (`moteur.attente`) : champs `tache`, `texte` (déjà signé `de`), `sauts`, `de`, `harnais`, `modele`, `source`, `mandat`, `role`, `reprise`, `pour`. Réécrit à chaque soumission, début de tour et arrêt (`Moteur._sauver_actifs`), sauf pendant l'arrêt du serveur. Au démarrage (`reprise.reprendre_au_demarrage`) les tours interrompus sont repris d'abord (INV-EXEC-1), puis la file est resoumise dans l'ordre ; une tâche fermée ou disparue est ignorée ; un message refusé (plafond de sauts…) n'empêche pas les suivants.
- **INV-EXEC-10** — Exception voulue à INV-EXEC-1 (demande de l'utilisateur, 15/11) : un tour en échec pour quota épuisé (`echecs.est_quota`, tâche et rôle `tache`/vide, pas un tour interrompu) programme la relance du MÊME message à l'heure de reprise annoncée par le harnais + 2 min (`echecs.heure_reprise` : « try again at 3:14 PM », « retry in 2 hours »), sinon toutes les 30 min ; au plus 8 relances, puis le journal le dit et le réveil s'éteint. État persisté dans `<donnees>/etat/reveils.json` (`tache → {a, essais, lance, harnais, texte, sauts, mandat, source}`), repris par `demarrer_reveils` au démarrage ; un réveil échu part aussitôt. La tâche est « en pause » (`etat_execution: en_pause`, `pause`: « En pause : quota <harnais>, reprise à HH:MM » ; `/etat` → `pauses`). Annulé par : l'arrêt (`POST /taches/{id}/arret`), tout tour qui se termine sans quota (réussi, autre erreur, interrompu), un échec effacé entre-temps (`echec_tour` vide au moment du réveil). `POST /taches/{id}/reprise` (« Reprendre maintenant ») relance aussitôt. SSE `pause` (`tache`) à chaque changement. Un autre échec (hors quota) ne se relance jamais seul. Articulation avec la reprise d'office (INV-EXEC-1) : un tour coupé par l'arrêt du serveur (`arrete`) ne programme jamais de réveil ; au démarrage la reprise d'office passe d'abord et annule le réveil des tâches qu'elle reprend, puis les réveils restants sont minutés ; un tour lancé par un réveil et coupé par un redémarrage est donc repris d'office une fois, jamais relancé deux fois.
- **INV-EXEC-11** — File d'une tâche bloquée retenue (demande du 18/11) : un tour de tâche (rôle `tache`/vide) en échec durable que rien ne relance (ni réseau gelé, ni bascule, ni réveil sur quota) remet son message en tête de file et retient la file (`retenus`, `reveil.retenir` ; jamais une routine, `nature: routine` : sa prochaine échéance est le nouvel essai) : les messages arrivés pendant le blocage (Telegram, agents) y attendent au lieu d'échouer un à un. Un geste humain la relâche dans l'ordre (`liberer`) : changement de moteur, changement de statut (`POST /statut` ; tâche close : la file tombe), message humain de l'interface (`POST /messages` sans `de`). La file retenue est persistée (INV-EXEC-9) ; après un redémarrage elle repart une fois et se retient de nouveau si l'échec persiste.
- **INV-EXEC-7** — Une tâche portant `nature: permanente`, `recurrente`, `pilotage` ou `routine` ne passe jamais à `fait` sur déclaration de l'agent : elle reste `en-cours` (aucune revue déclenchée). Le message du tour en cours est ajouté à `GET /taches/{id}/conversation` tant qu'il n'est pas dans le transcript.
- **INV-EXEC-12** — Fiche absente ≠ question (`relance_fiche.py`). Un tour réussi dont le dernier message ne porte aucun bloc `<fiche>` (texte libre ou résultat vide) ne passe plus la tâche à `retour-humain` : le moteur la laisse `en-cours` et resoumet UNE fois la demande de fiche (`[GoldenBrain — fiche manquante] …`) ; si la relance ne rend toujours pas de bloc, la tâche passe `bloque` avec le motif « fiche absente après relance » (`echec_tour`). Exception voulue à INV-EXEC-1, au plus une relance par tâche tant que la fiche manque (mémoire du processus : un redémarrage en accorde une de plus). Un tour arrêté à la main reste rendu à l'humain (`interrompu`), un tour en échec reste `bloque`. Compteur `absentes/relancees/bloquees` dans `GET /etat` (`fiches_absentes`). La consigne de tour (`[consigne] gabarit`) demande de trancher seul : `en_attente` est réservé à un envoi, une dépense, une décision de fond ou un secret.
- **INV-MOTEUR-1** — Un harnais indisponible ou inconnu fait échouer le tour avant tout lancement (`bloque`, erreur lisible) ; jamais de repli silencieux sur un autre harnais ou un autre modèle.
- **INV-DISTANT-1** — Exécuteurs distants : écoute et jetons (`executeurs.py`, `api_executeurs.py`, `__main__.py`, `[executeurs]`). Le chef écoute sur `127.0.0.1` ; `executeurs.ecoute` ajoute UNE adresse IPv4 littérale d'interface (ex. l'adresse Tailscale), normalisée, jamais toutes (`0.0.0.0` et ses formes abrégées, `::`, `*`, un nom d'hôte, une adresse de groupe : refusés au chargement). Garde à défaut fermé : quand une écoute est posée, toute requête reçue ailleurs que sur 127.0.0.1 est distante. Toute requête reçue sur cette interface exige `X-Orch-Jeton` valide (401 sinon), ne vise que `/api/` et jamais `/api/executeurs/jetons` — sauf une requête d'appareil appairé (INV-DISTANT-6), qui n'a pas d'en-tête de jeton. Un jeton par exécuteur, `secrets.token_urlsafe(32)`, montré une seule fois (`orch jeton-executeur <nom>` ou Réglages), seule son empreinte SHA-256 est gardée dans `<donnees>/etat/executeurs.json` (hors dépôt, hors vault), comparée à temps constant ; révocable. Les routes de l'exécuteur (`annonce`, `travail`, `evenements`) exigent le jeton même en local. Rien n'écoute sur l'exécuteur : il se connecte au chef.
- **INV-DISTANT-2** — Répartition (`Executeurs.placer`, appelé par `_tour_au_poste` avant tout créneau). Première règle qui s'applique : tour de rôle ou de sous-tâche regroupée → chef ; `ou: codespace` → chef ; conversation née sur un exécuteur (`nes`, persisté) → cet exécuteur, attendu s'il est absent ; conversation née au chef (session présente) ou dérivation → chef ; épinglage `executeur: <nom>` (`chef` = poste) ; `vault: intensif`, tâche sans dépôt ou dépôt sans `origin` git → chef ; créneau libre au chef et file vide → chef ; sinon l'exécuteur connecté qui a une place (`places`), le plus de mémoire libre ensuite ; aucun → chef. Un tour placé n'occupe pas de créneau du chef ; le journal, la session, la fiche et la conversation restent ceux du chef (adaptateur `HarnaisDistant`, transcript relu des journaux). Harnais absent de l'exécuteur : échec avant lancement (INV-MOTEUR-1). Session remise à zéro : la conversation renaîtra où il y a place.
- **INV-DISTANT-3** — Le vault ne quitte pas le chef. Un ordre ne porte que le message (précédé du préambule « le vault n'est pas ici, passe par orch »), la consigne, `ORCH_TACHE`, `ORCH_SAUTS`, le modèle et l'URL `origin` du dépôt ; l'exécuteur pose `ORCH_URL` (le chef) et `ORCH_JETON`, et l'agent lit ou écrit les tâches par `orch` (API du chef). Le code passe par GitHub : l'exécuteur clone ou met à jour le dépôt (`git` par liste d'arguments, URL et nom validés). `executeur.py` n'importe ni `vault`, ni `moteur`, ni `catalogue`.
- **INV-DISTANT-4** — Perte et retour. Signe de vie : annonce toutes les 10 s et relevé en cours (long-poll) ; au-delà de `executeurs.delai_perte_s` (45 s) sans signe, l'exécuteur est « perdu » : ses tours passent « en attente de l'exécuteur » (vue, événement `executeurs`), aucun n'est tué ni échoué. Événements numérotés, renvoyés par l'exécuteur jusqu'à accusé, jamais rejoués par le chef. Au retour, un ordre relevé qu'il ne tient plus (redémarrage, réponse perdue ; grâce de 60 s hors redémarrage) est renvoyé une fois — avec la session connue, sous `MESSAGE_REPRISE` (« redémarrage de l'exécuteur ») — puis échoue à la seconde perte. Tour inconnu du chef (chef redémarré) : 410 / `abandonner`, l'exécuteur l'arrête ; la reprise du chef (INV-EXEC-1) le relance sur le même exécuteur. Arrêt humain : ordre `arret` relayé.
- **INV-DISTANT-5** — Appairage d'un appareil par code QR (`appareils.py`, `api_appareils.py`, `qr.py`, `web/appairer.js`). Le code (`secrets.token_urlsafe(16)`) ne s'ouvre qu'au poste (Réglages → Appareils), vaut 120 s, sert une fois, 5 au plus ouverts ; seule son empreinte est gardée, en mémoire, comparée à temps constant. Il voyage dans le fragment de l'adresse (`/appairer.html#code`), donc dans aucune requête ni journal HTTP. Cinq échecs consécutifs verrouillent l'échange 60 s (429), même pour un bon code. Le code QR se calcule sur le poste (`qr.py`), jamais par un service tiers.
- **INV-DISTANT-6** — Jeton d'appareil (`appareils.py`, `api_appareils.py`, `api.py`). L'échange rend un jeton `secrets.token_urlsafe(32)` posé en cookie `gb_appareil` HttpOnly, SameSite=Strict, Secure en HTTPS ; seule son empreinte est persistée (`<donnees>/etat/appareils.json`, hors dépôt et hors vault). Toute requête reçue sur l'interface distante sans jeton d'appareil ni d'exécuteur valide est refusée (401), pages, API et flux SSE compris ; seules `appairer.html`, `appairer.js`, `favicon.svg`, `style.css`, `icone-192.png`, `icone-512.png` (le navigateur va chercher les icônes du manifeste sans cookie) et l'échange passent ; `manifest.json` et `sw.js` restent sous jeton. La révocation (au poste) est immédiate, y compris pour un flux SSE déjà ouvert, qui se ferme. La boucle locale n'est jamais concernée. L'accès des appareils est désactivé par défaut (`[distant] appareils = false`).
- **INV-DISTANT-7** — Protections de l'accès distant (`api_appareils.py`, `__main__.py`, `config_distant.py`, `web/api.js`). Hôte gardé par INV-API-1 (127.0.0.1, localhost, l'adresse d'écoute, `distant.nom_hote`) ; `Origin` présent et différent de l'origine servie → 403. Réservés au poste (403 à distance) : `/api/appareils`, `/api/installation`, jetons, appairage et réparations des exécuteurs, terminaux `natif`/`console`. Gestes à risque (tout `DELETE`, arrêt d'un tour ou d'un enfant, redémarrage, mise à jour) : interdits (403, défaut) ou soumis à confirmation (`gestes = "confirmer"` : 428 sans `X-Orch-Confirmation: 1`) — garde-fou d'usage, pas frontière. Avec `[distant] certificat` et `cle` (`tailscale cert`), l'adresse distante sert en HTTPS, la boucle locale reste en HTTP ; sans, l'écran avertit. Jamais `0.0.0.0` ; jamais de port ouvert sur la box ni de tunnel public (`tailscale serve`/`funnel` feraient passer le distant pour local).
- **INV-DISTANT-8** — Journal des connexions distantes (`appareils.py`, `web/appareils.js`). Appairage, appairage refusé, connexion (au plus une ligne par minute et par adresse), refus (cumulés par adresse dans la minute), révocation ; borné à 200 lignes, 50 montrées dans Réglages → Appareils.
- **INV-APPAIRAGE-1** — Appairage par code (`appairage.py`, `api_executeurs.py`, `executeur.py`). Le chef ouvre un code de 8 caractères (alphabet sans `0 O 1 I L`, `secrets.choice`), affiché `ABCD-EFGH`, valable 600 s, à usage unique, un par nom d'exécuteur (le nouveau remplace l'ancien), 10 au plus à la fois. Il ne s'ouvre que depuis le poste du chef (jamais par l'interface distante, même avec un jeton) ; seul `POST /api/executeurs/appairage/echange` s'admet sans jeton par l'interface distante, et rend `{nom, jeton}` en consommant le code. Seule l'empreinte SHA-256 du code est gardée, en mémoire (un redémarrage du chef annule les codes), comparée à temps constant ; jamais écrite sur disque ni journalisée, jamais rendue par `GET /api/executeurs` (qui ne donne que le nom et le temps restant). Cinq échecs consécutifs verrouillent l'échange 60 s (429), même pour un code valable. L'exécuteur n'affiche jamais le jeton reçu : il le range dans `~/.goldenbrain-executeur.json` avec l'adresse du chef (hors dépôt) et ne s'en sert que pour ce chef.
- **INV-ACCUEIL-1** — Lecture locale, par source consentie (`accueil_sources.py`, `api_accueil.py`). Chaque source (questions, dossier désigné, historiques d'agents, vault en place) est optionnelle et cochée par l'arrivant ; elle n'est lue qu'en lecture seule, bornée, sans suivre de lien symbolique, jamais en dehors de ce qu'elle désigne. Aucun modèle n'est appelé et rien ne quitte le poste (le plan le dit : `confidentialite`). Les routes `/api/accueil*` sont réservées au poste (INV-DISTANT-1). `ORCH_ACCUEIL_HOME` remplace le dossier personnel pour les essais.
- **INV-ACCUEIL-2** — Proposition sans écriture (`accueil.py`). `proposer` calcule un plan en mémoire, sans état serveur : corrections (renommer, décocher, glisser-déposer) et abandon ne laissent aucune trace ; seul `POST /api/accueil/valider` écrit, après revalidation complète du plan reçu (noms, références, harnais, sessions, bornes) et refus préalable si un projet tomberait hors des motifs `[vault] taches`.
- **INV-PREMIERS-PAS-1** — Diagnostic sans installation (`premiers_pas.py`). Les premiers pas lisent l'état des assistants IA du catalogue d'`installation.py` (présence, connexion par l'outil officiel sans saisie) et montrent commande et page officielle ; ils n'installent, ne connectent et ne téléchargent rien. Ils se proposent une seule fois, quand le vault ne porte aucune tâche et que `<donnees>/etat/premiers-pas.json` est absent ; « Revoir les premiers pas » (Réglages) les rouvre. Routes sous `/api/accueil` : poste seulement (INV-ACCUEIL-1).

- **INV-CERVEAU-1** — Le second cerveau se règle d'abord, par poste, jamais d'après le contenu du vault (`cerveau.py`, `api_cerveau.py`, `web/cerveau.js`). Tant que `<donnees>/etat/cerveau.json` n'existe pas (et qu'aucun état d'accueil ou de premiers pas n'a vécu : une mise à jour n'impose rien à qui est installé), l'interface s'ouvre sur « Configurer votre second cerveau », plein écran, avant accueil et premiers pas, que le vault soit absent, vide ou garni ; ces deux parcours ne se proposent qu'une fois l'état `fait`, et pas pendant `differe` (« Plus tard » laisse un rappel visible). Rien n'est écrit ni créé avant la validation. Routes `/api/accueil/cerveau*` : poste seulement (INV-ACCUEIL-1).

- **INV-CERVEAU-2** — Changer de dossier : examiner, puis écrire une seule clé, puis redémarrer (`cerveau.examiner`, `poser_racine`, `appliquer`). Le dossier candidat est refusé s'il est un fichier, relatif, non inscriptible, ou déjà servi par une autre instance (même verrou que INV-INSTANCE-1, pris puis rendu aussitôt). Seule la clé `[vault] racine` de `config.toml` est remplacée (le reste du fichier, fins de ligne comprises, est restitué tel quel, sous le verrou de configuration) ; un vault existant est repris en place, sans copie ; un dossier absent n'est créé qu'à la validation. Le serveur redémarre alors (code 3, boucle de `lancer.sh`) : verrou d'instance et index se règlent au démarrage ; garder le dossier actuel ne redémarre rien.
- **INV-PREMIERS-PAS-2** — Assistant absent, dit et non subi (`assistant_absent.py`). Une tâche créée et lancée dont l'assistant (choisi, propre à la tâche ou par défaut) n'est pas installé ne part pas pour échouer : si une bascule de quota (INV-QUOTA-1) peut le remplacer, rien n'est refusé ; sinon `Conflit` nommant l'assistant manquant et ceux qui sont prêts, avant toute création de tâche. En mode simple, l'assistant choisi aux premiers pas à la création d'une tâche est respecté (exception à INV-INTERFACE-1, qui continue d'ignorer un harnais demandé à un message ou inconnu). Tests : `tests/test_premier_lancement.py`.
- **INV-REFLEXES-1** — Réflexes de l'agent, par consentement explicite (`reflexes.py`, `api_reflexes.py`, `cli_reflexes.py`, `web/reflexes.js`). GoldenBrain propose d'ajouter aux consignes d'un assistant IA (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `copilot-instructions.md`, globales ou d'un projet) un bloc versionné de réflexes (tâche, traçage, liens, résultat), dans la langue de l'utilisateur. Le bloc est délimité par `<!-- goldenbrain:reflexes debut vN -->` et `<!-- goldenbrain:reflexes fin -->`, chacun seul sur sa ligne (le dernier couple complet fait foi ; un marqueur cité dans la prose n'est pas une borne) ; poser, mettre à jour ou retirer ne touche que ce bloc : le reste du fichier est restitué octet pour octet (fins de ligne comprises), un lien symbolique reste un lien, l'écriture est atomique. Rien n'est écrit sans le geste de l'utilisateur après aperçu (diff) : bouton « Accepter » / « Retirer » de l'interface (routes `/api/accueil/reflexes*`, poste seulement, INV-ACCUEIL-1), ou `orch reflexes … --accord` après l'avoir montré. État : absent, à jour, ancienne version (`vN` < `VERSION`), retouché (même version, texte modifié). « Plus tard » est mémorisé par version dans `<donnees>/etat/reflexes.json` : une nouvelle version se repropose.
- **INV-TRACE-1** — Traçage d'un travail (`api_reflexes.py`, `cli_reflexes.py`). `POST /api/taches/{id}/traces` (`orch tracer`) ajoute à la section `## Traces` de la fiche une ligne datée : ce qui a été fait et les documents créés ou modifiés ; un document du vault devient un lien `[[…]]` (graphe, notes liées), un document extérieur reste un chemin. Ajout seul, par `consigner` (INV-VAULT-1) ; mêmes gardes d'écriture que les autres routes (INV-API-1, INV-EXECUTANT-1).
- **INV-MODELES-1** — Modèles en fichiers, lecture seule (`modeles.py`). Un modèle est un fichier `modeles/<id>.md` (en-tête `titre` obligatoire, `resume`, `ordre` ; corps non vide = mission) ; un fichier illisible, trop gros, lien symbolique ou sans titre est écarté sans erreur. Sa traduction est `modeles/<code>/<id>.md` (en, de, es), lue dans la langue réglée (INV-LANGUE-1) ; absente ou invalide, le français sert. Choisir un modèle ne fait que pré-remplir le formulaire : rien n'est créé avant « Créer ». Le modèle `premiere-tache` sert la démonstration des premiers pas.
- **INV-ACCUEIL-3** — Ajout sans écrasement (`accueil_ecriture.py`). Un fichier déjà là n'est jamais modifié (compté « déjà là ») ; les tâches reprennent `harnais` et `session` (« Reprendre » continue la conversation d'origine) et sont sautées si la session ou le titre existe déjà dans le projet ; les noms de notes sont uniques, les liens `[[nom]]` relient profil et projets.
- **INV-ACCUEIL-4** — Rejouable (`accueil.py`, `web/reglages.js`). « Relancer l'accueil » reconnaît ce qui existe (projets, sessions déjà reprises, titres) et ne propose que ce qui manque ; rejouer un même plan ne crée rien de plus.
- **INV-ACCUEIL-5** — Vault de départ au seul vault vide (`squelette.py`, `accueil.py`, `accueil_ecriture.py`). Il n'est proposé (`squelette` du plan) que si le vault ne porte aucune note `.md` hors dossiers cachés et hors dossier d'arrivée `[vault] arrivee` (où GoldenBrain range ses propres tâches, dont la démonstration des premiers pas) ; il comprend les dossiers `[vault] casquettes`, `[vault] projets`, `Inbox`, `Ressources`, `Archives` et la note `Lisez-moi.md`. Il ne s'écrit qu'à la validation, si l'arrivant l'a gardé, recalculé côté serveur (le contenu reçu du client est ignoré), en ajout : rien n'est créé dans un vault déjà garni (vault Obsidian repris tel quel, `.obsidian` ignoré). `GET /api/accueil` rend aussi `vide` et `obsidian`.
- **INV-INSTALL-1** — Accord par commande exacte (`installation.py`, `api_installation.py`, `cli.py`, `web/installation.js`). Toute commande lancée par l'assistant vient du seul catalogue `OUTILS` (aucune donnée du client, d'un mail ou d'une page n'y entre). L'étape montre « Ce qui va être fait : <commande> » ; elle ne se lance que si l'accord rendu est cette commande, caractère pour caractère (CLI : réponse `o`, défaut non, fin de saisie = arrêt ; interface : confirmation puis `{accord}` ; sinon `AccordRefuse` / 400). Une étape à la fois (409 si une autre court), jamais d'option « tout accepter ». Les routes `/api/installation*` sont réservées au poste (INV-DISTANT-1).
- **INV-INSTALL-2** — Connexion des harnais sans identifiant (`installation.py`, `api_installation.py`). Une connexion se lance telle quelle dans l'outil officiel (navigateur, code d'appareil) : GoldenBrain n'en lit, n'en garde et n'en transmet ni identifiant, ni mot de passe, ni jeton. En terminal le processus hérite du terminal ; en interface le clavier est fermé (`stdin=DEVNULL`) et une commande qui dialogue (`sans_saisie=False`) est donnée en instructions à lancer dans un terminal (`au_terminal` vrai : phrase complète, affichée telle quelle). Le jeton d'appairage reçu n'est jamais affiché (INV-APPAIRAGE-1).
- **INV-INSTALL-3** — Repli sans droits administrateur (`installation.py`). Une étape élevée (`uac` Windows, `sudo`) est tentée ; sans terminal ni droits (`sudo`), ou si elle échoue pour droits insuffisants, l'assistant rend les instructions à copier dans un terminal administrateur, puis « relance `python orch.py executeur installer` ». Il ne contourne jamais l'élévation.
- **INV-INSTALL-4** — État par PC et réparation (`executeur.py`, `executeurs.py`, `api_executeurs.py`, `web/executeurs.js`). L'exécuteur annonce le relevé de ses étapes d'installation (`id, libelle, etat, genre, optionnel, commande, instructions, attend` ; au plus une fois par minute) ; le chef n'en garde que ces champs, bornés. « Réparer » relance UNE étape `manquant` ou `a_connecter` : le chef (poste seulement, `POST /api/executeurs/reparations`, jamais par l'interface distante) montre « Sur <PC>, lancer : <commande> », et relaie `{etape, accord}` seulement si l'accord est la commande exacte annoncée, l'exécuteur connecté. L'exécuteur refait l'épreuve de INV-INSTALL-1 contre son propre catalogue (`Assistant.executer`, non interactif : une étape qui dialogue ou demande `sudo` rend ses instructions, INV-INSTALL-2 et 3) : aucune commande n'a jamais une autre source que `OUTILS`. Le résultat revient une fois dans l'annonce suivante.
- **INV-CODESPACE-1** — `gh` est toujours lancé par liste d'arguments, jamais par un shell du poste ; la déclaration `codespace:` est validée (nom de codespace ou dépôt `propriétaire/nom`) avant tout appel ; la commande d'un harnais distant est citée argument par argument (`shlex.quote`) avant d'être confiée au shell du codespace. GoldenBrain ne lit ni ne stocke aucun jeton (l'authentification est celle de `gh`) et ne crée ni ne supprime de codespace.
- **INV-MCP-1** — Un tour Claude Code ne charge aucun serveur MCP de l'utilisateur par défaut : `[harnais.claude] mcp = "aucun"` (défaut) ajoute `--strict-mcp-config` sans `--mcp-config` à l'argv de `claude -p` (une chaîne navigateur coûte ≈ 200 Mo par tour simultané). Dérogation générale : `mcp = "heritage"` ; dérogation par tâche : clé de frontmatter `mcp: heritage` (posée à la main, lue par `compactage.instancier`, qui la transmet à la conf de l'adaptateur). Toute autre valeur vaut « aucun ». Ne vaut que pour les tours d'agent : le terminal natif (`argv_natif`) reste celui de l'utilisateur.
- **INV-CODESPACE-2** — Une tâche `ou: codespace` s'exécute dans le codespace ou échoue (projet sans `codespace:`, harnais non pris en charge, codespace introuvable, harnais absent du codespace) : jamais de repli silencieux sur le poste. Le lieu ne change pas pendant un tour (409) ; l'interface native ne s'ouvre pas sur le poste pour une telle tâche (409).
- **INV-MOTEUR-2** — Seule exception à INV-MOTEUR-1 : un rôle assistant (voir Moteurs par rôle) dont le harnais est inconnu, introuvable, en erreur de quota ou en erreur avant tout résultat passe au moteur suivant de sa chaîne ; le repli est JOURNALISÉ (log, `roles.replis` dans `GET /etat`, et pour conseil et persona un événement `repli` au journal du tour) et un harnais en erreur de quota est évité 10 minutes. Jamais de repli : persona qui fixe son moteur, tâche, `repli = false`, ni après un outil lancé (effet de bord possible), ni sur délai dépassé. Le dernier moteur de la chaîne en échec fait échouer le tour (INV-MOTEUR-1).

### Chat de projet
- **INV-PILOTAGE-1** — La conversation d'un nœud de l'arbre (casquette, opération, projet) est une tâche ordinaire du moteur portant `nature: pilotage` et `pilote: <id du nœud>` : aucun second chemin d'exécution (session, fiche, propagation, demi-verrou, reprise, échec visible hérités). Une seule par nœud ; elle n'existe qu'au premier message (`POST /api/pilotage {noeud, texte, harnais?, modele?}`, 202 `{tache, etat_execution}`), jamais à la lecture (`GET /api/pilotage?noeud=` rend `{noeud, tache|null}`) ; nœud inconnu de l'arbre : 400. Rangement : un projet la porte dans son `taches/` (retrouvée par son dossier, elle le suit s'il est déplacé) ; une casquette ou une opération, sans dossier propre, dans `vault.arrivee`, retrouvée par `pilote:`. Elle est absente de l'arbre (même « Toutes »), de la recherche, de la vue « Aujourd'hui » et des compteurs de `/api/etat` ; `GET /api/taches/{id}` l'ouvre dans le panneau d'une tâche. Une tâche mère n'a pas de tâche de pilotage : sa propre conversation est amorcée (INV-PILOTAGE-2).
- **INV-RAPPROCHEMENT-1** — Toute création de tâche par une entrée (`POST /api/taches`, donc formulaire « Nouvelle tâche », `orch creer`, `orch deleguer`, assistant Telegram) passe par `rapprochement.proches`, SEUL moteur de ressemblance (recherche lexicale locale : mots normalisés sans accents ni mots vides ; score 0,6·dice des titres + 0,25·couverture + 0,15·description, +0,10 même conteneur). Une candidate OUVERTE de score ≥ 0,72 avec au moins deux mots de titre partagés est « forte » : la création est refusée doucement, 409 `{detail, candidates}`, sauf `forcer: true` (`--nouvelle` dans `orch creer` et `orch deleguer`). Les candidates de 0,35 à 0,72 et les closes de moins de 30 jours sont proposées, jamais bloquantes. La tâche appelante (`X-Orch-Tache`, `de`) et le parent ne sont jamais candidats. Un titre sans parenté ne rencontre aucune friction. Le départage IA est un point d'extension (`departager(arbitre)`), absent par défaut.
- **INV-RAPPROCHEMENT-2** — La mesure (`<donnees>/etat/rapprochement.json`, `GET /api/rapprochement/mesure`, `orch rapprochement`) compte les créations évitées : un refus 409 non suivi d'une création de la même demande, et chaque complément (`POST /api/rapprochement/taches/{id}/completer`, qui réutilise `Moteur.soumettre` : le message relance l'agent de la tâche). Un refus suivi d'un forçage ne compte plus ; un refus suivi d'un complément ne compte qu'une fois.
- **INV-PILOTAGE-2** — Chaque tour d'une tâche de pilotage, ou d'une tâche qui a des enfants, reçoit en tête de son message (le message journalisé et affiché reste celui de l'humain) : la fiche de contexte du nœud (contenu borné au premier tour, chemin ensuite), sa descendance dans l'ordre de l'arbre avec, par tâche, identifiant, statut, état d'exécution et fiche (fait, situation, reste), les remontées reçues depuis le tour précédent et, pour un nœud, les gestes `orch` permis. Au-delà de `pilotage.SEUIL` tâches, les closes ne sont que comptées, les ouvertes bornées et leurs champs tronqués. Valider, fermer et déplacer un dossier restent des propositions.
- **INV-PILOTAGE-3** — Quand une tâche finit un tour réussi, chaque conversation existante au-dessus d'elle (tâche de pilotage d'un nœud ancêtre, tâche mère ayant une session ; jamais elle-même) reçoit une ligne de synthèse (titre, statut, fait, situation) : écrite au journal (`{"type": "orch_remontee", "texte", "date"}`, montrée comme message `systeme`), gardée dans `<donnees>/etat/remontees/<id>.jsonl` et consommée par le tour suivant ; événement `remontee {tache}`. Aucun tour n'est déclenché ; un échec de remontée ne fait jamais échouer la fin du tour.

### Retour arrière
- **INV-RETOUR-1** — « Modifier » un message envoyé (`retour.py`, routes `api_retour.py`) retire de la conversation son tour et tous les suivants, puis soumet aussitôt le nouveau texte. Un tour = une ligne `orch_message` des journaux de la tâche (identifiant `<AAAA-MM-JJ>/<fichier>#<k>`, deux tours d'une même seconde partagent un fichier) ; `/conversation` relie chaque message de l'utilisateur à son tour (clé `tour`, du plus récent au plus ancien) ; un message sans tour (écrit au terminal) n'est pas modifiable ; un tour inconnu est refusé (400). « Répondre à partir d'ici » sur une réponse de l'IA est le même geste appliqué au message qui la suit (clé `suite` de la réponse : même plan, même avertissement, même case code, même mécanisme ; saisie vide) ; la dernière réponse (clé `dernier`) renvoie simplement à la saisie ; une réponse suivie d'un message sans tour n'a pas le geste. La conversation est coupée après le tour entier de la réponse. Refus (409) si un tour est en cours ou en file sur la tâche, ou si son interface native est ouverte. **Retour natif** quand le harnais sait reprendre à un point (`point_de_reprise(session, texte, date)` rend l'entrée qui précède le message) : Claude Code `--resume <session> --resume-session-at <uuid> --fork-session` (option cachée de la version 2.1.325, vérifiée par essai réel le 16/11 : la conversation dérivée ignore la fin, l'ancienne session reste intacte) ; le point est posé sur l'adaptateur du tour suivant de la tâche seulement (`Moteur.rembobinages`, consommé une fois) et la nouvelle session s'écrit par INV-EXEC-3. **Repli commun** (Codex, OpenCode, Antigravity : aucune reprise à un message — `codex exec resume|fork`, `opencode run --fork`, `agy --conversation` reprennent ou dérivent la conversation entière, vérifié le 16/11 sur codex-cli 0.167.0 et l'aide d'`opencode`/`agy` ; Claude quand le message est introuvable dans la session courante) : `session` retirée de la fiche, nouvelle conversation dont le premier message porte la transcription (bornée à 40 000 caractères) jusqu'au message modifié exclu, sous un en-tête `[GoldenBrain — conversation reprise après modification d'un message. …]` que la conversation réduit à une ligne signalée. Premier message modifié : conversation neuve, sans transcription.
- **INV-RETOUR-2** — Rien n'est détruit : la fin retirée (portion du journal du tour modifié depuis sa ligne `orch_message`, puis tous les journaux suivants, échecs et remontées compris) est DÉPLACÉE sous `<donnees>/archives/retours/<id>/<n>/journal/` (copie écrite d'abord, original tronqué atomiquement ensuite) avec `retour.json` (date, tour, ancien et nouveau texte, harnais, ancienne session, mécanisme, nombre d'échanges, point de code, restauration). L'ancienne session du harnais reste sur disque. `GET /taches/{id}/versions` les liste ; `GET /taches/{id}/versions/{n}` relit la fin retirée dans l'ancienne session quand le harnais a un transcript lisible, sinon dans les journaux archivés. Les effets dans le vault ne sont jamais annulés (INV-VAULT-1) : le plan liste la fiche et les fichiers du vault écrits par les tours retirés (relevé indicatif dans les journaux : outils d'écriture de Claude, `file_change` de Codex ; une écriture par commande shell échappe).
- **INV-RETOUR-3** — Point de restauration du code (`points.py`) : avant chaque tour d'une tâche dont le dossier de travail (INV-DEPOT-1) est dans un dépôt git du poste (jamais au codespace), un commit hors branche capture l'arbre de travail (fichiers suivis et non suivis non ignorés, par un index temporaire : l'index réel, HEAD et les branches ne bougent pas), référencé `refs/goldenbrain/points/<tâche>/<horodatage>` et noté au journal du tour (`{"type": "orch_point", "depot", "ref", "commit"}`) ; un échec se journalise et n'empêche jamais le tour. Au « Modifier », la case « Restaurer aussi le code à cet instant » (décochée par défaut, grisée sans point ou sans changement) suit un plan à blanc (fichiers modifiés, recréés, retirés) ; la restauration précède toute modification de la conversation, capture d'abord l'état courant (point `avant-retour-…`, donc réversible), ne touche que les fichiers (les commits faits depuis restent dans l'historique), et se fait tout ou rien (échec : état d'avant réappliqué, 409, conversation intacte). Fichiers ignorés par git : non concernés ; fichiers hors dépôt : listés, non restaurables. Seul le dossier de travail est couvert : un arbre de travail que l'agent crée lui-même ailleurs (ex. `.claude/worktrees/…`) ne l'est pas.

### Exécution regroupée
- **INV-REGROUPE-1** — Les sous-tâches ouvertes d'une tâche mère s'exécutent soit chacune dans sa conversation (`par_tache`), soit dans la conversation de la mère (`regroupee`). Le réglage `execution: automatique|par_tache|regroupee` se pose sur une tâche (clé gérée) ou sur le `contexte.md` d'un conteneur, et s'hérite vers le bas (le plus proche ancêtre l'emporte ; défaut `automatique` ; une valeur vide rend l'héritage). Mère close ou tenue par Paperclip : par tâche. La règle automatique est déterministe, la première condition donne le motif : moins de deux sous-tâches → par tâche ; une sous-tâche qui exige un autre harnais ou modèle, sa propre `branche:` ou un autre `ou:` → par tâche (l'isolation prime même sur la RAM) ; RAM du poste insuffisante (réglage « Agents simultanés » régulé, seuil dépassé ou pause en cours, INV-SIMULT-1) → regroupée ; une sous-tâche lourde (`epreuves: lourdes` ou `taille: M|L|XL`) → par tâche ; conteneurs différents → par tâche ; sous-tâches non enchaînées par des prérequis (au moins n−1 en attendent une sœur) → par tâche ; sinon regroupée. Le motif s'affiche sur la sous-tâche (« Regroupée sous « M » : 3 sous-tâches petites et enchaînées »). Routes : `GET /api/execution?noeud=` et `PUT /api/execution {noeud, reglage}` rendent `{noeud, reglage, herite, herite_de, decision}` (réglage inconnu : 400 ; conteneur sans `contexte.md` : 409) ; `GET /api/taches/{id}` porte `execution`.
- **INV-REGROUPE-2** — En exécution regroupée, un message adressé à une sous-tâche (humain, autre tâche, propagation ; pas un mandat ni un rôle, ni un message venu de la mère elle-même) est soumis à la mère, préfixé de l'identité de la sous-tâche, de l'ordre de traitement (prérequis d'abord, puis classement INV-ORDO-2) et du geste `orch fiche` ; la sous-tâche en garde la trace (`{"type": "orch_regroupe"}` dans son journal, message `systeme` de sa conversation). Seule la conversation de la mère, en exécution regroupée, écrit la fiche et le statut proposé d'une sous-tâche (`POST /api/taches/{id}/fiche-regroupee {de, statut, fait…}`, sinon 409) ; « terminée » devient « retour-humain » si un contrôle est requis (INV-CONTROLE-1) et « en cours » pour une nature sans fin (INV-EXEC-7). Aucune session n'est créée ni effacée : passer d'un mode à l'autre ne perd rien, la conversation propre d'une sous-tâche est reprise dès qu'elle repasse par tâche ; les messages déjà en file restent où ils sont.
- **INV-REGROUPE-3** — Une sous-tâche portée par sa mère (message en file ou en cours pour elle, fiche écrite pendant le tour en cours de la mère) a l'état d'exécution `en_file` ou `en_cours` et le repère « IA au travail » (`occupees`, demi-verrou INV-VERROU-1), jusqu'à la fin de ce tour.

### Routines programmées
- **INV-ROUTINE-1** — Jamais deux exécutions simultanées d'une routine : une échéance qui tombe pendant qu'un tour tourne, attend en file ou en pause (quota, réseau) est notée `sautee` (« exécution précédente non terminée ») ; « Exécuter maintenant » répond 409. Toute exécution passe par `moteur.soumettre` (file, ordonnancement, mémoire, poste, réseau) : le planificateur ne lance rien lui-même.
- **INV-ROUTINE-2** — Le programme (`programme:`) est analysé avant toute écriture : écriture lisible (« chaque jour 08:00 », « en semaine 18:00 », « lundi,jeudi 09:30 », « toutes les 2 h de 8 h à 20 h », « toutes les 15 min ») ou cron à cinq champs ; illisible → 400, jamais deviné. Heure locale du poste. Un programme rendu illisible à la main dans la note n'exécute rien et s'affiche en erreur. Les clés `nature`, `programme`, `routine`, `contexte`, `rattrapage` sont des clés gérées (INV-VAULT-1).
- **INV-ROUTINE-3** — Échéance manquée (plus de 5 min de retard : poste éteint, serveur arrêté) : avec `rattrapage: une` (défaut), une seule exécution « rattrapée » quel que soit le nombre d'échéances manquées ; avec `aucune`, l'échéance est notée `sautee`. La prochaine échéance repart toujours de l'instant présent. Une routine `routine: en-pause` n'a pas d'échéance ; à la reprise (ou au changement de programme) l'échéance repart de maintenant, sans rattraper la pause.
- **INV-ROUTINE-4** — Chaque exécution laisse une entrée d'historique (`<donnees>/etat/routines.json`, 30 dernières) : `en_cours` puis `reussie` ou `echouee` (lu de `echec_tour` à la fin du tour), avec la session. La consigne de chaque exécution demande à l'agent de signaler livrable ou action dans sa fiche et, au besoin, de créer une tâche (`orch creer`). Une routine active dont la dernière exécution a échoué fait une ligne « Routine en échec » dans « Décisions » (gestes : relancer, mettre en pause) jusqu'à une exécution réussie ou sa mise en pause.
- **INV-ROUTINE-5** — Une routine est une note `nature: routine` dans le `taches/` de son conteneur, à sa place dans l'arbre parmi les tâches : `GET /arbre` annote son nœud de `routine: {programme, etat, prochaine, derniere, erreur}` ; l'interface montre l'horloge et la prochaine exécution à la place du statut, le point de la dernière issue (vert, rouge, en cours), et le filtre « Routines ». `contexte: neuf` vide la session avant chaque exécution (conversation neuve) ; `suite` (défaut) reprend la même.

### Chaînes de phases
- **INV-CHAINE-1** — Une chaîne avance une phase à la fois : la phase suivante n'est soumise (par `moteur.soumettre`, jamais par un second chemin) qu'après la conclusion « terminée » (`fait`) du tour de la phase courante, lue sur le flux d'événements du moteur (`tour_fin`), et rattrapée chaque minute sur le statut du vault quand cette fin n'a pas été vue (`reconcilier` : serveur arrêté, statut posé à la main) ; le tour d'une autre tâche ne fait rien avancer. Une phase `validation: true` arrête la chaîne (`attente_validation`, tâche parente au statut de retour humain) jusqu'au geste « Valider et poursuivre ». Un tour `bloque` met la chaîne en `echec` ; « Reprendre » resoumet la même phase (409 si elle tourne encore). Chaque exécution = une tâche parente (`chaine: <modèle>`, `execution: par_tache` : jamais regroupée, INV-REGROUPE-2, sans quoi la fin des phases ne se verrait pas) et une tâche enfant par phase (`chaine_phase: <n>`), clés gérées (INV-VAULT-1) ; état dans `<donnees>/etat/chaines.json`. La consigne d'une phase porte le dossier traité, le contexte commun, sa consigne, ses documents d'entrée, son livrable et les fiches des phases faites.
- **INV-CHAINE-2** — Un modèle de chaîne est un fichier Markdown (en-tête YAML : `titre`, `resume`, `phases` [titre, consigne, entrees, livrable, harnais, modele, validation], `surveiller`, `conteneur` ; corps = contexte commun). Modèles intégrés : `chaines/` du dépôt, traduits sous `chaines/<langue>/` ; modèles de l'utilisateur : `<vault>/_meta/chaines/`, qui l'emportent à identifiant égal. Lecture bornée (taille, nombre, 20 phases) ; un fichier illisible est écarté, jamais fatal ; titre et consigne de chaque phase obligatoires. L'identifiant est un nom de fichier normalisé : aucun chemin fourni par le client. Un assistant ou un modèle d'IA inconnu du poste retombe sur celui par défaut.
- **INV-CHAINE-3** — L'IA adapte la chaîne au dossier réel par `orch chaine sauter|ajouter|dedoubler|consigne`, seulement sur une phase à venir (jamais passée ni en cours), toujours avec un motif ; chaque ajustement est journalisé dans l'exécution et affiché à l'utilisateur. Une phase sautée passe au statut `abandonne` ; une phase ajoutée devient une tâche enfant numérotée `n.i`.
- **INV-CHAINE-4** — Surveillance : un modèle qui nomme `surveiller` (dossier relatif au vault, jamais absolu ni `..`) lance la chaîne sur chaque sous-dossier nouveau, une seule fois (compté avant le lancement), au plus 5 par passage ; les sous-dossiers présents quand la surveillance commence — ou quand le dossier surveillé change — ne sont jamais rattrapés.

### Messages et liens
- **INV-MSG-1** — Un message entre tâches porte un compteur de sauts ; au-delà de `moteur.sauts_max`, il est refusé (409).
- **INV-MSG-2** — Un tour déclenché par un message venu d'une tâche T (message `de`, ou propagation INV-LIEN-1, qui note sa tâche source) ne propage jamais vers T à sa fin : T est déjà informée.
- **INV-LIEN-1** — À la fin RÉUSSIE d'un tour d'une tâche source, si `liens.propagation` est vrai, chaque tâche qu'elle alimente et dont le statut est ouvert reçoit un message (`sauts` = sauts du tour + 1, soumis à INV-MSG-1) : `[La tâche « <titre> » (<id>), qui t'alimente, vient d'avancer. Fait : … Situation : … Mets à jour ce qui en dépend ; s'il n'y a rien à faire, dis-le en une ligne.]`. Jamais de propagation après un tour en échec ou interrompu, ni vers une tâche fermée.

### Temps
- **INV-TEMPS-1** — `echeance` (AAAA-MM-JJ) et `priorite` (`haute` | `moyenne` | `basse`) sont des clés gérées (INV-VAULT-1). Lecture tolérante : une valeur hors norme du vault (`priorite: normale`, date illisible) ne fait jamais échouer l'index, n'est jamais réécrite d'office, et vaut « moyenne » / « pas d'échéance » pour le tri. Écriture stricte : toute pose passe par `temps.valider` (400 sinon) ; la chaîne vide retire la clé. Une échéance proposée par un agent n'est écrite qu'à l'acceptation (INV-EXEC-5).

- **INV-DECISIONS-1** — Page « Décisions » (`decisions.py`, `api_decisions.py`, `web/decisions.js`). Une ligne par décision en attente, toutes sources réunies : tâche `retour-humain` (`reponse`), tâche terminée à valider (`validation`), proposition en attente hors `fermer` (`proposition`), propositions `fermer` d'un même auteur (`revue`), tâche ouverte à échéance dépassée qui n'est déjà dans aucune autre ligne (`echeance`). La question se lit sans ouvrir la fiche : clé `commentaire:`, sinon « Prochain pas », sinon dernier paragraphe interrogatif de l'agent relu aux journaux ; pour `validation`, Résultat et Essai (R1). Le tri est celui d'`ordonnancement.classer` (INV-ORDO-2), jamais un second classement. Aucun statut n'est posé sans geste humain : chaque geste (valider, renvoyer, répondre, reporter, accepter, fermer) réutilise la route existante ; chaque ligne de tâche porte « De quoi il s'agit » (`sujet` : description de la tâche, sinon `situation` de la fiche) et « Ce qui a été fait » (`fait`) ; sans l'un des deux, `muette` est vrai et « Faire documenter » (`POST /decisions/documenter`) envoie à l'agent de la tâche la consigne de les écrire avec le mode de validation. Une tâche ou un ticket créé par un agent exige une description d'au moins une phrase (`vault.exiger_description`, 400 lisible) : `POST /taches` avec `de` ou l'en-tête `X-Orch-Tache` (posé par `orch` depuis `ORCH_TACHE`), dont la commande `orch creer` (qui envoie toujours `de`), et les propositions `tache` / `ticket`, dont le `motif` devient la description. Les lots `POST /decisions/valider` et `/decisions/fermer` exécutent les gestes un à un, un refus (verrou, déjà tranché) n'arrête pas le lot.
- **INV-EVITABLE-1** — Pastille « évitable ? » (`evitable.py`, `GET|PUT /api/decisions/evitable`, section des Réglages `web/evitable.js`). Informative : elle ne pose aucun statut et n'écrit rien dans le vault. Réglage `{actif, seuil}` dans `<donnees>/etat/evitable.json` (défaut : activée, 75 % ; seuil entier de 25 à 100, sinon 400) ; fichier absent ou illisible = défaut. Sur une décision `validation` : quatre critères (fiche avec Résultat et Essai ; Essai sans geste dans l'interface ; contrôle réussi et non périmé ; aucun refus de la revue IA au dernier passage de la validation automatique) ; sur une `reponse` : deux critères (question de permission ou de choix ordinaire ; périmètre en validation automatique). La pastille paraît si la part de critères remplis atteint le seuil (au moins un critère) ; une exclusion sensible d'INV-VALID-2 (argent, envoi, secret, publication…) l'écarte toujours. `decisions.rassembler` ajoute `evitable: {score, sur, seuil, motif, criteres}` à la ligne ; l'interface l'affiche à côté du libellé (motif au survol) et en clair sous la fiche.
- **INV-SCAN-1** — Scan du système (`scan.py`, `POST /decisions/scan`, bouton « Scanner le système » de la page « Décisions »). Règles déterministes sur les tâches ouvertes (`a-faire`, `en-cours`, `confier-agent`, `bloque` ; hors `nature: permanente`, pilotage et tour en cours) : doublon probable (titres à 80 % de mots communs, hors mère et ticket : `fermer abandonne` sur la plus récente, gain fort, effort moyen), sommeil (aucune mise à jour depuis 60 jours, pas d'échéance à venir : `fermer abandonne`, gain moyen, effort faible), sans place (tâche du conteneur d'arrivée sans mère, titre à 50 % proche d'une tâche rangée : `deplacer` vers son conteneur, gain moyen, effort faible). Chaque préconisation est une proposition (`de: scan`, `gain`, `effort`, `motif`) toujours en attente, quelle que soit la politique (INV-INTERFACE-3 ne s'applique pas) : rien n'est fermé, déplacé ni supprimé sans l'acceptation de l'utilisateur (INV-EXEC-5). Une préconisation qui attend déjà ou a été refusée n'est jamais reproposée. Sur la page « Décisions », lignes `scan` (« Préconisation ») groupées sous « Scan du système », après les tâches, classées gain décroissant puis effort croissant, chacune avec Accepter / Refuser (`/propositions/{n}/accepter|refuser`).
- **INV-DECISIONS-2** — Réponse envoyée, décision levée (`decisions._repondue`, `decisions.reprises`). Une tâche `retour-humain` ou à valider sur laquelle un tour attend ou court (`moteur.etat_de` = `en_file` | `en_cours`) n'est plus une décision : le statut de retour ne se lève qu'au départ du tour (verrou, poste, compactage, file), et la page ne doit pas montrer entre-temps une question déjà traitée. `GET /decisions` la porte dans `reprises` (mention discrète « Réponse envoyée, l'agent reprend ») ; `total` et le compteur l'ignorent. Elle ne revient que par une nouvelle entrée, quand l'agent conclut à une nouvelle question (statut de retour reposé sans tour actif). Vaut pour toute réponse, d'où qu'elle vienne : toutes passent par `moteur.soumettre`.
- **INV-DECISIONS-3** — Décision reportée (`temps.poser`, `temps.reportee`, clé `reporte_jusqu_au`). Donner une échéance future à une tâche qui attend une décision (retour-humain, à valider, en retard) est un report : `temps.poser`, voie unique de `POST /taches/{id}/temps` (bouton « Reporter », fiche) et du geste Telegram, écrit aussi `reporte_jusqu_au`. Tant que cette date est future, la tâche n'est ni une ligne de `GET /decisions` (donc ni la pastille Décisions, ni le téléphone) ni comptée dans `a_moi` ; la date atteinte, elle revient d'elle-même, sans geste. Une échéance passée, vide ou donnée hors décision retire la clé.
- **INV-AGENTSCC-1** — Agents de Claude Code (`agents_cc.py`, `[agents_cc]`, `web/decisions-agents.js`). Lecture seule du dossier de travaux de Claude Code (`dossier`, vide = débrayé ; `rythme` = `a-la-demande` | `horaire` | `quotidien`, défaut quotidien) : un agent = un sous-dossier à `state.json` lisible avec une session (`resumeSessionId`, sinon `sessionId`) ; GoldenBrain n'y écrit jamais. Doublons : même nom normalisé (casse, accents, ponctuation, « ⑂ », suffixe « (n) » ignorés) et même dossier d'origine (`originCwd`, sinon `cwd`) = un groupe ; le plus récent est le titulaire (sa session est celle qu'on reprend), les autres l'historique. Rattachement proposé par groupe : `deja` (une tâche porte une session du groupe : aucune décision), `rattacher` (tâche ouverte sans conversation dont le titre ressemble, +0,2 si elle vit dans le projet du dossier ; jamais une tâche qui a déjà une `session`), `creer` (titre = nom, conteneur déduit du dépôt déclaré par le projet ou par la table des projets externes, description = dernier message), `ignorer` (agent clos sans message). Rien n'est créé ni rattaché sans geste : les groupes à trancher sont des lignes `agent` de la page « Décisions » (INV-DECISIONS-1, après les tâches), appliquées par `POST /decisions/agents` (un par un ; un refus n'arrête pas le lot) ; « ignorer » mémorise les sessions du groupe dans `etat/agents_cc.json` (une session plus récente le fait réapparaître). Rattacher ou créer pose `session` et `harnais: claude` sur la tâche : la reprise est celle de toute tâche à session (`claude --resume`). Relevé : à la demande (`orch agents-cc [--relever]`, `GET /agents-cc[?relever=true]`) et par une boucle du `lifespan` au rythme réglé. Option non installée : un hook de fin de session de Claude Code qui appellerait `orch agents-cc --relever` (sans dépendance, sans écriture dans `~/.claude` par GoldenBrain) — à proposer, pas à installer.

### Arbre
- **INV-ARBRE-1** — Un geste d'arbre qui écrit des rattachements logiques (gestes sur les tâches, rattachement logique d'un dossier non déplaçable) n'édite que les clés `parent` et `casquette` (ligne à ligne, INV-VAULT-1) et `updated` si elle existe déjà ; il ne crée, ne déplace ni ne renomme aucun dossier ; il est tout ou rien : si une écriture échoue, les fichiers déjà modifiés retrouvent leurs octets d'origine et le geste renvoie 409.
- **INV-ARBRE-2** — Le dossier fait foi : un conteneur sans `parent:` est aligné par construction ; un geste d'arbre sur un projet ou une opération déplace son dossier (plan puis application par l'alignement) et ne pose plus `parent:` ; il retire `parent:` des conteneurs déplacés. Seule exception : un projet dont le dossier contient `.git` ou `.claude` (INV-ALIGN-3) reçoit un rattachement logique (INV-ARBRE-1), signalé dans le plan et par `logique`.

### Équipe et validation
- **INV-EQUIPE-1** — Un tour de persona compte dans `moteur.simultanes_max`, a son journal (INV-EXEC-4), n'est jamais relancé seul (INV-EXEC-1) et n'écrit pas dans le fichier de la tâche. Un persona ne se revoit pas lui-même et une revue ne déclenche pas de revue ; un tour de persona (`ORCH_PERSONA`) ne sollicite pas l'équipe.
- **INV-VALID-1** — Une tâche verrouillée (INV-VAULT-4) n'est jamais validée ni renvoyée automatiquement. Le compteur de renvois est persistant (`<donnees>/etat/revues.json`) et remis à zéro par une validation.
- **INV-VALID-2** — Validation automatique par périmètre (`validation_auto.py`, `api_validation.py`). Clé `validation: manuelle|automatique` (défaut `manuelle` ; valeur inconnue = manuelle, jamais présumée) posée sur un `contexte.md` ou une tâche ; héritage tâche → conteneur le plus proche → … ; `validation_exclusions` (liste de mots **entiers**, frontière de mot, accents ignorés ; `deploi*` ouvre la fin du mot ; défaut : infra, déploiement, production, suppression, structure du vault, argent, identité, envoi, publication…) et `validation_exemptions` (expressions retirées du titre avant la recherche ; défaut « garde de publication ») et `validation_echantillon` (N, défaut 5) s'héritent de même, clé par clé. Posée depuis l'interface, la clé s'accompagne de `validation_accord: "posé depuis l'interface le AAAA-MM-JJ"` (posée à la main : l'auteur écrit la sienne). Sur une tâche du périmètre passée `fait` par sa déclaration `terminee`, le moteur écrit `cloture` **seulement si** : (a) aucune exclusion ne frappe son titre ni ses tags ; (b) la fiche porte Résultat et Essai (R1) et la tâche n'est pas démontrable : l'Essai ne décrit pas un geste dans l'interface (`DEMONTRABLE_MOTIFS` : interface, 127.0.0.1, cliquer, bouton, page, onglet, glisser, sélecteur, affichage, écran…, normalisés) ; `demontrable: oui` en frontmatter de la tâche force le refus, `demontrable: non` force l'automatique ; l'Essai écrit par l'agent décide donc de la clôture ; (c) un contrôle déterministe est déclaré et son dernier verdict est `reussi` et non périmé (INV-CONTROLE-1) ; (d) une revue IA indépendante — `[validation] revue_harnais/revue_modele`, sinon un autre harnais, sinon le même harnais avec une autre famille de modèle ; jamais le moteur de l'auteur — rend `verdict: ok` sans aucun point `[P1]` (grille P1/P2/P3) ; (e) la tâche n'est pas verrouillée (INV-VALID-1). Sinon la tâche reste `fait` (« à valider ») et la ligne de Décisions porte le motif. Une clôture sur N (compteur persistant) reste à l'utilisateur pour audit (issue `echantillon`). « Réévaluer » (`orch reevaluer`, `POST /api/validation-auto/reevaluer`) rejoue les seuls préalables sans IA (a, b, c) sur les tâches `fait` des périmètres automatiques : il ne clôt rien, ne lance ni revue ni contrôle, et écrit un motif par tâche sous `reevaluation` du journal. Chaque évaluation est journalisée dans `<donnees>/etat/validation_auto.json` (tâche, issue `cloture|refus|echantillon`, motif, date, contrôle, revue, auteur) ; « Rouvrir » (`POST /api/validation-auto/rouvrir`) remet `fait` une tâche close automatiquement (409 sinon) et marque l'entrée `rouvert`. Le persona validateur ne s'applique pas dans un périmètre automatique ; les personas de revue tournent seulement si l'équipe est active.
- **INV-RENOMMER-1** — Renommer une tâche ne change que son titre : le `# …` du corps (celui que lit `titre_de`), ou, faute de titre `# …`, un titre posé en tête du corps ; l'identifiant, le nom du fichier, les liens, la session et les routes restent valides, le frontmatter de l'utilisateur n'est pas reformaté (INV-VAULT-1 ; seul `updated` est rafraîchi). Le titre est validé par `vault.titre_valide` (une ligne, non vide, 200 caractères au plus ; 400 sinon). Même geste par `POST /taches/{id}/renommer {"titre"}`, `orch renommer <id> "<titre>"` et le clic sur le titre de la fiche. Le nouveau titre se lit partout où l'index est lu (arbre, recherche, Telegram, tableau de bord).
- **INV-DEJAFAIT-1** — Une proposition dont l'effet est déjà en place (`lier` : lien présent ; `rattacher` : lot déjà sous ce parent ; `deplacer` : déjà au bon projet, sans parent ; `fermer` : déjà ce statut) n'est pas déposée (`{"etat": "deja_fait"}`, rien de mémorisé) ; si elle le devient avant le geste humain, l'acceptation la conclut `acceptee` avec `deja_fait: true`, sans erreur (l'interface le dit discrètement).
- **INV-RATTACHER-1** — Une proposition `rattacher` (valeur = id de la tâche parente, ou `racine` pour détacher ; `tache` + `taches` = le lot, UNE seule entrée dans Décisions) pose la clé `parent` des tâches du lot, sans déplacer de dossier. Mêmes contrôles (`rattachement.verifier`) à la proposition (400/409 immédiat) et à l'acceptation (l'arbre a pu bouger ; tout le lot ou rien) : cycle (le parent descend de la tâche), tâche occupée par un agent (INV-VERROU-1), parent d'un autre projet que la tâche (le routage suit le projet : `deplacer` d'abord), plafond de tâches ouvertes sous le parent (INV-PLAFOND-1) et natures mêlées (INV-NATURE-1). Les tâches déjà sous ce parent sont ignorées.
- **INV-RENOMMER-2** — Une proposition `renommer` (valeur = titre proposé ; `motif` obligatoire : ce que le titre actuel ne dit pas) refuse tout de suite un titre invalide ou identique à l'actuel ; elle n'est appliquée que par le geste humain (INV-EXEC-5), page Décisions, et sous le plafond du jardinier (INV-JARD-2) — sauf si `renommer` est parmi les gestes d'office (INV-PROP-1).
- **INV-JARD-2** — Le jardinier ne fait que proposer : toute proposition déposée par la tâche du jardinage attend le geste humain (page Décisions), quelle que soit la politique des propositions, et au plus `[jardinage] plafond` (7 par défaut) par passage ; la suivante est refusée (`Invalide`). Le compte (`posees`, dans `etat/jardinage.json`) repart à zéro à chaque passage. Le message du passage cite les tâches modifiées depuis `recentes_jours`.
- **INV-JARD-1** — Au plus une revue de cohérence automatique par période (jour ou semaine). Une échéance manquée (serveur éteint) donne UNE revue au démarrage suivant, jamais un rattrapage multiple. Pas de revue automatique si celle de la tâche est déjà en cours ou en file.
- **INV-EXECUTANT-1** — Curseur « Moi / IA » (`executant.py`, `api_executant.py`). Clé gérée `executant: humain|ia` ; absente ou toute autre valeur = `ia` (jamais présumée humaine). Sur une tâche `humain` : (a) `Moteur.soumettre` lève 409 — aucun tour, qu'il vienne d'un message, de la file, d'une reprise ou relance après redémarrage, d'un réveil, d'une routine, du jardinier, d'une revue, d'une propagation ou de Telegram ; un tour déjà en attente du poste ne part pas si la tâche est passée humaine entre-temps ; (b) ni revue ni validation (persona, validateur, INV-VALID-2) ; (c) le middleware refuse (409) toute écriture d'agent (`X-Orch-Tache`) sur `/api/taches/{id}[/…]`, sauf `/liens`. La conversation reste lisible mais inactive (saisie désactivée). Passer à `humain` vide la file de la tâche (persistée, INV-EXEC-9) ; le tour en cours se termine. « Confier la suite » (`POST /confier`) pose `ia` puis soumet la consigne (ou « Reprends la suite à partir de mes notes. ») ; le contexte vient de l'amorce (INV-EXECUTANT-2), injectée d'office à ce tour-là.
- **INV-EXECUTANT-2** — Notes de l'utilisateur (`executant.py`, `fiches.bornes_notes`, `Vault.reecrire`). Bloc géré du corps, distinct du bloc fiche, créé avant lui (sinon en fin de fichier) : `<!-- orchestrateur:notes -->`, `## Notes`, puis par note `<!-- note AAAA-MM-JJ HH:MM[ · modifiée AAAA-MM-JJ HH:MM] -->` suivi de son texte Markdown, et `<!-- orchestrateur:notes-fin -->` ; une ligne de note qui ressemble à un marqueur est préfixée d'une espace ; le reste du fichier est restitué octet pour octet (INV-VAULT-1) et le bloc est retiré du `corps` affiché. Ajout et édition par l'humain seul, dans les deux modes : le middleware refuse à tout agent (`X-Orch-Tache`) l'écriture sur `/notes`, quel que soit l'exécutant ; l'agent les lit (`orch lire`) et écrit dans la conversation et la fiche. Amorce (`executant.amorcer`, appelée par le tour après INV-PILOTAGE-2) : si la tâche a des notes et que la session est neuve ou que les notes ont changé depuis la dernière injection (empreinte en mémoire du moteur ; « Confier la suite » la vide), le message envoyé au harnais est préfixé des notes (intégrales sous `PLAFOND` = 6 000 caractères ; au-delà, les plus anciennes réduites à « date — début… » avec le chemin du fichier), de l'état de la fiche (fait, résultat, essai, situation, reste, prochain pas), des 3 derniers tours (date, message demandé) et de la consigne d'ouvrir la réponse par un point de situation en 3 lignes tiré des notes ; le journal garde le texte humain.
- **INV-EXECUTANT-3** — Bouton « IA » du panneau Notes (`notes_ia.py`, `POST /taches/{id}/notes/ia`, `web/notes_ia.js`). Résumer, corriger ou synthétiser (points clés, décisions, actions à mener) : seul le texte de la portée choisie par l'utilisateur (sélection dans une note, sinon toutes les notes) part au modèle, par un appel éphémère hors de la conversation de la tâche, sur le rôle `notes` (famille `rapide` par défaut, décalée par le curseur, repli de quota journalisé, INV-ECO-1, INV-MOTEUR-2) ; coût rendu quand le harnais le mesure. Permis dans les deux modes (c'est l'utilisateur qui le demande) ; refusé à tout agent comme le reste de `/notes` (INV-EXECUTANT-2).
- **INV-DETAIL-1** — Ouverture d'une tâche allégée (`web/detail.js`, `web/ecrans.css`, `web/telephone.css`). Les alertes (incident, pause, contrôle échoué) ne s'empilent pas : une pastille pour la plus importante, « +N » pour les autres, un clic ouvre « Détails ». Rien n'est retiré ; seule la présentation change. Mesure gardée par `tests/ui/scenario_detail_allege.py` : la hauteur au-dessus des messages reste ≤ 15 % de l'écran (1366×768 et 390×844).
- **INV-BARRE-1** — La barre haute ne déborde jamais de la fenêtre et rien n'y chevauche rien (`web/interface.js`, `web/barre.css`). Gardé à 1366, 1280, 1024 et 390 px, en discussion et en disposition complète : rectangles de tous les éléments visibles deux à deux disjoints, dans la fenêtre, aucun texte de pastille rogné (`tests/ui/scenario_barre_haute.py`).
- **INV-DISCUSSION-1** — Mode discussion (`web/discussion.js`, `web/discussion.css`, `web/notes_tache.js`, `web/detail.js`). Dès qu'une tâche est ouverte (au-delà de 480 px) et sauf choix « Tout afficher », `body.discussion` rend à la conversation l'essentiel de l'écran : barre haute d'une rangée (les boutons Équipe, Revue, Routine, Chaînes, Réglages, Manager et guide vivent dans « Menu », déroulé au survol ou au clic ; « En cours » devient une pastille), arbre replié en rail à intercalaire toujours visible (survol = aperçu, clic = épinglé), notes repliées derrière un intercalaire portant leur nombre. Rien n'est retiré : chaque volet reste à un geste (survol, clic, Alt+T / Alt+N / Alt+M / Alt+D) ; jamais de menu invisible, toujours un repère cliquable ; un bandeau en flux (avant `#corps`, rien n'est recouvert) le dit une seule fois, marqué vu dès son apparition. Les choix sont mémorisés par poste (`gb.disposition`, `gb.panneaux-tache`). Au téléphone la disposition est inchangée. Ouverture d'une tâche : le fil est demandé en parallèle de la fiche et le transcript analysé est mémorisé par (fichier, date, taille) ; les derniers échanges s'affichent d'abord, le début de l'historique ensuite. La barre haute d'une rangée ne dépend pas de l'ouverture d'une tâche : `body.barre-fine` la pose sur tous les écrans (sauf « Tout afficher » et téléphone) ; en barre fine le silence d'un tour se lit sur la pastille « En cours » (`vigie.js`), la rangée « En direct » de la cascade et le bandeau de silence ne s'affichent pas, le filtre de statut partage la ligne du titre, et dans la fiche le titre cède sa place en dernier (`ui/scenario_accueil_rangee.py`).
- **INV-DISCUSSION-2** — Bandeau de premier usage du mode discussion vu une fois par poste (`web/discussion.js`, `api_interface.py`, `config.ConfigInterface.vus`). À sa première apparition, l'interface envoie `PUT /api/interface {vu: "discussion"}` ; le serveur l'ajoute à `[interface] vus` de `config.toml` et le renvoie dans `GET /api/interface` (`vus`). Tout navigateur, tout nouveau contexte de ce poste lit cette liste avant de montrer le bandeau : il ne réapparaît jamais. `localStorage` n'est plus qu'un relais hors ligne.
- **INV-DEROULANT-1** — Un seul composant déroulant (`web/deroulant.js`, `web/deroulant.css`) pour tout ce qui encombrait l'écran : Propositions, Aujourd'hui, Décisions, À moi, En cours (`web/apercus.js` : cinq lignes au plus, « Tout voir » vers la page pleine), Incidents, dossiers à aligner, Détails de la fiche, « Filtres et regroupement » de l'arbre (`web/filtres.js`, `#btn-filtres`), filtre de statut de la vue en cascade (`#btn-statuts`), modification en bloc (`web/lot.js`, `#btn-lot` : épinglé tant que la sélection dure), et la pastille « Infos » qui porte les bandeaux d'information (poste réservé, mise à jour, réseau ; `#panneau-etat`). Jamais invisible : une pastille ou un intercalaire avec compteur ; masquée seulement quand il n'y a rien. Ouverture au survol à la souris après 150 ms de présence (délai d'intention ; un passage bref n'ouvre rien), au clic, au clavier (focus dans le panneau), au toucher (= clic) ; fermeture 350 ms après la sortie du curseur (tolérance en diagonale vers le panneau), au reclic, à Échap (focus rendu à la pastille) ou au clic extérieur ; l'épingle le garde ouvert. Un seul ouvert à la fois, hors épinglés. Le panneau flotte au-dessus du contenu (aucun saut de mise en page) et glisse vers la gauche plutôt que de déborder ; au téléphone, feuille qui monte du bas. Une alerte qui exige un geste (`role=alert` : erreur, vigie) reste dans la pile des bandeaux, visible sans survol. Les rails (arbre, notes) partagent le même délai d'intention (`intention()`). Mesure gardée par `tests/ui/scenario_deroulant.py` : en mode discussion, aucune zone permanente hors barre haute d'une rangée, rails, conversation (en-tête compris) et alertes.
- **INV-REACTIVITE-1** — Budget de réactivité (`tests/ui/scenario_reactivite.py`, vault de charge `tests/ui/charge.py` : 260 tâches, 150 décisions, fil de 200 messages ; 1366×768 et 390×844). Premier affichage utile ≤ 1,5 s, derniers messages d'une tâche ≤ 300 ms, intercalaire ≤ 150 ms sans décalage notable, frappe < 50 ms, défilement à 60 images/s, aucun appel GET en double au chargement. L'index du vault est gardé `index_ttl_s` (2 s par défaut ; périmé par toute écriture de l'orchestrateur) : sans lui chaque page relisait le vault des centaines de fois (Décisions : 16 s). Un événement qui ne concerne pas la tâche ouverte (autre tâche, ou « arbre » seul) ne recharge que l'arbre et l'état (`app.js` `planifier`) : ni conversation, ni propositions, ni manager ; la fiche ouverte ne se relit que si sa ligne de l'arbre a changé. Limite assumée : épingler l'arbre déplace la conversation, c'est le geste lui-même. Itération 2 : (a) un seul bandeau à la fois, d'une ligne tronquée (les bandeaux d'information vivent depuis dans la pastille « Infos », INV-DEROULANT-1) (`web/bandeaux.js`, du plus urgent au moins urgent, les autres derrière « +N », détail au clic ou au toucher) ; le bandeau « Mode discussion » se referme à la première interaction ; (b) au téléphone, notes repliées par défaut, en-tête sur une rangée (« Voir le résultat » dans « Détails ») : fil + saisie ≥ 70 % de la hauteur (390×844) ; (c) intercalaires à identifiant stable : `#rail-arbre` (tâches) et `#intercalaire-notes` (notes), un seul élément chacun, au clavier ; `#onglet-taches` / `#onglet-notes` sont les onglets Tâches / Notes du vault, à l'intérieur de l'arbre ouvert ; (d) chargement : feuille de style unique `/style-tout.css` assemblée par le serveur depuis `web/styles.liste` (`api_styles.py`, sans étape de construction) ; écrans, fiche de tâche et services de fond chargés à la demande (`web/paresseux.js`, `import()` natif), ces derniers juste après l'affichage de l'arbre ; budget au premier affichage : ≤ 60 requêtes dont ≤ 10 appels /api.

### Feu vert
- **INV-FEU-1** — Un feu vert vaut pour un sha complet (40 hex) et pour lui seul : `orch feu-vert verifier <sha>` rend 0 seulement si une demande pour ce sha exact a été accordée ; préfixe, autre sha, demande en attente ou refusée, serveur injoignable : code non nul. Seul le contrôleur désigné par la demande (`ORCH_TACHE` = `--a`) tranche ; une tâche ne se demande pas son feu vert à elle-même ; un verdict ne se tranche qu'une fois (une nouvelle demande rouvre un refus ; un accord est définitif). Registre `<donnees>/etat/feux-verts.json` ; chaque demande et verdict est consigné, horodaté et signé, dans la section « Feux verts » du corps de la tâche demandeuse (frontmatter intact, INV-VAULT-1). Garde contre l'oubli, pas contre la malveillance : un agent peut forger `ORCH_TACHE`.

### Alignement et transformations
- **INV-ALIGN-1** — `appliquer` est tout ou rien. Ordre : (a) contrôle du jeton et des conflits, (b) point de restauration git si demandé et si le vault est un dépôt (`git add -A` + commit `--allow-empty` ; échec du commit = abandon, rien n'est touché), (c) déplacements (`os.rename`, parents créés, jamais d'écrasement, source = dossier entier), (d) réécritures atomiques, (e) clés de fiche posées (geste d'arbre). Un échec en (c), (d) ou (e) défait les déplacements faits et restaure les octets des fichiers réécrits. Les dossiers parents laissés vides par un déplacement sont retirés de proche en proche, jusqu'au premier dossier protégé (INV-ALIGN-3 : jamais un dossier de casquette ni `Projets`) ou non vide.
- **INV-ALIGN-4** — Le point de restauration git enregistre les octets du vault tels quels, et la restauration documentée les rend tels quels, quelle que soit la configuration git du poste (`core.autocrlf=true` de Git for Windows compris) : chaque appel git de l'alignement porte `GIT_NEUTRE` (`-c core.autocrlf=false -c core.eol=lf -c core.safecrlf=false`), sans rien écrire dans la configuration de l'utilisateur. Restauration : `git -c core.autocrlf=false -c core.eol=lf -c core.safecrlf=false reset --hard <commit>`, puis `git clean -nd` pour lister les dossiers créés par l'alignement et `git clean -fd` pour les retirer. Limite : un `.gitattributes` du vault (`text`, `eol`) prime encore ; le vault de l'utilisateur n'en a pas.
- **INV-ALIGN-2** — Un déplacement de dossier (geste d'arbre, alignement, acceptation d'une proposition `operation`, réduction d'un projet) ne bloque que les tours qui le touchent. `Moteur.exclusif(dossiers, fichiers)` (`verrou.py`) refuse (409) si un tour tourne, attend en file ou est en revue sur une tâche située DANS un des dossiers déplacés, ou sur une tâche dont le fichier figure parmi les fichiers réécrits par le plan (références, clés posées) ; le refus nomme ces tâches (« titre » (id)). Les autres tours continuent. Pendant `appliquer`, aucun tour ne démarre sur une tâche de ces dossiers ou fichiers (il attend la fin du geste, personas compris) ; les autres tâches démarrent. Le renommage ou déplacement d'une note applique la même règle à sa propre tâche et aux tâches dont le fichier est réécrit (409 nommé). `exclusif()` sans argument (avance du dépôt, `POST /mise-a-jour`) garde le verrou global : refus dès qu'un tour est actif n'importe où, puis aucun tour ne démarre (`Creneaux.bloquer`). Un seul déplacement à la fois. Le plan, simple simulation, n'est pas bloqué. Les sessions des tâches ne dépendent pas du chemin (identifiant = nom de fichier) : rien d'autre à migrer.
- **INV-LOT-1** — Changement en bloc (`lot_statuts.py`, `api_lots.py`, `web/lot.js`). `POST /api/lots {taches, statut?, echeance?, parent?, apercu?}` : tout le lot est validé AVANT la première écriture, avec les mêmes refus qu'à l'unité (statut inconnu, échéance mal formée, tâche inconnue, tâche tenue par Paperclip INV-VAULT-4, cycle ou plafond de rattachement INV-RATTACHER-1, plus de 200 tâches) ; un refus rejette le lot entier. Les tâches dont un agent travaille (INV-VERROU-1) ne sont jamais touchées : exclues et rendues dans `exclues`, le reste est appliqué. Une panne en cours d'écriture remet l'état d'avant (tout ou rien). `apercu: true` ne rend que `{retenues, exclues, de}` sans rien écrire (récapitulatif de confirmation). Chaque changement est tracé dans `donnees/journal/statuts/<tâche>.jsonl` et l'état d'avant/après est gardé dans `donnees/lots/<lot>.json` : `POST /api/lots/{lot}/annuler` remet seules les tâches encore dans l'état posé par le lot et non occupées (les autres sont rendues dans `ignorees`), une seule fois. Geste réservé à l'humain : toute requête portant `X-Orch-Tache` est refusée (403) — refus par en-tête, non par jeton (B4 reste à faire) ; à distance, lot et annulation sont des gestes à risque (INV-DISTANT-7).
- **INV-VERROU-1** — Demi-verrou des gestes humains. Une seule fonction dit qu'un agent travaille sur une tâche : `Moteur.occupation(id)` (`verrou.py`) — un tour de la tâche ou d'un persona sur elle tourne ou attend en file, ou une revue d'elle est en suspens ; elle rend `{tache, titre, depuis, moteur}` ou rien. `exclusif` (INV-ALIGN-2), `occupees_sous` et `etat_global().occupees` s'en servent, sans autre définition. Les gestes humains suivants répondent 409 nommé (`{"detail": "Un agent travaille sur « X » depuis HH:MM", "occupee": {…}}`) si leur cible est occupée, sauf `"forcer": true` dans le corps : `POST /arbre/deplacer`, `/arbre/monter`, `/arbre/plan` (nœud et toute sa descendance), `POST /taches/{id}/deplacer`, `/promouvoir` (tâche et descendance), `/statut`, `/valider`, `/renvoyer` (la tâche seule), `POST /conteneurs/reduire` (descendance), `PUT /vault/note` (fichier de tâche : la tâche ; `contexte.md` d'un conteneur : sa descendance), `POST /vault/note/deplacer` (tâche ou conteneur et descendance). `messages` et `arret` restent libres. `forcer` n'outrepasse jamais INV-ALIGN-2 : un dossier ou une note déplacés sous un agent qui y travaille restent refusés (409 sans `occupee`).
- **INV-NATIF-1** — Interface native du harnais. `POST /taches/{id}/natif` (`natif.py`) ouvre un onglet de Windows Terminal (`wt -w 0 nt`, repli : nouvelle console) qui lance `orch.py natif <fichier>` : ce relais écrit son PID (`<donnees>/etat/natif/<id>.pid`) puis exécute le harnais au premier plan — session de la tâche reprise, ou, sans session, session neuve préparée comme un premier tour (même consigne, `sessions.premier_message`), écrite dans la fiche avant l'ouverture. Refusé (409) si un tour tourne ou attend sur la tâche, si l'interface est déjà ouverte, ou si le harnais ne sait pas démarrer une session préparée (pas d'`argv_natif`) et que la tâche n'a pas de session. Tant que le processus du relais vit, la tâche est occupée par l'utilisateur (`occupation` rend `terminal: true`, 409 « Vous travaillez au terminal sur « X » depuis HH:MM ») et aucun tour ne démarre : `soumettre` met en file sans lancer la boucle. La mise à jour du dépôt est refusée pendant ce temps (`occupe`). À sa fin (onglet fermé compris) : l'échange ajouté depuis l'ouverture est relu ; terminé par une réponse de l'agent, sa fiche est écrite (statut déclaré, INV-EXEC-7) ; coupé en plein travail (dernier message de l'utilisateur sans réponse, ou dernier message de l'agent appelant un outil), un message de reprise signé GoldenBrain passe en tête de file ; puis la file est traitée sur la même session. Événement `natif_fin` `{tache, reprise}`. L'ouverture vit en mémoire : un redémarrage du serveur l'oublie (l'onglet survit, sa fermeture n'est plus relayée).
- **INV-RESULTAT-1** — « Voir le résultat » (`resultat.py`, routes `api_resultat.py`, bouton `web/resultat.js`). `GET /taches/{id}/resultat` relève, dans l'ordre, les adresses de ce poste (`localhost`, `127.x`, `[::1]`, `0.0.0.0`) citées dans le Résultat, l'Essai ou le Fait de la fiche, les fichiers ou dossiers existants qu'elle cite (absolus ou relatifs au dossier de travail), l'`index.html` du dossier de travail, les fichiers écrits au dernier tour (outils d'écriture du transcript, harnais qui en tient un lisible), puis le dossier de travail (INV-DEPOT-1) ; `{elements, message}`, message non vide si rien n'est trouvé. `POST /taches/{id}/resultat/ouvrir {cible}` ouvre avec l'application par défaut du système : le client ne désigne qu'un élément de la liste que le serveur recalcule (jamais un chemin libre ; sinon 404). Bornes : un chemin n'est retenu que sous le dossier de travail, le vault, le dossier personnel ou le temporaire ; une adresse hors de ce poste n'est jamais retenue ; un fichier qui s'exécuterait à l'ouverture (`EXECUTABLES` : scripts, programmes, raccourcis) n'est jamais lancé, son dossier s'ouvre à la place. Poste seulement : les deux routes sont refusées (403) à un appareil distant (`api_appareils.POSTE_SEUL_RE`, INV-DISTANT-7).
- **INV-ALIGN-3** — Un plan ne propose jamais de déplacer : la racine, un dossier de casquette, `Projets`, `_meta`, `Archives`, `Inbox`, `Journal-Log`, `Ressources`, ni un dossier qui contient un `.git` ou un sous-dossier `.claude`.
- **INV-TRANSFO-1** — Le découpage et la contraction ne sont exécutés que sur un geste humain (promotion, réduction, acceptation d'une proposition `projet`) ; les tickets sont créés par le moteur à partir du bloc rendu, l'agent ne crée rien lui-même (INV-EXEC-5). Un mandat en attente est persistant (`<donnees>/etat/mandats.json`) : un redémarrage ne le perd pas, un tour interrompu le laisse en attente d'un geste humain (jamais relancé seul).

### Notes
- **INV-NOTE-1** — Toute lecture et toute écriture portent sur un chemin résolu SOUS la racine du vault, hors dossiers exclus ; jamais de suivi d'un lien symbolique ou d'une jonction sortants ; un chemin fourni par un client est normalisé et vérifié (`notes.chemin_sur`) avant tout accès.
- **INV-NOTE-2** — L'écriture d'une note est atomique, enregistre EXACTEMENT le texte reçu (fins de ligne du fichier d'origine conservées, BOM conservé), et exige la date de modification lue (`mtime_ns`) : si le fichier a changé depuis (Obsidian, agent), 409 avec la version courante, rien n'est écrasé. La création refuse d'écraser (409).
- **INV-NOTE-4** — Les mentions non liées d'une note sont les notes dont le texte contient son titre ou son nom de fichier (au moins 4 caractères, mot entier, sans casse ni accents), hors la note elle-même et hors celles qui la lient déjà ; lecture seule, au plus 30.
- **INV-GRAPHE-1** — Le graphe se calcule côté serveur à partir des index (aucun balayage du disque) et se sert d'un cache, périmé dès que l'index des notes change (`IndexNotes.generation`, avancée à tout ajout, modification ou retrait) ou que l'ensemble des tâches ou des conteneurs change.
- **INV-GRAPHE-2** — Jamais plus de `graphe.PLAFOND` (2 000) nœuds servis : au-delà, les plus reliés (graphe global) ou les plus proches puis les plus reliés (graphe local) ; `total` et `tronque` le disent. Dans le navigateur, la simulation de forces s'arrête à la stabilisation (ou après 400 pas) : au repos, aucun calcul ni dessin hors geste.
- **INV-NOTE-3** — Renommer ou déplacer une note réécrit les liens entrants par chemin (règles 1 à 3 de la réécriture des références) et laisse les wikilinks par simple nom, sauf si le NOM de fichier change : ils sont alors mis à jour. Tout ou rien.

### Telegram
- **INV-ETOILE-1** — L'invitation à mettre une étoile GitHub est unique et sobre : affichée après `[etoile] seuil_h` heures d'usage actif cumulé (l'interface compte sur ses événements d'interaction, onglet visible, inaction au-delà d'une minute ignorée, sans minuterie ; un envoi est borné à 5 minutes), jamais si le réglage est éteint, si l'adresse du dépôt (`origin` ou `[etoile] depot`) n'est pas GitHub, ou si l'API publique GitHub (sans jeton, 3 s, au plus une sonde par jour, échec gardé pour le jour) ne le dit pas public. « Plus tard » redemande après `report_jours` jours d'usage ; « Mettre une étoile » et « Ne plus demander » sont définitifs (aucune vérification de l'étoile, aucun compte). Une fois sans objet, plus aucune écriture. État dans `<donnees>/etat/etoile.json`, jamais dans le vault ni le dépôt ; rien n'est envoyé hors la sonde publique.
- **INV-TELEGRAM-1** — Le connecteur est désactivé par défaut et ne lit le bot (`getUpdates`) que sur réglage explicite (`[telegram] actif = true`) ET jeton présent : un bot n'admet qu'un lecteur (deux lecteurs = conflits 409). Un envoi d'une discussion hors liste blanche `discussions` est consommé (décalage avancé) et journalisé par son seul identifiant de discussion, sans contenu ni expéditeur. Le décalage est persisté après chaque mise à jour traitée (`<donnees>/etat/telegram.json`) : une coupure ne perd rien. Les pièces ne s'écrivent que sous le dossier de réception, lui-même sous la racine du vault (INV-NOTE-1), noms rendus sûrs.
- **INV-TELEGRAM-2** — Le jeton du bot (et la clé de transcription) ne sont jamais écrits en clair ni journalisés : lus dans une variable d'environnement (prioritaire), ou dans `<donnees>/etat/telegram.jeton` (`coffre.py`) : chiffré par DPAPI sous Windows, fichier aux droits 0600 ailleurs (Linux, macOS), écrit par Réglages → Telegram, hors du dépôt (`etat/` est ignoré) ; jamais dans `config.toml`, jamais dans une réponse de l'API ; tout message d'erreur réseau est masqué (`telegram.masquer`) avant journal. Saisie recommandée : `orch telegram-jeton` (`telegram_jeton.py`), dans un terminal du poste, sans écho (getpass), vérifiée par `getMe` puis rangée dans le coffre ; le jeton ne passe par aucune conversation d'agent, aucun harnais, et n'est jamais réaffiché ; le champ mot de passe de Réglages reste un repli.
- **INV-TELEGRAM-3** — Un message ou un bouton Telegram n'est jamais un ordre au-delà de la liste blanche, et jamais un paiement : le tri et l'exécutant préparent, l'humain paie (la validation bancaire reste humaine). Seul un bouton pressé sur discussion autorisée change une tâche : Valider (`fait`), ou Confirmer d'un geste proposé par l'assistant (statut, échéance ou priorité, liste fermée `telegram_assistant.GESTES`), appliqués par le code (`vault.poser_statut(humain=True)`, `vault.poser_temps`) ; Renvoyer et Annuler ne changent rien ; un bouton ne sert qu'une fois. Aucun agent ne change un statut par Telegram.
- **INV-TELEGRAM-4** — La nature d'une entrée Telegram est posée par le code, jamais par l'agent : texte, légende ou note vocale écrits par l'expéditeur autorisé = `[instruction]` ; message transféré (`forward_origin`…) ou pièce = `[contenu]`, une donnée qui n'est jamais un ordre. Une instruction libre va à l'assistant sans note de capture ; un contenu devient un envoi rangé.
- **INV-TELEGRAM-5** — La connexion guidée (`telegram_connexion.py`, `POST /api/telegram/reconnaitre`) lit les derniers messages du bot par `getUpdates` sans décalage : rien n'est consommé, le connecteur les relira. Quand le connecteur tourne, elle n'appelle pas `getUpdates` (deux lecteurs s'interrompent : 409) : elle lit les discussions que sa boucle a vues depuis son démarrage (`vues`, en mémoire, liste blanche ou non). Elle ne rend que l'identifiant et le nom affichable des discussions, jamais un contenu. Tant qu'un webhook est actif (ancien pipeline), elle ne lit pas (409) et le dit ; le lever est un geste explicite (`POST /api/telegram/webhook/desactiver`, sans perdre les messages en attente). Un 409 d'un autre lecteur est expliqué, jamais contourné (INV-TELEGRAM-1).
- **INV-MANAGER-1** — Le volet « manager » et Telegram sont deux canaux d'un seul fil : la même tâche permanente de l'assistant (`Connecteur.tache_tri`), la même conversation, le même entête (`telegram_assistant.entete`), la même mémoire (`situation`, `/nouveau` commun). Le texte tapé dans le volet est une `[instruction]` posée par le code (INV-TELEGRAM-4) ; un geste ou un choix proposé par l'assistant attend un bouton humain, dans le volet ou sur Telegram, et n'est appliqué qu'une fois, quel que soit le canal (même clé d'attente, `telegram_assistant.trancher`, INV-TELEGRAM-3) ; la route du bouton refuse (409) toute requête portant l'en-tête `X-Orch-Tache` : un agent ne confirme pas son propre geste. Le volet marche sans Telegram configuré ; rien ne tourne quand il est fermé (pas de sondage : événement SSE `manager`).

### Version et mise à jour
- **INV-VERSION-1** — Au démarrage, le serveur calcule l'empreinte de son code (`src/orchestrateur/**/*.py` : chemins relatifs, tailles, dates de modification → hachage court). `GET /etat` porte `"version": {"demarree", "disque", "a_jour", "depuis", "redemarrages"}` ; `disque` est recalculé au plus toutes les 15 s. Quand `a_jour` est faux, toute réponse 404 de l'API porte en plus `"perime": true`. Un redémarrage demandé termine le processus avec le code 3 après la fermeture propre.
- **INV-INSTANCE-1** — Un seul moteur par vault (`__main__.prendre_verrou`). Au démarrage, avant tout, le processus prend un verrou système exclusif (`flock` ; `msvcrt.locking` sous Windows) sur `<cache utilisateur>/goldenbrain/verrous/<empreinte du chemin résolu du vault>.lock` et y écrit `{pid, port, vault, depuis}`. Verrou déjà tenu : sortie avec un message en français (PID, port, date, comment arrêter l'instance), sans rien lancer. Le système rend le verrou à la mort du processus, même brutale : aucun verrou périmé, aucun PID à vérifier. La clé est le vault, pas le dossier de données : un worktree qui pointe le vrai vault est refusé, un vault temporaire (essais, `tmp_path`) a son propre verrou et ne gêne personne.
- **INV-MAJ-1** — La mise à jour avance le checkout en avance rapide seulement (`git merge --ff-only <distant>/<branche>`) : jamais de fusion, de réécriture d'historique, de `stash`. Refus (`mise_a_jour.Refus`, 409 dans l'API, message lisible, rien n'est changé) : modifications locales de fichiers suivis (liste des fichiers), branche courante différente de la branche de diffusion, historique divergent. Dépôt déjà à jour ou seulement en avance : rien à faire. Les fichiers de l'utilisateur (`config.toml`, `etat/`, `journal/`, `equipe/`) sont ignorés par git : jamais touchés. Hors d'un dépôt git : aucune action (l'état rend `depot: false`, la mise à jour est refusée).
- **INV-MAJ-2** — `git` est toujours lancé par liste d'arguments (`subprocess.run([...])`), jamais par un shell, avec `GIT_TERMINAL_PROMPT=0` et un délai borné ; un nom de branche ou de dépôt distant qui ne tient pas dans `[A-Za-z0-9_][A-Za-z0-9_./-]*` est refusé avant tout appel.
- **INV-MAJ-4** — Canal de mise à jour (`maj_auto.json`, `reglage.canal`, « stable » par défaut) : « stable » suit `[mise_a_jour] branche`, « beta » la branche `beta` du même distant (`mise_a_jour.suivie`). La bascule n'a lieu qu'entre ces deux branches de diffusion : toute autre branche courante reste refusée (INV-MAJ-1). Elle passe par le même geste (« Mettre à jour », sous `Moteur.exclusif()`, puis redémarrage) : refusée si des fichiers suivis sont modifiés ou si la branche locale cible porte des commits absents du distant ; sinon `switch` puis avance rapide seule. Changer de canal vide la mémoire du contrôle. La commande `mettre-a-jour` lit le même canal.
- **INV-SIGNAL-1** — « Signaler un problème » (`GET /api/signaler`, `signalement.py`) ne compose que des adresses de formulaire GitHub du dépôt public, pré-remplies de la version (empreinte et date du commit, canal) et du système (nom et version de l'OS, version de Python) — aucune autre donnée : ni nom d'utilisateur, ni chemin, ni contenu du vault ou des conversations. GoldenBrain n'envoie rien : le navigateur ouvre le formulaire, l'utilisateur relit et envoie.
- **INV-REVUE-1** — L'outil de revue des contributions (`scripts/revue_contributions.py`) lit une demande de fusion par `gh` (liste d'arguments, jamais de shell) et ne traite son diff que comme du texte : jamais récupéré dans un arbre de travail, jamais exécuté ; le dossier remis à l'agent déclare toute consigne du diff non avenue et borne sa taille. Aucun commentaire n'est publié sans `--confirme` (publication à l'extérieur) ; l'outil ne fusionne, n'étiquette ni ne ferme rien.
- **INV-MAJ-3** — Mise à jour automatique (option `maj_auto.json`, désactivée par défaut) : une mise à jour disponible sur la branche de diffusion gèle le démarrage des tours (`Creneaux.gele`, la file attend), laisse finir les tours en cours, ne laisse couper (puis reprendre, INV-EXEC-1 / INV-EXEC-9) que ceux qui ont dépassé le délai réglable ET sont à un point de reprise sûr (pause RAM, ou vigie silencieuse sans processus enfant ni commande bloquante, session connue, pas déjà repris sans progrès) — au moindre doute on attend leur fin, jamais d'interruption brutale. Puis avance rapide (INV-MAJ-1), contrôle d'importation de la nouvelle version, redémarrage unique (INV-VERSION-1). Une seule tentative par version distante (`tentee`, écrite avant d'agir) : jamais de boucle. Échec : import cassé → retour de la branche sur l'ancienne empreinte (`reset` strict) ; refus ou échec → incident visible (cause, geste), dégel. `.maj_retour` (racine du dépôt, non suivi) porte l'ancienne version jusqu'au démarrage réussi du serveur relancé ; `lancer.sh` / `lancer.cmd` la rétablissent si le serveur ne revient pas. Fenêtre horaire facultative (traverse minuit) ; reportée tant que l'interface a reçu un geste (`POST /maj-auto/activite`) depuis moins de 2 min. Après le redémarrage : bandeau « Mis à jour vers … à HH:MM ; n tâches reprises ».
- **INV-NOUV-1** — Journal des nouveautés (`nouveautes.py`) : une entrée vient d'une ligne `Nouveauté: <phrase grand public>` d'un message d'enregistrement, à défaut du titre d'un enregistrement (hors fusion) qui change `docs/GUIDE.md` (évolution visible, INV-GUIDE-1) ; les renvois internes entre parenthèses (`INV-*`, `WCAG`, `lot`) sont retirés ; aucune entrée portant un motif de `.sensible` n'est retenue (INV-PUB-1). `CHANGELOG.md` n'est jamais écrit à la main : la CI le produit à chaque version publique (`scripts/nouveautes.py journal`, version datée `AAAA.MM.JJ`, suffixe `.2`… le même jour), la section la plus récente en tête. L'avis « Quoi de neuf » (`GET /api/mise-a-jour`, champ `nouveautes`) montre les versions du journal distant absentes du journal local, à défaut les entrées de `HEAD..<distant>/<branche>` ; au plus 40 entrées ; une erreur n'y fait jamais tomber l'avis de mise à jour.

- **INV-VERSION-2** — `POST /redemarrer` est tracé et bridé : chaque appel (accepté ou refusé) journalise `par` (champ facultatif du corps, 80 caractères), `User-Agent`, `X-Orchestrateur`, adresse du client, `force`, l'horodatage et l'âge du serveur ; sans `force`, il est refusé en 429 (message lisible) tant que le serveur a moins de 60 s ; `GET /etat` porte `version.redemarrages`, le nombre de demandes acceptées depuis le lancement. `force` lève la garde de 60 s comme celle des tours.

- **INV-VERSION-3** — Un redémarrage refusé parce que des tours tournent peut être différé : `POST /api/redemarrer-differe` arme une tâche du serveur qui sonde `moteur.occupe()` (2 s) et, dès qu'aucun tour ne tourne ni n'attend, demande le redémarrage normal d'INV-VERSION-1 (sortie 3) ; `DELETE` l'annule ; `GET /etat` porte `version.differe` (booléen). L'armement n'est pas persisté : il disparaît avec le processus qu'il fait redémarrer. Il s'agit du serveur GoldenBrain, jamais de la machine ; l'interface le dit (« Redémarrer GoldenBrain dès que les tours sont finis »).

### Installation « un clic »
- **INV-PAQUET-1** — La graine ne remplace jamais une copie existante (`installation/goldenbrain.sh`, `installation/GoldenBrain.cmd`, `installation/installer.sh`, `scripts/construction.py`). Les paquets (`.deb`, installateur Windows, `GoldenBrain.app`) livrent l'application en lecture seule (« graine » : copie git sur la branche de diffusion, `origin` = dépôt public) ; le premier lancement la recopie dans le dossier de données de l'utilisateur (`~/.local/share/goldenbrain/app`, `~/Library/Application Support/GoldenBrain/app`, `%LOCALAPPDATA%\GoldenBrain\app`), seule copie que la mise à jour avance (INV-MAJ-1). Une copie présente n'est jamais écrasée, ni par un lancement, ni par une réinstallation, ni par la désinstallation, qui la laisse en place. `python.local` y est réécrit à chaque lancement (le Python embarqué peut changer de place).
- **INV-PAQUET-2** — Tout composant téléchargé pour construire ou installer (Python portable, MinGit, Inno Setup) est épinglé dans `installation/versions.txt` (clé, adresse, empreinte SHA-256) et vérifié avant usage ; une empreinte différente refuse le fichier (`construction.telecharger`, `installer.sh`). Les dépendances Python sont épinglées dans `installation/contraintes.txt`.

### Publication
- **INV-PUB-1** — Aucun fichier suivi par git (ni à suivre) ne contient de donnée sensible : adresse électronique, chemin de poste (`C:\Users\<nom>`, `/home/<nom>`), identifiant de session réel, jeton usuel (motifs génériques versionnés dans `scripts/check.py`), ni aucun motif personnel de `.sensible` (absent ou vide : la porte AVERTIT d'une ligne, sans échouer ; fichier local non suivi, une expression régulière par ligne ; gabarit vide `.sensible.exemple` ; lu dans l'arbre de travail, sinon dans le checkout principal). Exemples admis : `example.org`, `C:/Users/utilisateur`, identifiants `00000000-…`. Seule mention d'auteur admise : la ligne `GoldenBrain — Copyright <année> <auteur>` du fichier `NOTICE` (un nom seul : ni adresse, ni chiffre, ni chemin), soustraite aux seuls motifs personnels ; de même, l'adresse du dépôt public `github.com/Greal-dev/goldenbrain` (installation, mise à jour), jamais le nom du compte seul. Chemins par défaut génériques : `~` étendu au chargement de `vault.racine`, dossier des harnais = dossier personnel ; le Python des lanceurs `.cmd` vient de `python.local` (non suivi), sinon du PATH. La porte échoue sur tout manquement nouveau (`fichier:ligne : motif`) ; un manquement déjà recensé dans `docs/publication-connue.txt` (fichier<TAB>empreinte sha256 tronquée de la ligne, aucune donnée recopiée ; éléments connus de la tâche « Nettoyer le code avant ouverture ») est seulement AVERTI, jusqu'à son retrait — toute modification de la ligne le refait bloquant.

### Connecteur Microsoft 365 Copilot
- **INV-M365-1** — Le connecteur (`m365.py`) ne fait que lire : hors connexion OAuth, ses seuls appels sont ouvrir une conversation Work IQ (`POST <chat_url>/conversations`), y poser une question (`…/conversations/{id}/chat`) et extraire (`POST <retrieval_url>`, Retrieval API). Il n'écrit jamais dans Microsoft 365 et ne passe pas par le serveur GoldenBrain : `orch m365` appelle Microsoft directement, sous l'identité déléguée de l'utilisateur.
- **INV-M365-2** — Le jeton de rafraîchissement vit hors du dépôt (`[m365] jeton`, défaut `~/.goldenbrain/m365-jeton.bin` ; un chemin sous le dépôt est refusé), chiffré par DPAPI sous Windows (compte Windows courant), restreint au propriétaire ailleurs ; il n'est jamais affiché, journalisé ni repris dans un message d'erreur. Le renouvelé remplace l'ancien. Aucun secret d'application : client public, code d'appareil.
- **INV-M365-3** — Désactivé par défaut : sans `[m365] actif = true` et `client_id`, aucune requête ne part.

### API et interface
- **INV-CONTROLE-1** — Contrôle requis (`controle.py`, R2). Un projet le déclare par `controle: "<commande>"` dans son `contexte.md` (le conteneur le plus proche l'emporte, comme `depot:` ; guillemets obligatoires autour de `{python}`, qui vaut l'interpréteur du serveur) ; seule cette clé fait lancer une commande, sans shell. Quand l'agent déclare `terminee` (hors tâche permanente, INV-EXEC-7), le moteur lance le contrôle **une fois**, avant la conclusion du tour, dans le dossier de travail (INV-DEPOT-1) ou dans `controle_dossier:` du bloc `<fiche>` s'il est sous ce dossier (un arbre de travail du dépôt ; hors du dossier : échec). Il attend un poste libre puis le réserve (INV-POSTE-1, motif « contrôle requis ») et le rend à la fin ; `moteur.controle_duree_s` (défaut 1800) borne le contrôle (arbre de processus tué). Verdict `{tache, verdict: reussi|echoue, date, commande, dossier, reference, journal, cause}` persisté dans `<donnees>/etat/controles.json` (dernier par tâche), reflété dans la clé gérée `controle:` (« réussi le … · branche@commit ») ; sortie dans `journal/<date>/<id>-controle-HHMMSS.log`. `reference` = `branche@commit`, suffixée `+modifs:<empreinte>` si l'arbre n'est pas propre, prise après le contrôle ; vide hors dépôt git. « Terminée » (`fait`) exige le succès ; un échec (commande en erreur, introuvable, délai, dossier refusé, aucun dossier de travail) pose `retour-humain`, écrit une ligne `orch_echec` (motif `controle`) au journal du tour et ne relance jamais l'agent. `GET /taches/{id}` rend `controle: {commande, declare_par, verdict|null}` — `null` sans contrôle déclaré (aucune preuve affichée) ; `verdict.perime` vaut vrai si la référence actuelle du dossier diffère, `null` si l'état n'est pas référencé. Le succès ne pose jamais `cloture`. SSE `controle {tache, verdict: en_cours|reussi|echoue}`.
- **INV-POSTE-1** — Réservation du poste (`poste.py`, routes `api_poste.py`). Une seule réservation à la fois, `{tache, motif, depuis, expire}`, persistée dans `<donnees>/etat/poste.json` (survit au redémarrage ; fichier illisible = poste libre). Elle est prise par une tâche (`orch poste reserver "<motif>"`, `POST /poste/reserver`) ; une autre tâche la demandant reçoit 409 nommé, le titulaire la renouvelle. Elle est rendue par le titulaire (`orch poste liberer`, `POST /poste/liberer {tache}` ; un autre titulaire : 409), d'office à la fin de chaque tour du titulaire (réussi, en échec ou interrompu), par un geste humain (`POST /poste/liberer {}`), ou par expiration après `moteur.poste_delai_min` minutes (défaut 120), contrôlée à chaque lecture. Tant qu'elle tient, le tour d'une tâche dont le frontmatter porte `epreuves: lourdes` (lu à chaque tour, valeur sans casse) ne démarre pas : son message reste en file, sans tenir de créneau `simultanes_max`, la tâche reste `en_file` et `GET /taches/{id}` rend `attente_poste: {par, titre, motif}` (« En attente du poste (réservé par <titre>) ») ; la file reprend dès la libération ou l'expiration (scrutation 1 s). Une tâche sans la marque, et le titulaire lui-même, ne sont jamais retenus ; un tour déjà commencé n'est jamais interrompu. `GET /etat` porte `poste` (réservation ou `null`) ; événement SSE `poste` à chaque prise ou restitution ; bandeau discret « Poste réservé » avec bouton « Libérer ». **File d'attente** : une demande refusée (`Poste.demander`, ou 409 de `POST /poste/reserver`) inscrit la tâche dans une file ordonnée, premier arrivé, tenue en mémoire (perdue au redémarrage). Le poste libre n'est donné qu'à la tête de file ; un attendant qui ne redemande pas pendant `FILE_TTL_S` (15 s) en sort, de même que celui dont le tour finit (`rendre`) ou qui annule (`POST /poste/annuler {tache}`). `POST /poste/reserver {attendre: true}` rend 200 `{poste: null, rang, titulaire}` au lieu de 409 ; `orch poste reserver` redemande toutes les 2 s jusqu'à obtenir le poste (stderr : « en attente du poste (rang n) ») ou jusqu'à `--attente <min>` (défaut 30, `ORCH_POSTE_ATTENTE_MIN` ; 0 = aussitôt) : il quitte alors la file et sort en code 1. Le contrôle requis (INV-CONTROLE-1) y prend aussi son rang. `GET /poste` porte `file`, `GET /etat` porte `poste.file` (bandeau : « File : 1. <tâche>, … »), `GET /taches/{id}` porte `rang_poste` (« En attente du poste (rang n) »). L'attente d'une tâche `epreuves: lourdes` (ci-dessus) ne passe pas par la file : elle ne réserve rien. Abandon : une réservation non renouvelée depuis 20 min (`Poste.ABANDON_S`) tombe d'office quand aucune porte d'interface ne tourne (verrou `check_ui`, `porte_vivante`) ; elle ne tient plus le poste jusqu'au délai complet.
- **INV-PORTE-1** — Reçu de porte (`scripts/porte.py`). La porte complète (`check.py` puis `check_ui.py`) lancée par `porte.py` écrit, seulement si elle est verte sur un arbre git propre (inchangé avant/après), un reçu `<arbre>.json` dans le dossier d'état local (`GOLDENBRAIN_ETAT_LOCAL`, sinon `$XDG_STATE_HOME/goldenbrain`) : empreinte de l'arbre, commit, date, résumé des tests, présence des motifs personnels `.sensible` (INV-PUB-1), signature HMAC-SHA256 par une clé locale (0600). `porte.py verifier [--arbre X]` rend 0 si le reçu existe, est authentique, porte l'arbre demandé, a moins de 24 h et a contrôlé INV-PUB-1. La CI locale s'en sert pour ne pas rejouer une suite que l'intégration vient de valider sur l'arbre exact de `origin/mvp`, et garde un passage complet au moins une fois par jour. Limite : la signature arrête l'affirmation et la copie, pas un processus qui lirait la clé avec les droits de l'utilisateur.
- **INV-API-1** — Écoute sur `127.0.0.1` (plus, sur option, l'adresse `executeurs.ecoute` gardée par INV-DISTANT-1). Toute requête dont l'en-tête `Host` n'est pas `127.0.0.1:<port>`, `localhost:<port>` ou `<ecoute>:<port>` est refusée (403). Toute requête non-GET exige l'en-tête `X-Orchestrateur: 1` (403 sinon). Toute réponse porte `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'self'; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'` et `X-Content-Type-Options: nosniff`. Seule exception : `/api/vault/fichier` répond `X-Frame-Options: SAMEORIGIN` et `frame-ancestors 'self'`, pour que l'interface incorpore un PDF.
- **INV-INTERFACE-1** — Une famille débrayée (voir Mode simple et réglages) ne lance aucun tour : pas de propagation (`liens`), pas de revue de persona (`equipe` : la tâche terminée attend le geste humain), pas de revue de jardinage, pas d'avis (`conseil` répond `indisponible`), le harnais demandé est ignoré (`moteurs`). Ses routes répondent 409 « fonction « x » désactivée (Réglages) » : écritures seulement pour `equipe`, `liens`, `transformations` (lire reste possible) ; toutes les méthodes pour `alignement` (`/api/alignement*`), `jardinage` (`/api/jardinage`), `notes` (`/api/vault/*`). Garde centrale : `api_interface.famille_fermee`, dans le middleware. Exception : l'assistant choisi aux premiers pas, à la création d'une tâche seulement (INV-PREMIERS-PAS-2).
- **INV-INTERFACE-2** — La persistance des réglages ne touche que la section réglée (`[interface]`, ou `[telegram]` pour le connecteur) de `config.toml` : le reste du fichier est restitué octet pour octet (fins de ligne comprises), écriture atomique ; le disque est écrit avant la mémoire.
- **INV-INTERFACE-3** — Une proposition d'agent hors gestes d'office (INV-PROP-1) est traitée selon la politique `propositions` : `ignorer` ne mémorise rien et répond `{"etat": "ignoree"}` ; `accepter` l'exécute aussitôt par le geste humain correspondant (INV-EXEC-5 : même chemin que `/accepter`) ; `montrer` la laisse en attente.
- **INV-AFFICHAGE-1** — Affichage par défaut « sobre éditorial » : jetons dans `web/style.css`, surcouche `web/affichage.css` chargée en dernier par `web/styles.liste`. L'accent (vermillon) est une seule variable `--accent` dont les fonds (`--accent-fond`, `--sel`, `--info-fond`) dérivent par `color-mix` ; il marque (sélection, focus, lien, pastille pressée) et n'habille jamais une action : le bouton d'action positive est à l'encre (`--action`), le rouge reste à `--danger`. Barre haute sombre en clair comme en sombre, ses menus déroulants au thème de la page. Surcouche ≤ 15 Ko, sans flou, animation ni ressource distante ; contrastes AA mesurés en clair et en sombre (`tests/test_affichage.py`, `tests/ui/scenario_affichage.py`). Plus de direction d'essai `?theme=`.
- **INV-REGLAGES-1** — Page Réglages (`web/reglages.js`) : un événement `etat` (émis à chaque ligne d'un agent qui parle) ne redessine que ce qui en dépend — moteurs par rôle, version, résumés des groupes ; les sections spécialisées se rechargent par leurs propres événements et annoncent leur résumé par l'événement `resume`. La page entière ne se reconstruit qu'à l'ouverture, à l'ancre `#reglages/<section>` ou au changement de mode ou de famille, et garde alors groupes ouverts (`localStorage` `orch.reglages.ouverts`), recherche, champ en cours de saisie et focus. Aucun réglage ne change de comportement : seule la présentation est regroupée.
- **INV-CONSOLE-1** — La console en terminal (`orch console`) n'a aucun chemin d'envoi propre : une ligne saisie part par `POST /taches/{id}/messages` sans `de` ni `sauts`, comme le chat (même file, même tour, message de l'utilisateur) ; `/arret` passe par `POST /taches/{id}/arret`. Fermer la vue (`/quitter`, Ctrl+C, fermeture de l'onglet) ne touche jamais au tour : le serveur le suit seul.
- **INV-GUIDE-1** — Le guide d'utilisation est un seul fichier, `docs/GUIDE.md`, lu tel quel par l'interface (écran « Guide », bouton « ? » de l'en-tête et « ? » contextuel des écrans), par l'API (`GET /api/guide`, texte brut `text/markdown`) et par les agents (`orch guide`, lu sur place sans serveur). Le registre `guide.SECTIONS` (ancre → titre exact, titres `##` ou `###`) liste chaque écran ou réglage visible ; `scripts/check.py` échoue si un titre du registre manque au guide, si une ancre ne vaut pas `ancre(titre)` (minuscules, sans accents, tirets ; même calcul dans `web/guide.js`) ni l'ancre fixée au bout du titre en `{#ancre}` (titre reformulé, ancre gardée), ou si la ligne « Mis à jour le AAAA-MM-JJ. » manque. Toute évolution visible met le guide (section et date) à jour dans le même commit ; un écran nouveau s'inscrit au registre.
- **INV-LANGUE-1** — Tout texte montré à l'utilisateur (libellé, bouton, info-bulle, message d'erreur, aide, message du serveur affiché) passe par une clé des dictionnaires `web/langues/{fr,en,de,es}.json` (`fr` = source) : `t()` / `tn()` de `web/langues.js` côté interface, `langues.t()` côté serveur, `data-t*` dans le HTML statique. Les quatre dictionnaires ont exactement les mêmes clés et les mêmes paramètres `{x}` ; toute clé citée existe ; aucun libellé visible n'est codé en dur dans `web/` hors `scripts/langues_exceptions.txt` (exceptions motivées) — `scripts/check.py` le contrôle (`scripts/dictionnaires.py`). Identifiants, clés de configuration, statuts du vault et noms de commandes ne se traduisent jamais. La langue vit dans `[interface] langue` (détectée depuis le navigateur au premier lancement) ; l'interface ne charge que le dictionnaire de cette langue. Les consignes d'agent (tâche et assistant Telegram) demandent de répondre dans la langue de l'utilisateur. Chaque guide traduit (`docs/GUIDE.<langue>.md`) porte toutes les ancres du registre en `{#ancre}` ; `GET /api/guide?langue=` le sert, repli sur le français. Vocabulaire grand public et règle de stabilité des clés : `docs/VOCABULAIRE.md`.
- **INV-WEB-1** — Dans l'interface, tout texte venu de l'API est échappé avant d'être balisé ; `innerHTML` n'est alimenté que par le rendu Markdown maison (`web/md.js`). Pour une note : aucun HTML brut interprété ; URL d'images et de liens limitées à `http(s)` et à `/api/vault/fichier`.
- **INV-COMPAGNON-1** — Instantané du compagnon mobile (`compagnon.py`, `api_compagnon.py`). Lecture seule : l'instantané n'écrit rien dans le vault ; l'écran n'ajoute qu'UN geste (jalon 2), valider ou renvoyer une tâche à valider par les routes existantes `/taches/{id}/valider|renvoyer`, en ligne et après confirmation, jamais hors ligne ni depuis le stockage local. La projection est une liste blanche posée côté serveur (`CHAMPS_NOEUD`, question tronquée à 160 caractères, décisions de tâche seulement ; un résumé du résultat de 140 caractères (`resume`) n'y entre que si `[distant] resume = true`, défaut faux, et n'est jamais écrit dans le stockage local INV-PWA-2) : ni corps de fiche, ni conversation, ni note, ni chemin, ni jeton n'y figurent ; arbre borné (`NOEUDS_MAX`, `tronque`), décisions bornées. Validée par ETag (empreinte du contenu, sans horodatage) : `If-None-Match` identique → 304. La route passe par la garde d'appareil (INV-DISTANT-6) comme toute route ; réponse `Cache-Control: no-store`.
- **INV-PWA-2** — Stockage local du compagnon (`web/compagnon.js`), seule exception à l'absence de donnée d'API hors ligne d'INV-PWA-1 (qui reste vrai du service worker). Doublement optionnel : `[distant] hors_ligne = true` sur le poste (défaut faux), ET case cochée sur l'appareil (`localStorage`). Seul l'instantané INV-COMPAGNON-1 s'y trouve (IndexedDB `gb-compagnon`), jamais le flux des conversations ni une autre route. Durée de vie `ttl_s` (7 jours) depuis `genere` ; effacé sur toute réponse 401 (appareil révoqué), quand le serveur retire la permission, quand la case est décochée, ou par « Effacer les données de cet appareil ». Limite assumée : hors ligne, une révocation ne peut pas purger ; d'où la liste blanche minimale et le TTL court. Test : `tests/test_compagnon.py`, `ui/scenario_compagnon.py`.
- **INV-COMPAGNON-2** — « Travail en cours » et chat par tâche du compagnon (`web/travail.js`, `web/epingles.js`). L'épinglage est un réglage de l'appareil (`localStorage`, identifiants de tâche seulement) : le serveur n'en sait rien et le vault n'est jamais écrit. La liste se lit dans l'instantané INV-COMPAGNON-1 ; le chat n'emploie que des routes existantes — `GET /taches/{id}/conversation` et `POST /taches/{id}/messages` (message humain, comme `orch dire`) — donc toute la garde d'appareil INV-DISTANT-6/7 ; aucune route nouvelle, aucun geste de statut ni de structure (valider/renvoyer restent ceux de l'Accueil, avec confirmation). Hors ligne : la liste s'affiche en aperçu, le chat est inactif. Les erreurs d'envoi s'affichent dans la vue.
- **INV-PWA-1** — Le service worker de l'application installable (`web/sw.js`) ne met en cache que des fichiers statiques de même origine, en GET ; jamais `/api/` ni le flux d'événements. Réseau d'abord : le cache ne sert que hors ligne, si bien qu'une nouvelle version s'applique au premier chargement en ligne. Test : `ui/scenario_telephone.py`.

## Modèle

- **Tâche** : un fichier `.md` d'un dossier `taches/` couvert par les motifs `vault.taches` (jusqu'à cinq niveaux sous `Casquettes` et `Projets`), hors `vault.exclure`. Identifiant : le nom du fichier sans `.md` ; entre homonymes, le second reçoit le suffixe `~<4 hex du chemin>`. Titre : premier titre `# ` du corps, à défaut `titre`/`title` du frontmatter, à défaut l'identifiant.
- **Conteneur** : le dossier parent d'un dossier `taches/`. Identifiant : son chemin relatif au vault, séparateurs `/` (ex. `Projets/C1-ORION-V2`). Attributs lus dans son `contexte.md` s'il existe : `casquette`, `parent`, `nom`. Seul un conteneur doté d'un `contexte.md` se range (gestes d'arbre, réduction, proposition `operation`).
- **Casquette** : `^(C\d+|META)` appliqué à la valeur du `contexte.md` du conteneur, à défaut à la clé `casquette` des tâches ; à défaut `?`.
- **Clés gérées** du frontmatter : celles d'INV-VAULT-1. `parent:` d'une tâche = identifiant de sa mère (wikilink `[[…]]` toléré). `parent:` d'un `contexte.md` = chemin de rattachement (voir Arbre).
- **Bloc fiche**, écrit par le moteur en fin de fichier s'il n'existe pas :

```markdown
<!-- orchestrateur:debut -->
## Fiche
- **Fait** : …
- **Résultat** : …
- **Essai** : …
- **Situation** : …
- **Reste à faire** : …
- **Prochain pas** : …

### Sous-tâches
- [x] …
- [ ] …
<!-- orchestrateur:fin -->
```

- **Bloc rendu par l'agent** à la fin de chaque tour (exigé par la consigne). Analyse tolérante (clés absentes = chaîne vide) ; seul le dernier bloc compte. Bloc absent : la fiche existante est gardée, `situation` reçoit les 500 premiers caractères du message final, et `tour_fin` porte `fiche_absente: true`.
- **Résultat et essai** (R1) : `resultat` = quoi et où (chemin, branche et commit, adresse) ; `essai` = comment l'utilisateur l'essaie (commande, adresse ou scénario, résultat attendu). Le moteur ne les contrôle pas : une valeur vide s'affiche « non indiqué » (fiche ouverte, liste « À moi » pour une tâche à valider), jamais comme un résultat. « Renvoyer » compose un message « attendu / observé » envoyé dans la même conversation (même session, même identifiant de tâche).

```
<fiche>
statut: en_cours | en_attente | terminee
fait: …
resultat: …
essai: …
controle_dossier: …   (facultatif, INV-CONTROLE-1 : arbre de travail à contrôler, sous le dossier de travail)
situation: …
reste: …
prochain_pas: …
sous_taches:
- [x] …
- [ ] …
</fiche>
```

## Statuts

| Libellé affiché | Valeur dans le vault | Qui l'écrit |
|---|---|---|
| Non commencée | `a-faire` (et `confier-agent`) | création |
| En cours | `en-cours` | moteur : début de tour ; fin de tour si l'agent déclare `en_cours` |
| En attente | `retour-humain` (réglable : `[vault] statut_retour`, INV-STATUT-1) | moteur : déclaration `en_attente`, déclaration absente ou invalide, tour interrompu ; revues au-delà de `boucles_max` |
| Bloquée | `bloque` | moteur : échec technique du tour (harnais, durée maximale, tour sans résultat) |
| Terminée | `fait` | moteur, sur déclaration `terminee` (sauf INV-EXEC-7) et, si le projet déclare un contrôle, après son succès (INV-CONTROLE-1 ; échec → `retour-humain`) |
| Validée | `cloture` | le validateur seulement (humain, persona selon `[validation]`, ou validation automatique du périmètre, INV-VALID-2) |
| Abandonnée | `abandonne` | humain seulement |

- Un humain peut poser tout statut connu (`POST /taches/{id}/statut`). En fin de tour, le moteur n'écrit le statut que si la tâche est encore `en-cours` : un statut posé par un humain pendant le tour est gardé.
- Si la clé `tags` contient l'ancien statut, il y est remplacé par le nouveau.
- **INV-LIGNES-1** — Un travail court (sans livrable ni branche propres, même objectif que sa tâche) est une LIGNE : `- [x] texte · AAAA-MM-JJ · Moi|IA[ · lien]` dans un bloc géré `<!-- orchestrateur:lignes -->` … `<!-- orchestrateur:lignes-fin -->` du corps de la tâche, distinct du bloc fiche (la réécriture de la fiche par un agent ne l'efface pas). L'auteur est posé par le serveur (en-tête `X-Orch-Tache` : IA, sinon Moi), jamais lu du corps ; un agent peut ajouter des lignes à une tâche « Moi » (`executant.PERMIS_AGENT`). `lignes.promouvoir` crée une tâche fille et retire la ligne ; `lignes.en_ligne` clôt la tâche (`cloture`, jamais supprimée) et consigne « Devenue ligne » ; refus si cible descendante, enfants ouverts ou tour en cours. Le frontmatter n'est jamais reformaté (INV-VAULT-1). Une proposition `tache` émise par un agent (`de` = tâche existante, hors jardinier et scan) n'est pas déposée : elle devient une ligne IA de la tâche émettrice (`etat: ligne`) — une suite d'audit ou un reste à faire est une ligne, pas une tâche à trancher.
- **INV-LECTEUR-1** — Lecteur de fichiers (`lecteur.py`, `api_lecteur.py`, `web/lecteur.js`). Un fichier n'est lu que sous une racine : vault, dossiers de travail des tâches, dossiers de `[lecteur] dossiers`, ou livrable déclaré (exact) ; chemin sans `..`, lien symbolique résolu avant le contrôle, hors racines = 403, jamais servi. Registre extension → genre/mode en une table (`[lecteur] lecteur|application` le surcharge) ; extension inconnue → application. Le texte se lit par pages de 256 Kio coupées sur fin de ligne. HTML/SVG : `<iframe sandbox>` sans script ni origine + CSP `sandbox; default-src 'none'`, ressources externes seulement si `externe=true` par fichier ; PDF et images servis par `/api/lecteur/brut` (nosniff, no-store). Ouvrir dans l'application ou afficher le dossier : poste seul (refus d'un appareil distant et d'un jeton d'agent, `POST /api/lecteur/ouvrir|dossier|reglages`) ; un script ou binaire ouvre son dossier, jamais exécuté. Depuis un appareil distant : vault et livrables seulement.
- **INV-LIVRABLES-1** — Les livrables d'une tâche sont une liste dédoublonnée d'artefacts (`note`, `fichier`, `url`, `publie`, `branche`, `commit`). Déclarés dans le bloc géré `<!-- orchestrateur:livrables -->` de la fiche (même format de ligne que les lignes ; sans lien = attendu), relevés d'office des traces et des lignes à document (aucune migration), fusionnés par clé normalisée (le déclaré prime). Cibles validées à l'entrée (pas de `..`, octet nul, schéma autre que http(s)). Depuis un appareil distant, aucun fichier hors vault n'est lu (`existe` = inconnu) ; l'ouverture d'un fichier passe par le serveur sur un élément de la liste recalculée, dans les bornes de INV-RESULTAT-1, route réservée au poste. En-tête : une seule pastille « Livrables (n) » (INV-DETAIL-1). Module `livrables.py`, routes `api_livrables.py`, `orch livrable`.
- **INV-PLAFOND-1** — Au plus `[rangement] plafond` (défaut 10, 2 à 100) tâches ouvertes directement sous un même parent. Au-delà, `POST /api/taches` répond 409 `{detail, rangement}` (propositions : `ligne`, `sous_groupe`, `nouveau_groupe`) sauf `groupe`, ou `forcer: true` pour l'interface (dérogation humaine) ; pour un agent (en-tête `X-Orch-Tache` ou `de`), `forcer` (`--nouvelle`) ne lève que la proximité (INV-RAPPROCHEMENT-1) et la dérogation est `hors_rangement: true` (`--hors-rangement`) ; `orch creer` rend les gestes en commandes. Le jardinier signale les parents en excès (`rangement.excedents`). Rangement proposé, jamais imposé ; l'arrivée n'est pas un parent.
- **INV-NATURE-1** — Nature de travail d'une tâche : `developpement`, `operation` ou `pilotage`, clé de frontmatter `genre` (la clé `nature` est déjà prise : permanente, routine). Absente, elle est déduite du titre et de la description par `rangement.deduire` (indices lexicaux, vide si égalité) ; posée, elle l'emporte. Avec `[rangement] natures_separees` (défaut vrai), une création qui mêlerait les natures sous un parent de ≥ 2 enfants d'une seule autre nature reçoit le 409 de rangement. Filtre et pastille dans l'arbre.
- **INV-APPRENDRE-1** — Mode « Apprendre » (`apprendre.py`, routes `api_apprendre.py`, `[apprendre] actif`, défaut faux). Actif, `Moteur._consigne` ajoute la consigne `serveur.apprendre.consigne` des dictionnaires, dans la langue réglée (INV-LANGUE-1) : explications en une ou deux phrases dans des encadrés Markdown `> [!apprendre]` (mis en valeur par le rendu des conversations) et une ligne `retenir:` (trois points séparés par « ; ») dans le bloc `<fiche>`, conservée dans le champ facultatif `retenir` de la fiche (hors `fiches.CHAMPS` : seul `rendre_bloc` l'écrit, et seulement s'il est renseigné). Inactif, la consigne est strictement celle d'avant. Une tâche pose `apprendre: oui|non` dans son frontmatter (clé gérée) ; elle l'emporte sur le réglage général ; l'effet vaut au tour suivant (harnais sans consigne native : à la prochaine conversation neuve). Les libellés d’écran sont aux dictionnaires (préfixe `apprendre.`).
- **INV-STATUT-1** — Le statut « En attente » (la main revient à l'humain : « À moi », Décisions) porte le nom réglé par `[vault] statut_retour` (défaut `retour-humain`) ; aucun module, route ni écran ne le code en dur : le serveur lit `Vault.retour` (et `Vault.statut_declare` pour la déclaration `en_attente`), l'interface le reçoit de `GET /api/interface` (`statut_retour`) et le dessine avec la classe générique `st-retour`. Le nom doit être en minuscules à tirets et distinct des statuts fixes, sinon la configuration est refusée au démarrage ; il est toujours compté ouvert. Un autre nom présent dans le vault (par exemple l'ancien nom d'avant le réglage) n'est qu'un statut inconnu : ni ouvert, ni « À moi », ni décision, et `poser_statut` le refuse. Un vault qui garde un ancien nom le déclare dans `config.toml`.
- **Ouverte** : statut dans `vault.statuts_ouverts` (`a-faire`, `en-cours`, `confier-agent`, `bloque`, plus le statut de retour, toujours ajouté) ou **à valider** (`fait` avec une clé `session`).
- **État d'exécution** (mémoire du moteur, hors vault) : `inactif`, `en_file`, `en_cours`, `interrompu`, `en_pause` (réveil sur quota programmé, INV-EXEC-9).

## Arbre

**Forme** : casquette → nœuds nommés de profondeur libre (opérations et conteneurs) → tâches → tâches enfants. Identifiants dans `GET /arbre` : `casquette:<C>` ; opération `operation:<C>/<chemin complet>` (ex. `operation:C1/Atelier > ORION`) ; conteneur : son identifiant ; tâche : son identifiant. Deux opérations qui ne diffèrent que par la casse forment un seul nœud.

**Place d'un conteneur — le dossier fait foi (INV-ARBRE-2)** :
- SANS `parent:` : son plus proche dossier ancêtre qui est un conteneur (hors dossiers de casquette et conteneur d'arrivée) ; à défaut, sa casquette. Les dossiers intermédiaires entre ce conteneur ancêtre (ou un dossier `Casquettes/<C>-…`, ou `Projets`) et lui sont des **opérations**, avec ou sans `contexte.md`. Ex. `Casquettes/C1-Pro/Atelier/C1-ORION` → C1 › Atelier › C1-ORION ; `Projets/A/X` → opération A. Un dossier de casquette et `_meta` ne sont jamais parents implicites : un projet né dans le conteneur d'arrivée apparaît directement sous sa casquette.
- AVEC `parent:` : **rattachement logique de repli** (dossier pas encore aligné, ou non déplaçable). `parent:` vaut un chemin de segments séparés par ` > ` (`parent: Atelier > ORION`) ; `parent: ""` = directement sous la casquette ; wikilinks tolérés par segment. Un segment égal (sans casse) au nom de dossier d'un conteneur de la même casquette désigne ce conteneur ; sinon c'est une opération. Le dernier segment conteneur fixe la place ; un conteneur dont `parent:` cite son propre nom de dossier (sous-aires `Asso-*`) est rendu comme le nœud lui-même. Un rattachement qui contredit le dossier est un écart d'alignement et le nœud porte `"logique": true`.
- Un cycle entre conteneurs est coupé à la lecture : le conteneur fautif est rendu sous sa casquette, et journalisé.

**Dossier d'un nœud** (`Aligneur.dossier`) : conteneur = son dossier ; opération = le dossier où elle a été lue (409 si plusieurs), sinon dossier du parent + son nom ; casquette = son unique dossier de `vault.casquettes` dont le nom commence par `<C>-`, à défaut `Projets`.

**Gestes sur une tâche** (humains, `POST /arbre/deplacer` et `/arbre/monter`, `?toutes=0|1`) :
- tâche sur tâche : devient son enfant (`parent`, changement de conteneur si besoin) ; tâche sur conteneur : déplacée dans ce conteneur, sans mère ; sur opération ou casquette : 409 (« une tâche vit dans un projet ») ;
- monter : `parent` = la mère de sa mère, ou retiré (elle reste dans son conteneur) ; tâche sans mère : 409 ;
- 409 sur soi-même ou un descendant. Un projet ou une opération envoyé à ces routes : 409 (« demander d'abord le plan »).

**Gestes sur un projet ou une opération** : `POST /arbre/plan {"noeud", "sous"?}` (absent = monter d'un niveau) rend un `Plan` d'alignement augmenté de `"fiches": [{"fichier", "cles": {clé: valeur|null}}]` (clés posées après le déplacement, chemins d'après), sans rien écrire ; l'application passe par `POST /alignement/appliquer` (INV-ALIGN-1, INV-ALIGN-2 ; commit de restauration « GoldenBrain : avant déplacement <date> »).
- Destination : sous un conteneur ou une opération, `<dossier de la cible>/<nom>` ; un projet sous une casquette rejoint `Projets/<nom>`, sauf s'il est déjà directement sous une casquette dans les dossiers (seule sa casquette change). Une opération déplace son dossier entier, notes comprises.
- Changement de casquette : `casquette` posée dans le `contexte.md` de chaque conteneur concerné et sur ses tâches.
- 409 : destination existante ; destination dans le dossier lui-même ; dossier protégé (INV-ALIGN-3 : rattachement logique à la place pour un projet) ; opération sans dossier ; descendant pas encore aligné (« aligne-le d'abord ») ; déjà sous cette cible ; nœud déposé sur une tâche ; casquette inconnue ; casquette non déplaçable.
- Après application : SSE `arbre`, index des notes périmé.

**Champs de nœud** : `Noeud = {"id","type","titre","ouvertes": int,"enfants": [Noeud],"deplacable","montable"}` ; tout nœud autre qu'une tâche ajoute `"logique": bool` ; une tâche ajoute `"statut","etat_execution","situation","maj","harnais","modele","a_valider","echeance","priorite","retard","liens": int`. `?toutes=1` inclut les tâches fermées.

## Liens

- Trois clés gérées, listes YAML en ligne d'identifiants sur UNE ligne : `alimente: [id-b, id-c]`, `prerequis: [id-a]`, `voir_aussi: [id-d]` ; clé retirée quand la liste est vide.
- `prerequis` est orienté et stocké côté tâche qui attend (`B: prerequis: [A]` = A doit être terminée avant que B démarre) ; « requis par » est calculé, jamais écrit. Blocage et ordre : INV-ORDO-1, INV-ORDO-2.
- `alimente` est orienté et stocké côté source ; « alimenté par » est calculé, jamais écrit. `voir_aussi` est symétrique : stocké d'un côté, affiché des deux.
- Un identifiant qui ne correspond plus à aucune tâche est ignoré à l'affichage, conservé dans le fichier. Déplacements et promotions ne touchent pas aux liens.
- Refus (409) : lien vers soi-même, doublon, `alimente` ou `prerequis` qui fermerait un cycle. Retrait d'un lien absent : 404 (pour `voir_aussi`, quel que soit le côté qui le stocke).
- Propagation : INV-LIEN-1.

## Moteur et harnais

**Tours** : un message soumis à une tâche entre dans sa file (INV-EXEC-2) ; au plus `moteur.simultanes_max` tours en même temps (sémaphore) ; `moteur.duree_max_s` borne un tour (0 = sans limite ; dépassement → `bloque`). Début de tour : statut `en-cours`, SSE `tour_debut`, journal ouvert par une ligne `{"type": "orch_message", "texte", "de", "harnais", "date"}`. Pendant le tour : session écrite au premier événement (INV-EXEC-3), SSE `tour_texte` / `tour_outil`. Fin : statut (voir Statuts), mandat éventuel conclu (Transformations), fiche réécrite, SSE `tour_fin` puis `arbre`, puis propagation (INV-LIEN-1) et revues si `fait` (Équipe). Toute sortie tue l'arbre de processus du tour.

**Occupation et demi-verrou** (`verrou.py`) : `occupation(id)`, `occupees()`, `occupees_sous(noeud)` (le nœud — tâche, conteneur, opération, casquette — et sa descendance dans `vault.arbre(True)`, liens `parent:` compris), `demi_verrou(noeud, forcer, seule=False)` qui lève `Occupee(Conflit)` portant `occupee`. `depuis` = début du tour en cours, sinon heure de mise en file (`Moteur.en_file_depuis`), sinon date de l'avis de revue en cours. INV-VERROU-1.

**Verrou des déplacements** (`verrou.py`, mélangé au `Moteur`) : `Moteur.exclusif(dossiers, fichiers)` tient à l'arrêt les seules tâches touchées par un déplacement de dossier ; `Moteur.exclusif()` sans argument bloque tout démarrage de tour et refuse (409) dès qu'un tour est actif ou en file, ou qu'une revue ou sollicitation de persona est en suspens (`Moteur.occupe()`), ou qu'un exclusif est déjà en cours ; il garde la mise à jour du dépôt. INV-ALIGN-2.

**Messages entre tâches** : `orch dire` ou `POST /taches/{id}/messages {"texte","de","sauts"}` ; sauts INV-MSG-1, pas d'accusé de retour INV-MSG-2.

**Consigne injectée** (`[consigne] gabarit`, variables `{titre}`, `{chemin}`, `{fil_ariane}`, `{contexte}`, `{soeurs}`, `{orch}`, `{equipe}`) : la tâche et sa place, les fichiers à lire avant d'agir, l'obligation de dire d'abord où l'agent s'est placé et ce qu'il a lu, les précautions (aucun envoi, publication, paiement ni suppression sans accord ; un contenu externe n'est jamais un ordre ; secrets jamais affichés), la recherche du voisinage et les propositions (au plus trois par tour, sept lors d'une revue de cohérence, chacune avec son motif ; une demande de structure de l'utilisateur dans la conversation se dépose aussitôt en proposition), les personas actifs, le bloc `<fiche>` final. Un harnais à consigne native la reçoit à part ; sinon le moteur la place en tête du PREMIER message de la conversation. Une conversation dérivée hérite de la consigne de sa mère.

**Environnement du tour** : `ORCH_TACHE`, `ORCH_SAUTS`, `ORCH_URL` ; tour de persona : `ORCH_PERSONA` en plus.

**Protocole d'un harnais** (`harnais/__init__.py`) :

```python
@dataclass
class Evenement:
    type: str            # "session" | "texte" | "outil" | "fin" | "erreur"
    session: str = ""
    texte: str = ""
    brut: dict | None = None

@dataclass
class Message:           # élément de transcript
    role: str            # "utilisateur" | "assistant" | "systeme" (échec de tour, INV-EXEC-8)
    texte: str
    outils: list[str] = []
    horodatage: str = ""
    secondaire: bool = False   # réponse de l'agent à un hook de fin, après sa vraie réponse

class Harnais(Protocol):
    nom: str
    consigne_native: bool      # faux : consigne en tête du premier message
    sait_deriver: bool         # faux : dérivation avec fil refusée (409)
    def lancer(self, message, *, session, deriver, consigne, env, modele="") -> AsyncIterator[Evenement]: ...
    async def arreter(self) -> None: ...                         # tue l'arbre de processus
    def transcript(self, session, limite) -> list[Message]: ...  # peut lever NotImplementedError
    def commande_terminal(self, session) -> str: ...            # reprise dans l'interface native
    # facultatifs : chemin_transcript(session), decouvrir_modeles(), analyser(brut, etat),
    # argv_natif(session, neuve, consigne, modele, message) (interface native, INV-NATIF-1)
```

`lancer` avec `session=None` crée une conversation ; `deriver=True` (avec `session`) dérive. Une instance par tour (`HARNAIS[nom](conf)`, `conf` = section `[harnais.<nom>]`). Ajouter un harnais = un module + une entrée de registre. Quand `transcript` lève `NotImplementedError`, `/conversation` reconstruit la conversation à partir des journaux (messages soumis + événements `texte`/`outil`).

**Adaptateurs** :
- `claude` : `claude -p --output-format stream-json --verbose`, prompt par stdin, consigne native par `--append-system-prompt`, `--resume <id>` (reprise ; absent = conversation neuve), `--fork-session` (dérivation), `--resume-session-at <uuid>` (reprise au point, INV-RETOUR-1), `--model`, lancé depuis `[harnais.claude] dossier`. Transcript : `<transcripts>/*/<uuid>.jsonl` (défaut `~/.claude/projects`) ; les messages que le harnais s'adresse à lui-même sous le rôle utilisateur (`<task-notification>`, `<system-reminder>`, retours de hook) sont ignorés. Comme un hook de fin de session peut faire écrire un second message, le texte final d'un tour est celui de TOUS les messages de l'agent : les blocs `<fiche>`, `<decoupage>`, `<avis>`, `<conseil>` se lisent dans le tour entier. Arrêt : `taskkill /T /F`.
- `codex` : `codex exec --json … -m`, reprise `codex exec resume <id>`, dérivation `codex exec fork`, prompt par stdin (`-`) ; pas de transcript lisible.
- `opencode` : `opencode run --format json -s <id> -m <fournisseur/modèle>`, `--fork` pour dériver ; modèles découverts par `opencode models` ; pas de transcript lisible.
- `agy` (Antigravity) : `agy --input-format stream-json --output-format stream-json [--conversation <id>] [--model <id>]` ; message en NDJSON sur stdin `{"event":"user","message":{"content":…}}` (`-p` exigerait le prompt en argument) ; événements `init` (conversation_id), `step_update` (`agent_response` + `text_delta`, `tool` ACTIVE) et `result` (`SUCCESS`/`ERROR`) ; ni dérivation, ni consigne système, ni transcript lisible ; modèles par `agy models`. Extraits réels : `tests/donnees/agy-*.jsonl`. Utilisable pour le travail principal d'une tâche (sélecteur de moteur, ou `[moteur] harnais_defaut = "agy"`).

- `copilot` : `copilot --output-format=json --allow-all-tools --no-ask-user --session-id=<uuid>|--resume=<id> [--model=<m>] -p <texte>` (`[harnais.copilot] prompt = "stdin"` : texte sur l'entrée standard) ; l'identifiant de session est choisi par GoldenBrain, l'événement `session` précède le lancement (INV-EXEC-3). Événements lus : `assistant.message`, `tool.execution_start`, `result`, `error` ; sans `result`, la fin propre est le code de sortie 0. Ni dérivation, ni consigne système, ni seuil de compactage (Copilot se compacte seul à ~95 %), ni mesure de jetons ou de quota (aucun champ documenté : INV-ECO-2 neutre) ; journal : `~/.copilot/session-state/<id>/events.jsonl` (ou `COPILOT_HOME`). Source : documentation officielle, SANS essai réel (schéma JSONL et syntaxe de `--resume` non vérifiés).

**Choix du moteur par tâche** : clés `harnais` et `modele`. `GET /harnais` → `[{"nom","disponible","motif","modeles","modele_defaut"}]` (`disponible` = exécutable trouvé ; `modeles` = liste de `[harnais.<nom>] modeles`, ou découverte si `"auto"`, en cache 10 min, hors de la boucle d'événements). `POST /taches/{id}/moteur` écrit les deux clés (chaîne vide = défaut) ; 409 pendant un tour ; changer de harnais retire `modele`. Même harnais, autre modèle : la conversation continue. Autre harnais : l'ancienne session est mémorisée (`<donnees>/etat/sessions.json`, `tache → {harnais: session}`), `session` reçoit celle du nouveau harnais si elle existe, sinon est retirée ; le premier message est précédé de `[Reprise de la tâche dans <harnais>. Lis sa fiche : <chemin>. Conversation précédente (<ancien>) : <chemin du transcript ou « non disponible »>.]`. Revenir à l'ancien harnais reprend sa session. INV-MOTEUR-1.

**Dérivation** (`POST /taches/{id}/deriver`) : crée une tâche dans le conteneur de l'origine ; `enfant` pose `parent` = origine, `soeur` copie le `parent` de l'origine ; `avec_fil` : le premier tour dérive la session de l'origine (409 si elle n'en a pas ou si le harnais ne sait pas dériver) ; `message` présent : soumis aussitôt.

**Propositions** (`propositions.py`, persistées dans `etat/propositions.json`) : `Proposition = {"n","type","tache","titre_tache","valeur","de","motif","etat": "en_attente"|"acceptee"|"refusee","cree"}`. `tache` peut désigner une autre tâche que celle qui propose (`de`). L'acceptation appelle la fonction du geste humain correspondant ; une exception laisse la proposition en attente.

| Type | `valeur` | Effet de l'acceptation |
|---|---|---|
| `deplacer` | conteneur (un simple nom de dossier est ramené à l'identifiant, sinon refus immédiat avec pistes) | déplace la tâche dans ce conteneur |
| `ticket` | titre ; `motif` d'au moins une phrase (refus 400 sinon), qui devient la description | dérivation `enfant`, avec fil si la tâche a une session |
| `projet` | nom | promotion sur place avec découpage |
| `lier` | `alimente:<cible>`, `prerequis:<cible>` ou `voir_aussi:<cible>` | crée le lien depuis `tache` |
| `operation` | nom ou chemin `A > B` de l'opération (existante ou nouvelle) | déplace le dossier du conteneur de `tache` sous le dossier de l'opération (créé s'il est nouveau, sous le dossier de la casquette, à défaut `Projets`) et retire son `parent:` (INV-ARBRE-2) : plan `geste.planifier_operation`, application par `Aligneur.appliquer` sous le verrou d'INV-ALIGN-2, point de restauration git compris. Acceptation par l'API seulement (`Moteur.trancher` refuse). 409, proposition laissée en attente : conteneur sans `contexte.md` (« promouvoir d'abord en projet »), tour sur une tâche du projet, destination existante, etc. |
| `tache` | titre ; `motif` d'au moins une phrase (refus 400 sinon), qui devient la description | crée une tâche `a-faire`, non lancée, dans le conteneur de `tache`, liée `voir_aussi` à `tache` |
| `renommer` | nouveau titre ; `motif` obligatoire (refus 400 sinon) | change le titre de `tache` (INV-RENOMMER-1, INV-RENOMMER-2) |
| `perimetre` | texte | soumet à `tache` `[Périmètre révisé, validé par l'utilisateur] <texte>` |
| `echeance` | `AAAA-MM-JJ` (refus immédiat si illisible) | pose `echeance` (INV-TEMPS-1) |
| `fermer` | `cloture` ou `abandonne` (refus immédiat sinon) | pose ce statut sur `tache` ; les propositions `fermer` d'un même auteur forment une « revue » sur la page Décisions (INV-DECISIONS-1) |

Sort d'une proposition à sa création : INV-INTERFACE-3.

## Codespace (`codespace.py`, `harnais/distant.py`)

- **Poste** : `gh` authentifié avec la portée `codespace` (`gh auth refresh -s codespace`) ; `[codespace] gh` de `config.toml` s'il n'est pas sur le PATH.
- **Rattachement** : un projet déclare son codespace par la clé `codespace:` de son `contexte.md` — un nom de codespace, ou un dépôt `propriétaire/nom` (le premier codespace de ce dépôt dans `gh codespace list`). Lu pour le conteneur de la tâche seulement.
- **État** : `GET /taches/{id}/codespace[?frais=1]` → `{declaration, ou, nom, etat, depot, erreur}` ; la liste de `gh` est gardée 15 s ; une erreur de `gh` se rend dans `erreur`, jamais en 500. L'interface dessine d'emblée le dernier état connu et le rafraîchit en arrière-plan (20 s).
- **Gestes** : `POST /taches/{id}/codespace/{code|web|arreter}` → `gh codespace code -c <nom> [--web]` (détaché : le codespace démarre s'il est arrêté) ou `gh codespace stop -c <nom>`. Ni création ni suppression.
- **Exécution distante** : clé `ou: codespace` de la tâche (`POST /taches/{id}/ou {"ou": "poste"|"codespace"}` ; `poste` retire la clé). Le moteur passe au harnais (`claude`, `codex`) une section de conf portant `distant` ; l'adaptateur garde sa commande non résolue et `distant.envelopper` la lance par `gh codespace ssh -c <nom> -- bash -lc '<script>'` : le script vérifie la présence du harnais (sinon code 127 et la commande d'installation dans l'erreur du tour), se place dans `/workspaces/<dépôt>`, transmet `ORCH_TACHE` et `ORCH_SAUTS` (pas `ORCH_URL` : l'API du poste est injoignable du codespace, `orch` n'y fonctionne pas). Prompt par stdin, flux analysé comme en local, arrêt par l'arbre de processus local (`gh` puis `ssh`). Les sessions restent dans le codespace : la reprise (`--resume`, `exec resume`) s'y fait ; la conversation se relit dans les journaux du poste ; « Reprendre au terminal » ouvre `gh codespace ssh … -- -t '<commande de reprise>'`.
- **Avec un dépôt** (INV-DEPOT-1) : `depot.conf_harnais` s'applique d'abord, `codespace.conf_tour` ensuite. Pour une tâche `ou: codespace`, le codespace l'emporte : le tour s'exécute dans `/workspaces/<dépôt du codespace>` ; le dépôt local ne sert que de dossier de lancement de `gh` (le « Dossier de travail » affiché reste celui du poste). L'interface native (INV-NATIF-1) est refusée (409) pour une telle tâche : ouvrir le codespace dans VS Code, ou « Reprendre au terminal ».

## Moteurs par rôle (`roles.py`)

Les rôles assistants ou temporaires ont chacun leur moteur ; le travail principal d'une tâche garde le moteur de la tâche, qui ne change que par le geste explicite (sélecteur de moteur, `POST /taches/{id}/moteur`) et n'est pas géré par `[credits]`.

```toml
[harnais.agy]       # modèle de chaque famille, par harnais (ids exacts de `agy models`)
familles = { rapide = "gemini-3.8-flash-medium", sonnet = "claude-sonnet-5-5-medium", opus = "claude-opus-5-5-medium" }
[harnais.claude]
familles = { rapide = "haiku", sonnet = "sonnet", opus = "opus" }

[credits]           # ordre des moteurs par famille
rapide = ["agy", "claude"]
sonnet = ["agy", "claude"]
opus = ["agy", "claude"]

[moteurs_par_role.conseil]        # conseil | persona | jardinage | mandat | fiche | tri | notes
famille = "rapide"                # ou harnais = "agy" + modele = "…" (explicite, l'emporte), repli = false
```
- Rôles : `tri` (agent de tri des envois Telegram), `conseil` (avis rapide), `persona` (revues et validation, sauf persona qui fixe son moteur), `jardinage` (revue de cohérence), `mandat` (découpage, contraction), `fiche` (réglage réservé). Un rôle absent garde le comportement par défaut : `[conseil] harnais` pour le conseil, harnais par défaut pour un persona, moteur de la tâche pour jardinage et mandat. Rôle, famille ou `[credits]` inconnus : erreur de configuration.
- Chaîne d'un rôle par famille : les harnais de `[credits][famille]` dans l'ordre, ceux qui n'ont pas de modèle pour la famille sautés. Réglage explicite (`harnais` + `modele`) : ce moteur, puis `repli_harnais` / `repli_modele` (défaut : harnais par défaut).
- L'ordre ne vaut qu'au premier tour d'une conversation : une conversation ne se transporte pas d'un harnais à l'autre. Un persona qui a déjà une session garde son harnais en tête de chaîne (`prefere`).
- `conseil` et `persona` : `Roles.lancer` parcourt la chaîne. `jardinage`, `mandat` et `tri` : tour éphémère (`Envoi.role`) sur le premier moteur de la chaîne, sans lire ni écrire la `session` de la tâche (sa conversation reste intacte, un préambule de reprise est ajouté) ; en cas d'échec, le même message repart en tête de file sur le moteur de la tâche, tour ordinaire.
- Repli : INV-MOTEUR-2.
- Visibilité : `GET /etat` → `roles: {tours: [{harnais, role, tours}], replis: [{role, de, vers, motif, date}], roles: {rôle: {famille, harnais, modele, moteurs}}, credits}` (compteurs depuis le démarrage) ; la page Réglages les affiche.

## Temps

- **En retard** : échéance antérieure à aujourd'hui (date du poste) ET tâche ouverte.
- Champs `"echeance": "AAAA-MM-JJ"|"", "priorite", "retard": bool` sur les nœuds de tâche, les résultats de recherche et `Tache` ; `GET /etat` porte `en_retard`.
- `POST /taches/{id}/temps {"echeance"?, "priorite"?}` (absent = inchangé, `""` = retiré) ; `POST /taches` accepte les deux clés.
- `GET /aujourdhui` → `{"date", "groupes": [{"cle": "retard"|"aujourdhui"|"semaine"|"amoi", "titre", "taches": [{"id","titre","statut","a_valider","resultat","essai","echeance","priorite","retard","fil_ariane"}]}]}`. Une tâche ouverte n'apparaît que dans le premier groupe qui la concerne : en retard ; aujourd'hui ; dans les 7 jours (`]aujourd'hui, +7 j]`) ; « À moi » (`retour-humain` ou à valider, sans échéance dans les 7 jours). Tri : priorité (haute, moyenne = normale, basse, aucune), échéance, titre.
- `orch arbre` et `orch chercher` ajoutent « — échéance AAAA-MM-JJ (en retard) ».

## Décisions (`decisions.py`, `api_decisions.py`)

- `GET /decisions` → `{"decisions": [Decision], "total"}`, trié du plus au moins prioritaire. `Decision = {"id", "genre": "reponse"|"validation"|"proposition"|"revue"|"echeance"|"scan"|"agent"|"routine", "libelle", "tache", "titre", "projet", "statut", "priorite", "echeance", "retard", "sujet", "fait", "muette", "question", "source": "commentaire"|"prochain_pas"|"agent"|"", "resultat", "essai", "fait", "proposition": Proposition|null, "fermetures": [{"n","tache","titre","statut","motif"}], "rapide", "rang", "motif", "auto"?: {"issue","motif","date"}}`, plus `"clos_auto": [entrée du journal INV-VALID-2]` (clôtures automatiques des 7 derniers jours, non rouvertes). `rapide` : proposition, ou validation dont le Résultat est annoncé.
- `GET /decisions/evitable` · `PUT /decisions/evitable {"actif"?, "seuil"?}` → `{"actif", "seuil"}` (INV-EVITABLE-1). Une ligne `reponse` ou `validation` porte `"evitable"?: {"score","sur","seuil","motif","criteres":[{"nom","ok"}]}`.
- `POST /decisions/documenter {"tache"}` → 202 `{"etat_execution"}`.
- `POST /decisions/scan` → `{"nouvelles", "ignorees", "erreurs": [{"tache","erreur"}]}` (INV-SCAN-1).
- `POST /decisions/valider {"taches": [id]}` et `POST /decisions/fermer {"numeros": [n]}` → `{"faits": [...], "echecs": [{"cible","erreur"}]}`. `GET /etat` porte `decisions` (nombre de lignes).
- Gestes à l'unité : `POST /taches/{id}/valider`, `/renvoyer {"texte"}` (refus avec motif), `/messages` (répondre), `/temps` (reporter), `/propositions/{n}/accepter|refuser`.
- Interface : bouton « Décisions » du bandeau (compteur), adresse `#decisions`, groupes par projet repliables, filtre « Rapides seulement », cases « à valider » et bouton « Valider la sélection ».

## Équipe et validation

**Personas** : un regard (mandat + focus), pas un agent à droits propres : il tourne dans une session normale du harnais. Un fichier `<id>.md` par persona dans `[equipe] dossier` (défaut `<donnees>/equipe/`), `id` = `[a-z0-9-]+` ; trois exemples inactifs amorcés au premier démarrage ; un retrait déplace le fichier dans `equipe/_retires/`.

```markdown
---
nom: Relecteur de code
actif: true
declenchement: filtre        # "toujours" | "filtre" | "a-la-demande"
casquettes: [C1, META]       # filtre facultatif
conteneurs: []               # filtre facultatif
mots: [code, script, dev]    # filtre facultatif : un mot dans le titre ou la fiche
harnais: ""                  # facultatif
modele: ""
---
## Mandat
…
## Focus
…
```
Sans filtre renseigné, `filtre` équivaut à `toujours`.

**Revue** : sur la déclaration `terminee` de l'agent (pas sur un statut posé à la main), chaque persona actif qui s'applique (hors `a-la-demande` et hors validateur du mode `persona`) lance un tour de revue, l'un après l'autre, dans SA conversation pour CETTE tâche (session mémorisée dans `etat/revues.json`, clé `tache|persona`). Message : mandat, focus, chemin de la fiche, chemin du transcript de la tâche, fiche courante, et l'ordre de finir par :

```
<avis>
verdict: ok | reserves
points:
- …
</avis>
```
Analyse tolérante ; bloc absent = `reserves` avec le texte final pour seul point. L'avis est persisté ; les réserves de toutes les revues partent en UN message `[Revue de <nom> : réserves] <points>` et comptent pour un renvoi ; un avis `ok` n'envoie rien. Le tour de persona passe son `modele` au harnais et, sans consigne native, ouvre sa conversation par la consigne. INV-EQUIPE-1.

**Validation** (`[validation] mode`, `persona`, `boucles_max`) :
- `humain` : une tâche terminée attend ; `POST /taches/{id}/valider` écrit `cloture` ; `POST /taches/{id}/renvoyer {"texte"}` soumet le texte (non compté dans les renvois).
- `persona` : après les revues, le validateur passe en dernier, seulement si aucune revue n'a de réserves en cours ni n'a échoué ; `ok` → `cloture` ; `reserves` → renvoi `[Validation de <persona> : réserves] …` tant que les renvois < `boucles_max`, sinon `retour-humain`. L'humain peut toujours valider ou renvoyer.
- INV-VALID-1.
- Par périmètre, `validation: automatique` remplace le validateur (INV-VALID-2) ; `[validation] revue_harnais`, `revue_modele` désignent le relecteur indépendant (vide = choisi d'office).
- `GET /validation-auto/reglage?conteneur=` → `{conteneur, mode (« » s'il hérite), accord}` ; `POST /validation-auto/reglage {conteneur, mode}` (400 mode inconnu, 404 conteneur) ; `POST /validation-auto/rouvrir {tache}` → `{tache, statut: "fait"}` (409 si non close automatiquement). Interface : sélecteur « Validation » dans la barre d'une note `contexte.md` (confirmation pour « automatique ») ; section repliable « Clos automatiquement » en bas de Décisions, bouton « Rouvrir ».

**À la demande** : `POST /taches/{id}/solliciter {"persona","question"?}` (humain, répond `{"tache","persona"}`) et `orch solliciter <persona> "<question>"` (agent ; refusé dans un tour de persona) lancent le même tour ; la réponse revient à la tâche comme message `[Avis de <nom>] …`, quel que soit le verdict.

**Formes** :
```
Persona = {"id","nom","actif","declenchement","casquettes":[str],"conteneurs":[str],"mots":[str],"harnais","modele","mandat","focus"}
Avis = {"persona","nom","verdict":"ok"|"reserves"|"en_cours"|"echec","points":[str],"date","origine":"revue"|"validation"|"demande","moteur","modele"}   # moteur et modèle du tour : preuve d'indépendance (INV-VALID-2)
```
`Tache` porte `"revues"` (dernier avis par persona) et `"renvois": int`.

**Paperclip** : INV-VAULT-4 ; `POST /taches/{id}/liberer` retire `paperclip` et `execution` (409 si absentes), sans toucher `updated`.

## Jardinage

La revue de cohérence est UNE tâche dédiée, créée à la première revue dans `vault.arrivee` (sans clé `nature` : INV-EXEC-7 ne la couvre pas), retrouvée ensuite par son identifiant mémorisé dans `<donnees>/etat/jardinage.json`. Une revue = un message (`[jardinage] message`) soumis à cette tâche ; son agent lit l'arbre (`orch arbre`, `orch chercher`, `orch lire`) et dépose des propositions. `[jardinage] rythme` = `a-la-demande` | `quotidien` | `hebdomadaire` (`heure`, `jour`) ; `plafond` et `recentes_jours` : INV-JARD-2. Le planificateur est une tâche asyncio démarrée et arrêtée par le `lifespan`, qui vérifie l'échéance une fois par minute. INV-JARD-1.

## Notes

- Une **note** = un fichier `.md` du vault ; identifiant = chemin relatif, séparateurs `/`. Exclus partout : tout dossier ou fichier dont le nom commence par un point (`.git`, `.obsidian`, `.claude`, `.trash`…) et `[notes] exclure`. Un chemin hors du vault ou exclu répond 404, une syntaxe interdite 400.
- **Résolution d'un wikilink** `[[cible]]`, `[[cible|alias]]`, `[[cible#ancre]]`, `![[cible]]`, comme Obsidian : chemin exact depuis la racine ; sinon relatif au dossier de la note ; sinon nom de fichier (sans `.md`, sans casse) — entre plusieurs, le plus proche du dossier de la note, puis le chemin le plus court. Cible absente = lien « à créer ».
- Écriture : INV-NOTE-2 ; renommer ou déplacer : INV-NOTE-3 ; `creer_dossier` accepté par la création et le déplacement. Un fichier de tâche ne se renomme pas par son fichier et ne se déplace pas pendant un tour ou une file d'attente. Le frontmatter n'est jamais réécrit hors du texte reçu.
- **Index** (`index_notes.py`) : en mémoire (titre, chemin, contenu), construit hors de la boucle d'événements au premier besoin, entretenu par (`mtime_ns`, taille) — seuls les fichiers changés sont relus ; `[notes] ttl_s` (défaut 5 s) ; périmé après tout déplacement de dossier. Recherche insensible à la casse et aux accents, tous les mots requis, guillemets pour une expression exacte, titre et nom pèsent plus que le corps, `dossier` restreint. Les liens entrants viennent du même index. Budget : ~4 000 notes ; index initial < 5 s hors boucle ; recherche < 150 ms ; aucune lecture disque bloquante dans la boucle.
- **Mentions non liées** : INV-NOTE-4 ; repliées sous la note, chargées à l'ouverture. Sur le détail d'une tâche, le bloc replié « Notes liées » montre les notes qu'elle cite, celles qui la lient et ses mentions non liées.
- **Graphe** (`graphe.py`) : nœuds = notes, tâches (fichier de tâche), conteneurs (`contexte.md`, sinon nœud synthétique `<dossier>/`) ; arêtes non orientées, une par paire, genre `alimente` | `prerequis` | `voir_aussi` (liens de tâches, prioritaires) puis `lien` (wikilink résolu) puis `appartient` (vers le conteneur le plus proche ; conteneur vers son englobant). Casquette normalisée (`C1`…`META`, `?` inconnue), projet = conteneur d'appartenance, tags du frontmatter (liste en ligne ou en bloc, sans casse ni accents). INV-GRAPHE-1, INV-GRAPHE-2. Mesure (vault réel, ~2 400 notes) : construction 0,9 s CPU, +5 Mo, servi du cache en < 0,1 ms ; global plafonné en 13 ms ; simulation à 2 000 nœuds ≈ 12 ms par pas, ~300 pas.
- Les extensions d'Obsidian (Dataview, Templater, bases) ne sont pas exécutées : leurs blocs s'affichent comme du code.
- SSE `note {chemin, ancien?}` après toute écriture, création ou déplacement faits par GoldenBrain ; plus `arbre` quand le fichier est une tâche ou un `contexte.md`.

```
NoteRef = {"chemin","nom","titre","type","maj"}
Note = NoteRef + {"contenu","mtime_ns": str,"frontmatter": {…},
        "liens": [{"brut","cible","chemin": str|null,"alias","ancre","incorpore": bool}],
        "entrants": [{"chemin","titre","extrait"}],
        "tache": id|null}
```

## Alignement

**Dossier attendu** d'un conteneur, calculé d'après sa place (jamais saisi) :
- conteneur sans `parent:` : aligné par construction (INV-ARBRE-2) ;
- rattachement vide (`parent: ""`) → `<projets>/<nom>` (`vault.projets`, défaut `Projets`) ;
- chemin `A > B` sans segment conteneur → `<dossier de la casquette>/A/B/<nom>` ; dossier de la casquette = l'unique dossier de `vault.casquettes` dont le nom commence par `<C>-`, à défaut `<projets>` ; une opération lue sur le disque garde son dossier ;
- chemin dont le dernier segment conteneur est C → `<dossier de C>/<segments d'opération suivants>/<nom>`.
`<nom>` = nom de dossier actuel, jamais renommé. **Aligné** = dossier actuel égal au dossier attendu.

**Gestes** :
- `GET /alignement` → `[Ecart]`, `Ecart = {"conteneur","titre","de","vers","conflit": str|null}` (destination existante, source ou destination hors vault, dossier parent d'un autre écart…).
- `POST /alignement/plan {"conteneurs": [id]}` → `Plan`, simulation qui n'écrit rien :
  ```
  Plan = {"deplacements": [{"de","vers"}],
          "reecritures": [{"fichier","lignes": int,"exemples": [{"avant","apres"}]}],
          "externes": [{"fichier","occurrences": int}],
          "avertissements": [str], "jeton": str}
  ```
- `POST /alignement/appliquer {"jeton", "point_git"?: true}` → `{"deplacements","fichiers_reecrits","commit": str|null,"arbre": {"noeuds"}}`. Jeton périmé (un fichier concerné a changé) : 409 « le vault a changé, refaire le plan ». Commit de restauration « GoldenBrain : avant alignement <date> ». Ensuite : SSE `arbre`, index des notes périmé, et `[alignement] apres` (commande facultative) lancée en tâche de fond.
- INV-ALIGN-1, INV-ALIGN-2, INV-ALIGN-3.

**Réécriture des références** (`references.py`, dans le vault seulement) — pour chaque chemin déplacé `de → vers`, dans les fichiers texte (`.md`, `.base`, `.canvas`, `.json` hors `.obsidian`, `.py`, `.toml`, `.yaml`) hors `vault.exclure`, `.git`, `.obsidian`, `.claude`, `Archives` :
1. chemins relatifs à la racine : `de/…` → `vers/…` quand `de` est un chemin entier ou un préfixe de chemin délimité, séparateurs `/` et `\` ;
2. chemins absolus `<racine du vault>/de/…` : idem, séparateurs conservés ;
3. liens relatifs `[[../…]]`, `[[./…]]`, `](../…)`, `](./…)` : résolus depuis l'ANCIEN emplacement de leur fichier, recalculés depuis le NOUVEAU si la source ou la cible a bougé (deux fichiers d'un même dossier déplacé : inchangé) ; ancres et alias conservés ; un lien déjà cassé est laissé tel quel ;
4. wikilinks par simple nom : jamais touchés (sauf renommage de note, INV-NOTE-3).
Dans le doute, rien n'est réécrit et un avertissement est émis : nom voisin plus long, casse différente, fichier non décodable, cible au-dessus de la racine, liens `..\`. Hors vault (`[alignement] externes`, défaut `~/.claude/skills`, `~/.claude/projects/*/memory`, `~/.claude/CLAUDE.md`) : occurrences comptées, jamais modifiées.

## Transformations

**Promotion sur place** — `POST /taches/{id}/promouvoir {"nom"?, "decouper"?: true}` → `{"conteneur", "tache"}` :
- le projet naît dans le dossier du conteneur de la tâche : `<dossier>/<slug>/contexte.md` (`type: contexte`, `nom`, `projet`, `casquette`, `created`, `updated` ; corps : titre + « Issu de la tâche [[<id>]] ») et `taches/`. Aucune clé `parent:` : la place se lit dans le dossier, le projet apparaît sous le conteneur d'origine, parmi ses tâches. `nom` absent = titre de la tâche. 409 si le dossier existe ou si les motifs `vault.taches` ne le couvriraient pas ;
- la tâche et sa descendance y sont déplacées ; la tâche et ses enfants directs perdent `parent` (ils deviennent des tickets du projet) ;
- si `decouper` : le mandat `[transformations] mandat_decoupage` est soumis à la conversation de la tâche ; l'agent doit finir par
  ```
  <decoupage>
  resume: une phrase sur le projet
  - titre: …
    description: …
  </decoupage>
  ```
  En fin de tour réussi, le moteur crée chaque ticket (`a-faire`, non lancé, description en corps ; titre déjà pris ignoré), écrit « Résumé : … » dans le corps du `contexte.md` et publie `arbre` ; `tour_fin` porte `decoupage: <nombre>`. Moins de deux tickets ou bloc absent : rien n'est créé, `decoupage: "insuffisant"`, la fiche le dit ; le mandat reste en attente UNE fois (l'interface propose « Relancer »), puis s'efface. Un mandat sans message en file (redémarrage, tour interrompu) est traité par le prochain tour réussi de la tâche. INV-TRANSFO-1.

**Réduction d'un projet en tâche** — `POST /conteneurs/reduire {"conteneur", "point_git"?: true}` → `{"tache", "archive"}` :
- admis : conteneur avec `contexte.md`, ni dossier de casquette, ni `_meta`, ni conteneur d'arrivée, sans sous-conteneur ayant des tâches ouvertes, dont le dossier ne contient ni `.git` ni `.claude` ; aucun tour actif, en file ou en revue sur ses tâches (INV-ALIGN-2). Sinon 409 explicite ;
- effets, tout ou rien (INV-ALIGN-1, commit « GoldenBrain : avant archivage ») : (1) une tâche est créée dans le conteneur parent du projet (à défaut celui de sa casquette, à défaut `vault.arrivee`), titre = nom du projet, corps = corps du `contexte.md` + liste des tâches absorbées (titre, statut, fiche résumée, session) ; (2) le dossier est archivé vers `Archives/<nom>-ARCHIVE-<AAAA-MM-JJ>/` (suffixe `-2`, `-3`… si pris), références réécrites ; (3) le mandat `[transformations] mandat_contraction` est soumis à la nouvelle tâche (une fiche unique, sous-tâches restantes, ce qui est abandonné et pourquoi). La contraction ne rend aucun bloc particulier.

**Avis d'un agent rapide** — `POST /conseil {"action": "promouvoir"|"reduire", "tache"?, "conteneur"?}` → `{"avis": "favorable"|"defavorable"|"indisponible", "motif", "duree_s"}` :
- conversation éphémère sur le moteur du rôle `conseil` (à défaut `[conseil] harnais` ; voir Moteurs par rôle) (aucune session gardée, aucun fichier du vault écrit), hors `simultanes_max`, consigne `[conseil] consigne` qui interdit tout outil d'écriture et exige `<conseil>\navis: favorable | defavorable\nmotif: une phrase\n</conseil>` ; faits fournis : pour `promouvoir`, titre, fiche, sous-tâches, nombre d'enfants ; pour `reduire`, nom du projet, tâches ouvertes et fermées avec titres et statuts, nombre d'autres notes du dossier ;
- délai `delai_s` dépassé, chaîne de moteurs épuisée (INV-MOTEUR-1, INV-MOTEUR-2), bloc absent, `actif = false` : `indisponible`, jamais d'erreur bloquante.

## Mode simple et réglages

Deux niveaux, réglables dans l'interface (page « Réglages ») et dans `config.toml` (`config.ConfigInterface`).
- **Mode simple** (défaut d'une installation neuve, `config.depart.toml`) : projets, tâches, conversation, statut, valider ; un seul vocabulaire, « projet » et « tâche ». **Mode avancé** : tout. Une configuration sans section `[interface]` reste avancée.
- `[interface]` : `mode` (`simple` | `avance`) ; un drapeau booléen par famille — `equipe` (personas et revues), `liens` (alimente / voir aussi, propagation), `alignement`, `jardinage`, `moteurs` (choix du harnais ; le modèle reste), `notes`, `transformations` (promouvoir, réduire), `conseil` ; absent = suit le mode (actif en avancé, débrayé en simple) ; `propositions` = `montrer` | `accepter` | `ignorer` (absent : `ignorer` en simple, `montrer` en avancé) ; `langue` = `fr` | `en` | `de` | `es` (absent : détectée par le navigateur au premier lancement, puis écrite ; INV-LANGUE-1).
- `GET /api/interface` → `{"mode", "familles": {famille: bool}, "propositions", "statut_retour"}` (valeurs effectives ; `statut_retour` en lecture seule, INV-STATUT-1). `PUT /api/interface` `{"mode"?, "familles"?: {famille: bool|null}, "propositions"?}` → même forme, 400 si valeur inconnue. Changer `mode` remet familles et politique au défaut du mode, avant d'appliquer `familles` et `propositions` du même appel (`null` = suit le mode). SSE `interface`.
- INV-INTERFACE-1, INV-INTERFACE-2, INV-INTERFACE-3.

## Connecteur Telegram (`telegram.py`)

- **Réception** : lecture longue `getUpdates` (`attente_s`), dans un fil démon (l'arrêt du serveur n'attend pas). Texte, photo (plus grande taille), document, note vocale, audio : pièces écrites dans `[telegram] reception` (défaut `Inbox/telegram/`), `AAAA-MM-JJ-HHMMSS-<message>-<nom>`, et une note de capture `…-telegram.md` (`type: capture`, `source: telegram`, `envoi: n`) qui les cite.
- **Tri** : chaque envoi (numéroté `n`) est soumis à la tâche permanente `titre_tri` (`nature: permanente`, créée au premier envoi dans `conteneur`, défaut `vault.arrivee`). Cette tâche garde sa conversation (session) sur le moteur du rôle `tri` (`[roles]`) : envois et réponses arrivent dans le même fil, pas de tour éphémère. Le message porte la consigne `[telegram] consigne`, la note, les pièces, le texte. L'agent questionne (`orch telegram`) ou range : `orch creer "<titre>" --conteneur <id> --envoi n [--lancer --mission "<consigne>"]` ou `orch rattacher n <id>`.
- **Retour** : l'issue d'un envoi (`POST /telegram/envois/{n}/issue`) répond sur Telegram, en réponse à l'envoi : « Tâche créée : <titre> — <fil d'Ariane> » ou « Rattaché à : … » ; la note reçoit `Rangé : [[<id>]]`.
- **Routage** : une réponse Telegram à un message du bot (ou à l'envoi rangé) devient un message `[Réponse Telegram] …` à la tâche correspondante (routes `discussion:message → tâche`, 1000 dernières). `orch telegram "<texte>"` envoie une question `[<titre>] <texte>` à la première discussion autorisée ; la réponse revient à la tâche (reply, ou le message libre suivant tant que la question est en attente : `attente`, une seule à la fois).
- **Compte rendu à valider** : `orch telegram "<texte>" --validation` envoie le compte rendu avec deux boutons, `valider` et `renvoyer` (`callback_data`, tâche retrouvée par la route du message). Valider pose `fait` par la voie humaine (`poser_statut(humain=True)`, comme `POST /statut`) ; Renvoyer ouvre l'attente : la remarque suivante de l'utilisateur revient à la tâche. Hors discussion autorisée : sans effet (INV-TELEGRAM-3).
- **Lancement** : `orch creer … --lancer [--mission "<consigne>"]` crée et lance la tâche ; le premier tour porte la mission, à défaut la description (`POST /taches` accepte `lancer` et `mission`).
- **Transcription** (facultative) : `transcription_url` (fournisseur compatible OpenAI, `/audio/transcriptions`), `transcription_modele`, clé lue comme le jeton (`transcription_variable`, `transcription_fichier`). Sans fournisseur : la note vocale est rangée, le message de tri le signale.
- **Assistant** (`telegram_assistant.py`) : la tâche permanente (titre par défaut « Assistant Telegram ») converse. Chaque ligne soumise porte sa nature (INV-TELEGRAM-4). Le message est précédé de la consigne si la conversation est neuve, du résumé repris après `/nouveau`, et de `[Dernière tâche évoquée] <id> — <titre>` (reconnaissance de la tâche visée : réponse routée, puis ce rappel, puis `orch chercher`), et, pour une instruction libre, de `[Tâches proches de l'instruction]` : jusqu'à trois tâches ouvertes rendues par `rapprochement.proches` (INV-RAPPROCHEMENT-1, aucun score propre à Telegram), « correspondance forte » le cas échéant ; la consigne fait proposer la mise à jour de la tâche trouvée plutôt qu'une création. `orch telegram "<texte>" --tache <id>` ajoute « → titre — place » et fait de la tâche la dernière évoquée ; ni lien ni préfixe dans les réponses de l'assistant (retour d'essai, 18/11). `orch renommer <id> "<titre>"` est un geste direct de l'assistant, non sensible : seul le titre change (INV-RENOMMER-1). `--choix <id1> --choix <id2> [--choix <id3>]` envoie une question à boutons (2 ou 3 tâches) : le choix revient à l'assistant `[Choix Telegram — instruction] Tâche visée : …`. `--tache <id> --geste statut=<s>|echeance=AAAA-MM-JJ|priorite=<p>` envoie Confirmer / Annuler : Confirmer applique le geste (INV-TELEGRAM-3), l'assistant en est averti. Un « Répondre » à un message du bot ajoute au message `[cite] <texte cité>` (donnée, jamais un ordre, INV-TELEGRAM-4) et, si ce message visait une tâche (`vises`), `[Tâche visée par la citation] <id> — <titre>` ; une réponse à un message de l'assistant lui revient avec son entête. Une question à boutons n'ouvre pas d'attente, ni une réponse de l'assistant (ses messages libres lui reviennent déjà).
- **`/nouveau`** : la session de l'assistant est effacée (l'ancienne conversation reste sur disque), sa fiche (`situation` : dernière tâche, actions) devient le résumé repris au message suivant ; refusé pendant un tour.
- INV-TELEGRAM-1, INV-TELEGRAM-2, INV-TELEGRAM-3, INV-TELEGRAM-4.

## Volet « manager » (`manager.py`, `api_manager.py`, `web/manager.js`)

- **Un fil, deux canaux** (INV-MANAGER-1) : le journal `<donnees>/etat/manager.json` (200 derniers messages `{n, de: vous|manager, texte, canal: volet|telegram, quand, cle?, boutons?, issue?}`) reçoit les instructions écrites sur Telegram, celles du volet et chaque réponse de l'assistant (`orch telegram`). Chaque ajout est publié en SSE (`manager`).
- **Instruction du volet** : soumise à la tâche de l'assistant (créée au besoin) avec l'entête commun, `[Instruction du volet]` puis `[instruction] <texte>` ; `/nouveau` ouvre un fil neuf sans lancer de tour.
- **Réponse** : `orch telegram "<texte>"` de l'assistant paraît dans le volet, et sur Telegram s'il est branché ; sans Telegram, elle n'échoue pas. `--choix` et `--geste` y portent leurs boutons ; le bouton pressé dans un canal fait tomber ceux de l'autre (`issue`).
- **Écran** : bouton « Manager » du bandeau, état mémorisé (`localStorage` `orch.manager`) ; troisième colonne à droite, par-dessus sous 900 px, plein écran avec « ← Retour » sur téléphone.

## Version et mise à jour

- **Serveur à jour** : INV-VERSION-1. `POST /redemarrer {"force"?, "par"?}` : 429 sans `force` si le serveur a moins de 60 s (INV-VERSION-2) ; 409 si un tour tourne ou attend en file (sauf `force`, qui arrête les tours comme un arrêt normal) ; sinon 202 `{"code_sortie": 3}`, puis sortie 3 après la fermeture propre (uvicorn : 5 s de grâce). `lancer.cmd` relance le serveur tant que le code de sortie est 3, sans rouvrir le navigateur.
- **Mise à jour en un geste** : INV-MAJ-1, INV-MAJ-2. Réglage `[mise_a_jour] branche` (défaut `main`) et `distant` (défaut `origin`). `GET /api/mise-a-jour[?actualiser=true]` → `{depot, branche, distant, branche_courante, locale, distante, retard, avance, modifies, dernier_controle, erreur?, nouveautes?}` (`nouveautes` quand `retard` > 0 : `[{version|null, entrees: [texte]}]`, INV-NOUV-1) ; `git fetch` au plus une fois par heure (5 min après un échec, la dernière valeur gardée et `erreur` renseignée) ou sur `actualiser`. `POST /api/mise-a-jour` : sous `Moteur.exclusif()` (409 si un tour tourne), avance le dépôt puis, si l'avance a eu lieu (`appliquee`), demande le redémarrage ; répond `{…état, appliquee, redemarre}`. `mettre-a-jour.cmd` = `python -m orchestrateur.mise_a_jour`, puis `POST /api/redemarrer` sur le serveur local s'il tourne ; codes de sortie : 0 fait ou déjà à jour, 1 refus, 2 erreur git.

## Commande `orch` (`cli.py`, stdlib seule)

Toujours par `python orch.py …` (jamais par un `.cmd` : espaces du chemin et guillemets). Elle lit `ORCH_URL`, `ORCH_TACHE`, `ORCH_SAUTS` (transmis + 1, INV-MSG-1), `ORCH_PERSONA` et `ORCH_JETON` (sur un exécuteur, porté en `X-Orch-Jeton`, INV-DISTANT-1). `orch executeur --serveur <url> (--code <code> | --jeton <jeton>) [--depots <dossier>] [--places N]` fait du PC un exécuteur (avec `--code`, le jeton est reçu et gardé ; ensuite `orch executeur` seul suffit) ; `orch jeton-executeur <nom> [--revoquer]` crée ou révoque son jeton depuis le chef (voir `docs/EXECUTEURS.md`).

```
orch arbre                                   # arbre des tâches ouvertes, texte
orch chercher "<mots>"
orch lire <id>                               # fiche + chemin d'une tâche
orch dire <id> "<message>"                   # source = ORCH_TACHE ; lance ou relance la tâche
orch conteneurs                              # identifiants et titres des projets
orch creer "<titre>" [--conteneur <id>] [--parent <id>] [--description "<texte>"]   # non lancée
orch fiche <id> [--statut en_cours|en_attente|terminee] [--fait …] [--situation …] [--reste …] [--resultat …] [--essai …] [--prochain-pas …]   # INV-REGROUPE-2 ; de = ORCH_TACHE (la mère)
orch arreter <id> | orch relancer <id>       # arrêt d'un tour ; reprise d'un tour interrompu
orch solliciter <persona> "<question>"       # tâche = ORCH_TACHE ; refusé dans un tour de persona
orch deleguer "<titre>" "<brief>"           # tâche enfant de ORCH_TACHE, qui l'alimente, lancée avec le brief (INV-ECO-1)
```

## Interface (`web/`)

- **Bandeau** : nom et icône, recherche (tâches ET notes, deux groupes ; Entrée = recherche plein texte complète dans le volet droit, extraits surlignés), « Aujourd'hui » (compteur de retard, vue `#aujourdhui`), « Décisions » (compteur, vue `#decisions`, INV-DECISIONS-1), pastille « n dossiers à aligner », page « Équipe », bandeau « serveur sur l'ancienne version » avec « Redémarrer » (attend le retour du serveur puis recharge ; sans relance après 20 s, invite à relancer à la main), bandeau « Une mise à jour est disponible » (`#maj-dispo`, contrôle au chargement puis toutes les 30 min).
- **Volet gauche** : onglets « Tâches » (arbre) et « Notes » (dossiers chargés niveau par niveau, replis mémorisés, compteur de notes). Ligne d'information (résultat d'un geste, lien « Annuler » 10 s) tenue dans la largeur du volet.
- **Vue en cascade** (sans tâche sélectionnée, ou au clic sur une casquette, une opération ou un conteneur) : sous-arbre en tableau indenté — titre, statut, activité, situation, moteur, liens, échéance, priorité (colonnes triables entre sœurs, projets et opérations en place, valeurs absentes en dernier), mise à jour ; compteurs par statut servant de filtres ; repli par niveau ; ⛓ « rattachement logique » sur un nœud `logique`.
- **Glisser-déposer** (volet gauche et cascade) : toute ligne d'opération, de conteneur ou de tâche est une source ; toute ligne est une cible ; cible admise surlignée, refusée marquée, sans appel au serveur. Tâche sur tâche : menu enfant / alimente / voir aussi. Autre dépôt d'une tâche : `POST /arbre/deplacer`. Projet ou opération (dépôt, « Monter », « Déplacer vers… ») : dialogue du plan (`alignement-plan.js`, section « Fiches mises à jour »), puis « Appliquer » ; « Annuler » rejoue le geste inverse (nouveau plan) ; un dossier déplacé est retrouvé par son titre. « Monter d'un niveau » : bouton au survol ou au focus (`montable`), raccourci Maj+←. Après un geste : arbre remplacé, replis et défilement conservés, élément sélectionné et visible.
- **IA au travail** (`web/verrou.js`, INV-VERROU-1) : pastille animée (`data-ia="1"`, immobile sous `prefers-reduced-motion`) sur la tâche occupée dans l'arbre, la cascade, « Aujourd'hui » et l'en-tête de la tâche ouverte, infobulle « moteur · depuis HH:MM » ; « IA : n » (`.ia-compte`) sur chaque ancêtre, calculé depuis `occupees` de `GET /etat` et l'arbre affiché ; mis à jour en direct. Un geste refusé (409 `occupee`) ouvre « Un agent travaille sur « X » depuis HH:MM. Continuer quand même ? » (focus sur « Non ») ; « Continuer quand même » rejoue la même requête avec `forcer: true` (`api.js`) ; « Non » ne change rien, sans bannière.
- **Tâche** : fil d'Ariane cliquable (`fil`) ; « Rattachée à : … » avec « Changer… » (dialogue « Déplacer vers… ») ; sélecteur de moteur (en-tête et à côté d'Envoyer) ; échéance et priorité éditables (aussi à la création) ; carte « Revues » ; boutons « Valider », « Renvoyer… », « Solliciter… », « Console GoldenBrain » (toujours offert, INV-CONSOLE-1), « Reprendre la main » (Paperclip), « Ouvrir la note », « Promouvoir en projet ».
- **Curseur « Moi / IA » et notes** (`web/executant.js`, `web/notes_tache.js`, INV-EXECUTANT-1, INV-EXECUTANT-2) : en tête de la tâche, « 👤 Moi » / « 🤖 IA » en un clic ; vers IA, dialogue « Confier la suite » (consigne facultative ; Annuler laisse la tâche à l'utilisateur). La zone de la tâche est séparée en deux panneaux côte à côte, chacun réductible d'un clic (état mémorisé dans le navigateur ; empilés sur écran étroit) : **Conversation** (inchangée en mode IA ; grisée, saisie désactivée, historique lisible en mode Moi) et **Notes** (notes datées en Markdown, liens `[[…]]`, ajout et « Modifier », dans les deux modes). Les pièces passent par des liens `[[…]]` (pas de téléversement). Pastille 👤 dans l'arbre et la cascade ; filtre « Qui la mène » (Toutes / À faire par moi / Confiées à l'IA).
- **Bouton « IA » des notes** (`web/notes_ia.js`, INV-EXECUTANT-3) : barre « IA » du panneau Notes (Résumer, Corriger, Synthétiser) sur la sélection dans une note, sinon sur toutes les notes ; proposition affichée (différence mot à mot pour « Corriger »), coût et modèle ; Remplacer la sélection (seulement si la sélection se retrouve telle quelle dans le texte d'une seule note), Insérer en dessous (sous la sélection, ou sous la dernière note pour « toutes les notes »), Annuler ; après application, « Annuler la modification ».
- **Conversation** : bascule « Étapes », mémorisée (localStorage), masquée par défaut. Masquée : messages de l'utilisateur, messages venus d'autres tâches ou de personas, et pour chaque tour la réponse finale (dernier message assistant non `secondaire`) ; pendant un tour, une ligne d'activité qui se remplace. Compteur « n étapes masquées » dépliable par tour. Un message d'utilisateur qui commence par un crochet est signé « GoldenBrain ». Wikilinks et chemins de notes cités deviennent cliquables.
- **Note** : fil d'Ariane des dossiers ; propriétés (frontmatter en tableau, repliable) ; corps rendu (titres, listes, cases, tableaux, citations, code, images et PDF incorporés par `/api/vault/fichier`, wikilinks résolus ou « à créer ») ; blocs `dataview`/`dataviewjs`/`base` en code avec la mention « bloc Obsidian non exécuté » ; liens entrants ; « Ouvrir la tâche » si c'est un fichier de tâche. Édition : « Modifier » (touche `e`), texte brut, Ctrl+S, Échap avec confirmation, avertissement avant de quitter ; 409 → « La note a changé ailleurs » (voir la version courante / garder la mienne). « Nouvelle note », « Renommer / déplacer… ». Sur un `contexte.md` et en tête de la cascade d'un conteneur : « Réduire en tâche ». « Graphe local », mentions non liées repliées.
- **Graphe** (`graphe.js`, `#g` ou `#g=<centre>`) : canvas 2D natif ; global (bouton « Graphe » du panneau Notes : filtres casquette, projet, genre, type, tag, période) ou local (« Graphe local » d'une note, « Graphe » d'une tâche ; profondeur 1 ou 2) ; recherche qui met en évidence ; survol = voisinage ; clic = ouvrir la tâche, la note ou le dossier ; molette = zoom, glisser = déplacer ; liste des nœuds repliée (accessibilité).
- **Transformations** : « Promouvoir en projet » et « Réduire en tâche » demandent d'abord l'avis du conseil (attente annulable : « Continuer sans avis ») ; `defavorable` → confirmation ; `favorable` ou `indisponible` → on continue, motif dans la ligne d'information. Promotion : dialogue (nom, case « Faire découper le travail par l'agent » cochée). Réduction : rappel de ce qui sera archivé, case « Point de restauration git ».
- **Alignement** : panneau des écarts (cases, tout cocher) ; « Voir le plan » → déplacements, fichiers et lignes réécrits avec exemples avant → après, références externes à corriger à la main, avertissements, case « Point de restauration git » cochée ; « Appliquer » ; compte rendu.
- **Équipe** : liste, création, édition, désactivation des personas.
- **Système visuel** (`web/style.css`, `web/theme.js`) : jetons CSS natifs, seule source des couleurs (chacune `light-dark(clair, sombre)`), rayons, espacements et durée ; les autres feuilles n'emploient que ces variables. Thème : celui du système, ou forcé par `data-theme="clair|sombre"` sur `<html>` (Réglages → Thème, mémorisé dans le navigateur). Police système, icônes SVG en ligne, aucune police ni bibliothèque téléchargée. Sous `prefers-reduced-motion`, aucune animation ni transition. Écran ≤ 900 px : une colonne, bandeau replié, page défilante.
- **Invitation à l'étoile** (`web/etoile.js`, INV-ETOILE-1) : fenêtre unique « GoldenBrain vous est utile ? » (Mettre une étoile / Plus tard / Ne plus demander ; Échap = Plus tard) ; interrupteur dans les Réglages.
- **Réglages** (`web/interface.js`, `web/reglages.js`, `web/reglages.css`) : page `#reglages`, bouton « Réglages » toujours visible. Classes sur `<body>` : `mode-simple|mode-avance`, `sans-<famille>`, `sans-propositions` ; les éléments d'une famille portent `f-<famille>` et sont masqués quand elle est débrayée, sans aucun appel à ses routes. `S.arbre` est une vue : en simple, les opérations en sont retirées (leurs projets remontent sous la casquette) et « conteneur » se dit « projet ». `alignement` débrayé : un projet n'a ni « Monter » ni « Déplacer vers… ». Section « Telegram » (`web/telegram.js`) : activer, jeton (champ masqué, jamais relu), discussions autorisées, dossier de réception, projet de la tâche de tri, « Tester la connexion ». La page affiche aussi les moteurs par rôle, les compteurs de tours et les replis (`roles` de `GET /etat`).
- INV-WEB-1.

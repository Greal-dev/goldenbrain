# Journal des décisions — GoldenBrain (orchestrateur)

Journal daté, une entrée par décision : **contexte**, **décision**, **conséquence**. Il porte l'historique (lots, amendements, révisions) que `docs/ARCHITECTURE.md` ne garde plus : celui-ci décrit l'état présent, ce journal dit pourquoi et dans quel ordre on y est arrivé.

Conventions :
- Entrées dans l'ordre chronologique ; identifiant stable `D-nnn`, jamais renuméroté. Une décision révisée n'est pas réécrite : une nouvelle entrée l'amende et les deux se renvoient l'une à l'autre (`Amende D-…`, `Amendée par D-…`).
- « Lot n » = numérotation de l'ancien ARCHITECTURE (lot 1 = MVP ; les lots 2 à 9 en sont les ajouts). Les hachages de commit sont ceux de l'historique git.
- Les invariants `INV-*` sont définis dans `docs/ARCHITECTURE.md` ; ici on ne retient que leur origine.
- Décideur : L'utilisateur sauf mention contraire ; « pilote » = la session de pilotage qui rédige les contrats et fusionne.

## 2026-11-12 — Lot 1 : MVP

### D-001 — L'orchestrateur pilote, il n'exécute rien (12/11, `77d4413`)
- **Contexte** : surface de pilotage de tâches confiées à des agents IA, à bâtir sur le vault Markdown ; Paperclip, en place, est propriétaire de ses tâches.
- **Décision** : chaque tâche est une conversation d'un harnais natif (Claude Code d'abord), reprise telle quelle ; le vault est la seule base de données ; aucune dépendance nouvelle, interface sans étape de build ; code, identifiants et messages en français ; module ≤ 500 lignes, en-tête de module, tests sur vault temporaire et avec un harnais factice. Contrat stable pendant l'EPIC : un changement se demande (`DEMANDE CONTRAT`), il ne se fait pas.
- **Conséquence** : carte de modules à frontières nettes (`config`, `fiches`, `vault`, `moteur`, `api`, `cli`, `harnais/`), `web/` ne parlant qu'à l'API.

### D-002 — Faits retenus sur Claude Code 2.1.322 et écart de `--bg` (12/11, `77d4413`)
- **Contexte** : le harnais doit se piloter sans état propre.
- **Décision** (faits vérifiés le 12/11) : `claude -p --resume <uuid>` continue la même conversation sous le même identifiant, depuis `C:\Users\utilisateur` ; `--session-id <uuid>` fixe l'identifiant d'une conversation neuve ; `--fork-session` (avec `--resume`) dérive sous un nouvel identifiant ; `--output-format stream-json --verbose` émet un événement JSON par ligne, le dernier (`type: result`) portant `session_id` et `result` ; le transcript vit dans `~/.claude/projects/<dossier>/<uuid>.jsonl` ; le prompt passe par stdin (citations Windows). **`claude --bg` est écarté** : refus de confiance depuis le dossier personnel, et chaque reprise change d'identifiant.
- **Conséquence** : adaptateur `harnais/claude.py` ; arrêt par `taskkill /T /F` de l'arbre de processus.

### D-003 — Édition du vault ligne à ligne, atomique, sous index (INV-VAULT-1 à 3) (12/11, `77d4413`)
- **Contexte** : le frontmatter de l'utilisateur (ordre des clés, commentaires, clés inconnues, fins de ligne) ne doit jamais être reformaté.
- **Décision** : INV-VAULT-1 — une réécriture ne touche que les clés gérées (`statut`, `updated`, `harnais`, `session`, `parent`, `projet`, `casquette`, `tags`, `alimente`, `voir_aussi`) et le bloc fiche ; jamais de `yaml.dump`. INV-VAULT-2 — écriture atomique (fichier temporaire + `os.replace`), un déplacement ne détruit jamais. INV-VAULT-3 — tout chemin écrit est sous `vault.racine` et provient de l'index.
- **Conséquence** : `fiches.py` est zone dangereuse. Le bloc géré est le dernier marqueur `debut` seul sur sa ligne suivi de son `fin` (bornage durci à la revue du 12/11, voir D-009).

### D-004 — Double run avec Paperclip : INV-VAULT-4 (12/11, `77d4413`)
- **Décision** : une tâche portant la clé `paperclip:` appartient à Paperclip pour son statut ; l'orchestrateur n'y écrit jamais `statut` ni `tags`.
- **Conséquence** : levé par réglage le 13/11 (D-022) ; geste `liberer` ajouté au lot 3 (D-016).

### D-005 — Exécution : pas de relance automatique, un tour à la fois, journal brut (INV-EXEC-1 à 4) (12/11, `77d4413`)
- **Décision** : INV-EXEC-1 — jamais de relance d'un tour ; un tour interrompu (arrêt, plantage, redémarrage) est marqué `interrompu` et attend un geste humain ; tours actifs persistés dans `<donnees>/etat/tours.json`, l'arrêt tue leurs processus. INV-EXEC-2 — un seul tour à la fois par tâche, messages suivants en file dans l'ordre. INV-EXEC-3 — l'identifiant de session est écrit dans la fiche dès le premier événement, pas en fin de tour. INV-EXEC-4 — chaque tour a son journal brut `journal/<date>/<id>-<HHMMSS>.jsonl`.
- **Conséquence** : états d'exécution `inactif`, `en_file`, `en_cours`, `interrompu` (mémoire du moteur, hors vault).

### D-006 — L'agent ne change jamais la structure seul : propositions (INV-EXEC-5) (12/11, `77d4413`)
- **Décision** : `orch proposer` crée une proposition ; seul un appel humain (`/accepter`) l'exécute ; le statut `fait` n'est écrit que sur geste humain. Types initiaux : `deplacer`, `ticket`, `projet`.
- **Conséquence** : amendée par D-015 (statuts déclarés) ; étendue par D-012 (types ajoutés). Limite connue, reportée : seule la commande `orch` tient INV-EXEC-5 et INV-MSG-1, un agent appelant l'API directement les contourne (voir D-010).

### D-007 — Messages entre tâches bornés (INV-MSG-1) (12/11, `77d4413`)
- **Décision** : un message entre tâches porte un compteur de sauts ; au-delà de `moteur.sauts_max`, refus (409).
- **Conséquence** : complété le 14/11 par INV-MSG-2 (D-034).

### D-008 — Garde locale et en-têtes anti-clickjacking, échappement côté interface (INV-API-1, INV-WEB-1) (12/11, `77d4413`, `7404d89`)
- **Décision** : INV-API-1 — écoute sur `127.0.0.1` seul ; `Host` limité à `127.0.0.1:<port>` / `localhost:<port>` (403) ; toute requête non-GET exige `X-Orchestrateur: 1` (403) ; toute réponse porte `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'self'; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'` et `X-Content-Type-Options: nosniff`. INV-WEB-1 (inscrit à part, `7404d89`) — tout texte venu de l'API est échappé avant balisage ; `innerHTML` n'est alimenté que par le rendu Markdown maison (`web/md.js`).
- **Conséquence** : exception pour `/api/vault/fichier` (D-025). Les styles en ligne ont été autorisés le 13/11 (D-011).

### D-009 — Corrections de l'essai réel et durcissement après revue adversariale (12/11, `9dcd160`, `d3e6fa6`, `b6128ee`)
- **Contexte** : premier essai réel, puis revue adversariale du MVP.

(Revue, « [DURCISSEMENT] ») : orphelins tués, tours actifs persistés (`interrompu` au redémarrage), frontmatter de repli, en-têtes anti-clickjacking, bloc fiche borné, déplacement transactionnel, liens hors vault ignorés, échec de tour affiché.
- **Conséquence** : le backlog (`BACKLOG.md`) est posé le soir du 12/11 avec la liste des points reportés (voir D-010).

### D-010 — Points de la revue adversariale du 12/11 reportés (non bloquants) (12/11, `d3e6fa6`)

### D-012 — Lot 2 : cohérence d'ensemble — liens, propositions enrichies, jardinage (13/11, `0ac4bde`, `d7d1fc7`)
- **Contexte** : L'utilisateur ouvre une conversation sur une idée ; l'orchestrateur doit la ranger, la relier aux tâches connexes sans hiérarchie, entretenir la cohérence et proposer des retouches d'organisation, tout en laissant l'utilisateur imposer sa structure à la main ou en langage courant. Tout changement venu d'un agent reste une proposition (INV-EXEC-5).
- **Décision** :
  - Liens fonctionnels : deux clés gérées, `alimente: [..]` (orienté, stocké du seul côté source ; « alimenté par » calculé, jamais écrit) et `voir_aussi: [..]` (symétrique, stocké d'un côté, affiché des deux), listes en ligne sur une ligne, clé retirée si vide ; un identifiant orphelin est ignoré à l'affichage mais conservé ; refus 409 : lien vers soi, doublon, cycle d'`alimente` ; un déplacement ou une promotion ne touche pas aux liens (portés par l'identifiant).
  - INV-LIEN-1 — propagation : à la fin RÉUSSIE d'un tour d'une source, chaque tâche ouverte qu'elle alimente reçoit un message (sauts + 1, INV-MSG-1) ; jamais après un échec, une interruption, ni vers une tâche fermée ; réglage `liens.propagation`.
  - Propositions enrichies : motif facultatif, types `lier`, `operation` (écrit `parent:` dans le `contexte.md` ; 409 sans `contexte.md`), `tache` (tâche `a-faire` non lancée + lien `voir_aussi`), `perimetre` (message `[Périmètre révisé, validé par l'utilisateur] …`) ; `tache` peut viser une AUTRE tâche que celle qui propose.
  - Routes `/taches/{id}/liens`, `/liens/retirer`, `/recherche` (tous les mots, sans casse ni accents, titre/fiche/fil d'Ariane), `/jardinage` ; commandes `orch chercher`, `orch proposer lier|operation|tache|perimetre`, `--motif` pour tous les types.
  - Jardinage : revue de cohérence = UNE tâche permanente (créée à la première revue dans `vault.arrivee`, identifiant mémorisé dans `etat/jardinage.json`) ; rythmes `a-la-demande | quotidien | hebdomadaire`. INV-JARD-1 — au plus une revue automatique par période ; échéance manquée = UNE revue au démarrage suivant, jamais de rattrapage multiple ; pas de revue si la précédente est en cours ou en file. Planificateur asyncio démarré par le `lifespan`, vérification chaque minute.
  - Consigne : recherche du voisinage, règle « si l'utilisateur demande un changement de structure ou de lien en conversation, propose-le aussitôt », sobriété (au plus trois propositions par tour, chacune avec son motif).
- **Conséquence** : modules `liens.py`, `recherche.py`, `jardinage.py`. Ajustements d'intégration (`73cf853`) : un déplacement proposé par nom de dossier est ramené à l'identifiant du conteneur ; plafond de propositions relevé pour la revue de cohérence ; `lancer.cmd` crée la configuration et ouvre l'interface.

### D-016 — Lot 3 : validation humaine ou par persona (INV-VALID-1), geste `liberer` (13/11, `da7c16a`, `6880e6d`)

INV-VALID-1 — une tâche verrouillée (INV-VAULT-4) n'est jamais validée ni renvoyée automatiquement ; compteur de renvois persistant (`etat/revues.json`), remis à zéro par une validation. ### D-017 — Lot 3 : équipe de personas (INV-EQUIPE-1) (13/11, `da7c16a`, `6880e6d`)
- **Décision** : un persona est un regard (mandat + focus), pas un agent à droits propres : il tourne dans une session normale du harnais, mêmes skills et mêmes droits. Un fichier Markdown par persona dans `[equipe] dossier` (défaut `<donnees>/equipe/`, peut pointer dans le vault), déclenchement `toujours | filtre | a-la-demande` (filtre par casquettes, conteneurs, mots ; sans filtre renseigné = `toujours`). Revue quand une tâche passe à Terminée : chaque persona applicable lance un tour dans SA conversation pour CETTE tâche (session mémorisée par `tache|persona`), et finit par un bloc `<avis> verdict: ok | reserves`. Réserves soumises à la tâche (comptées dans les renvois, plafonnées par `boucles_max`) ; `ok` n'envoie rien ; revues séquentielles, validateur en dernier et seulement si aucune réserve en cours. Sollicitation à la demande : `POST /taches/{id}/solliciter` et `orch solliciter`, réponse `[Avis de <nom>] …` quel que soit le verdict. INV-EQUIPE-1 — un tour de persona compte dans `simultanes_max`, a son journal, n'est jamais relancé seul et n'écrit pas dans le fichier de la tâche ; un persona ne se revoit pas lui-même, une revue ne déclenche pas de revue. Suppression = déplacement dans `equipe/_retires/`, jamais effacement.

### D-021 — Lot 4 : arbre libre, un élément se glisse sous un autre ou remonte d'un niveau (13/11, `ab0cd26`, `223b4d2`, `7049e66`, `a439033`)

Un changement de casquette met à jour `casquette` dans le `contexte.md` ET dans les tâches. INV-ARBRE-1 — un geste d'arbre n'édite que `parent`, `casquette` et `updated` (si existant), ne crée/déplace/renomme aucun dossier, tout ou rien (octets d'origine restitués en cas d'échec, 409). - **Conséquence** : la licence reste nommée en peu d'endroits (`LICENSE`, `NOTICE`, `pyproject.toml`, section licence des README, CONTRIBUTING) ; `ROADMAP.md` publie la feuille de route ; `.github/workflows/porte.yml` joue la porte sur chaque demande de fusion.
